## (a) Job Queue Semantics

FIFO schedules
jobs strictly
in arrival
order. It
is simple
and never
starves a
job, but
assumes all
jobs are
equal. Fair-share
allocates resources
proportionally across
users or
projects, so
one noisy
tenant cannot
starve everyone
else. Priority-weighted
queues rank
jobs by
numeric weight,
letting urgent
builds jump
ahead of
batch work.
Dominant Resource
Fairness, from
Mesos, measures
the largest
single resource
each job
holds and
schedules to
equalize that
dominant share
across jobs,
not just
one axis.
Weighted fair
queueing comes
from networking,
where each
flow gets
a guaranteed
share of
bandwidth. A
token bucket
issues credits
at a
fixed rate,
bounding burst
traffic. FIFO
breaks when
durations differ
widely, because
long batch
tasks block
short urgent
work, inflating
tail latency.
It also
fails when
tenants must
be isolated
from one
another. GitHub
Actions runs
queued workflow
jobs roughly
FIFO within
a repository,
constrained by
concurrency and
per-repository limits.
GitLab CI
exposes a
per-project priority
queue with
normal, urgent,
and paused
states. Concourse
derives order
from the
pipeline graph
and resource
versions, not
a global
queue. For
a self-hosted
runner under
one hundred
concurrent jobs,
start with
FIFO, add
a priority
override, and
cap each
tenant with
fair-share limits.

Reference: Dominant Resource Fairness: Fair Allocation of Multiple Resource Types, Mohit Ghodsi et al. (CMU / UC Berkeley), 2011, https://www.usenix.org/conference/nsdi11/technical-sessions/presentation/ghodsi

## (b) Cache Poisoning Defenses

Content-addressable storage
names every
artifact by
its cryptographic
hash, so
a stored
blob is
immutable and
tamper-evident. If
an attacker
rewrites the
file, the
hash changes
and the
key no
longer matches.
Signature verification
adds a
second layer.
Tools like
cosign and
sigstore sign
build artifacts
and verify
them against
a trusted
key or
certificate before
use. For
CI caches,
derive the
cache key
from the
commit SHA
plus the
dependency lockfile
hash, because
either change
can alter
the exact
set of
installed packages.
Use the
git commit
SHA and
a hash
of package-lock.json
or requirements.txt
as the
key inputs.
Pin action
versions by
digest hash
when you
cache, so
a moved
action tag
cannot silently
swap in
different code.
For eviction,
LRU keeps
the most
recently used
entries, TTL
drops entries
after a
fixed age,
and a
hybrid combines
both, expiring
by age
or by
size pressure.
GitHub Actions
cache stores
a tarball
on blob
storage, keyed
by a
string your
workflow computes,
and retrieves
it on
a matching
key. The
actions/cache action
packs the
requested paths
into a
tar.gz, uploads
it, and
matches keys,
falling back
to restore
keys on
a miss.
Treat restored
cache as
untrusted input.

Reference: cosign: signing and verifying container images and artifacts, Sigstore Project (Google), 2021, https://www.sigstore.dev/

## (c) Secret Injection: OIDC vs Long-Lived Tokens

OIDC token
exchange replaces
stored long-lived
credentials with
short-lived identity
tokens. GitHub
issues an
OIDC token
from ACTIONS_ID_TOKEN_REQUEST_TOKEN,
GitLab issues
a CI_JOB_JWT,
and Buildkite
supports OIDC
federation. These
tokens typically
live about
one hour,
then expire,
which lets
them be
rotated and
revoked quickly.
The audience
claim restricts
a token
to a
specific issuer,
like one
cloud account
or workload
identity pool,
so it
cannot be
replayed elsewhere.
The CI
provider reissues
a fresh
token each
job, making
rotation automatic
with no
manual re-issuance.
Federation maps
the CI
identity directly
into the
target system.
AWS uses
role assumption
via AssumeRoleWithWebIdentity,
GCP uses
Workload Identity
Federation, Azure
uses federated
credentials, and
Kubernetes uses
projected service
account tokens.
OIDC trades
one-time trust-anchor
configuration, defining
issuers and
subject claims,
for no
secret distribution.
Long-lived stored
secrets are
dangerous because
they sit
in a
secret store
forever, can
leak, and
cannot be
scoped to
a single
run. The
CircleCI December
2022 incident,
where exposed
credentials let
attackers run
jobs, shows
why stored
tokens are
risky. For
OpenForge, prefer
OIDC federation
to cloud
and Kubernetes
targets, keep
any remaining
secrets in
a managed
store with
per-repository scoping,
and never
embed long-lived
tokens in
the workflow.

Reference: OpenID Connect Core 1.0, OpenID Foundation, 2014, https://openid.net/specs/openid-connect-core-1_0.html

## (d) Network Egress Filtering

Egress filtering
controls what
a runner
can send
to the
outside network.
A forward
proxy like
Squid intercepts
outbound traffic
and enforces
policy. Redirect
all traffic
through the
proxy at
the firewall
level so
connections are
impossible, and
log every
denied egress
attempt because
they reveal
compromise. An
allowlist permits
only known-good
destinations, while
a denylist
blocks known-bad
ones, but
allowlists are
far safer
by default
because they
deny everything
new automatically.
DNS filtering
blocks DNS-over-HTTPS
and redirects
NXDOMAIN responses,
catching traffic
that tries
to bypass
the proxy.
Combine that
with IP
allowlists for
package registries,
pinning npm,
PyPI, and
Maven to
their published
IP ranges.
TLS SNI
filtering inspects
the Server
Name Indication
field in
the handshake
to decide
on the
destination hostname
without full
decryption. GitHub
Actions hosted
runners run
on Microsoft
infrastructure and
restrict egress
to needed
services, while
self-hosted runners
depend on
the host
network, so
filtering is
the operator
responsibility. Buildkite
self-hosted agents
run on
your machines,
so egress
control is
entirely yours
to implement.
The practical
limit is
that DNS-over-TLS
and DNS-over-HTTPS
let clients
resolve names
without going
through your
resolver, which
defeats DNS-based
filtering, so
you must
also block
or intercept
those channels.

Reference: Squid Proxy Cache documentation, The Squid Community, 2023, https://www.squid-cache.org/

## (e) Ephemeral vs Persistent Runners

Ephemeral runners
are fresh
for each
job and
destroyed afterward,
so no
state, files,
or credentials
leak between
jobs. Persistent
runners stay
alive, which
enables faster
startup because
the image
is already
pulled and
caches are
pre-warmed. The
cold-start cost
of an
ephemeral runner
includes container
spin-up, image
pull, and
dependency install,
which can
add minutes
per job.
Persistent runners
avoid that
repeated work.
A warm
persistent pool
lets you
snapshot dependencies
into a
reusable layer,
and measure
the break-even
point, because
persistent payoff
grows with
image size.
Security favors
ephemeral, because
a compromised
job cannot
inspect leftover
secrets or
artifacts from
other tenants.
Performance favors
persistent, especially
for large
monorepos where
a full
dependency build
dominates. Persistent
runners make
sense for
self-hosted GPU
runners, where
provisioning a
GPU machine
is expensive,
for repos
with huge
dependency trees,
and for
runners holding
expensive software
licenses that
must be
reused. GitHub
Actions uses
an ephemeral
Linux container
per job,
refreshed after
each job
since the
2022 transition.
GitLab offers
both shared
and specific
runners, where
specific self-managed
runners are
typically persistent
and reused
across jobs.
For OpenForge,
default to
ephemeral for
security and
use persistent
only for
GPU and
large-repository pools.

Reference: About GitHub-hosted runners, GitHub Docs, 2023, https://docs.github.com/en/actions/using-github-hosted-runners/about-github-hosted-runners

## (f) Cross-Repo PR Triggers

Cross-repository pull
requests create
a core
trust problem.
A fork
pull request
runs untrusted
code from
an external
contributor, yet
the workflow
may need
access to
your repository.
GitHub's pull_request
event runs
in the
fork's context
with no
write access
and no
secrets by
default, which
is safe.
The pull_request_target
event runs
in the
base repository
context with
write access
and secrets,
so it
is dangerous,
because it
can execute
untrusted code
while holding
those credentials.
The strong
recommendation is
to never
run pull_request_target
on fork
pull requests,
since that
combination grants
untrusted code
write access
and secret
access. The
fork-based permission
model separates
what can
run from
what can
touch. The
safe pattern
is to
run untrusted
jobs under
pull_request with
no secrets
and no
elevated write
token, and
only run
trusted, secret-bearing
steps after
the pull
request is
approved and
merged, or
in a
separate restricted
workflow. GitLab
runs merge
requests from
forks without
secrets by
default, keeping
the fork
strictly isolated.
Buildkite does
not run
pull requests
from forks
by default
at all,
requiring explicit
configuration. For
OpenForge, default
fork pull
requests to
no secrets
and no
write token,
and gate
privileged steps
behind explicit
human approval.

Reference: Security hardening for GitHub Actions, GitHub Docs, 2023, https://docs.github.com/en/actions/security-guides/security-hardening-for-github-actions
