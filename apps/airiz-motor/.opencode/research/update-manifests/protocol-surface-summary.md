# Auto-Updater Protocol Surface Reference

> **Scope.** AIRIZ Motor Console needs the protocol surface of every major auto-updater to find a common subset for a unified signed-manifest layer. This document is the diff substrate for that exercise.
> **Convention.** "Manifest" = the metadata side-channel that points clients at a candidate update. "Signing" = the cryptographic check applied to the manifest and/or the binary payload. "Cache" = on-disk staging area for the next-version payload before swap. "Rollback" = explicit support for reverting to a known-good version (vs. merely "no version is forced").
> **Provenance.** Direct canonical fetches on 2026-11-05: v2.tauri.app/plugin/updater/, learn.microsoft.com/.../app-installer/update-settings, developer.chrome.com/docs/workbox/modules/workbox-window, docs.expo.dev/eas-update/introduction, sparkle-project.org/documentation, developer.apple.com/app-store/review/guidelines/. Where a number is critical (sunset dates, version support floors) the URL is cited inline.

## 1. Squirrel.Windows

| Field | Value |
|---|---|
| Manifest | **`RELEASES`** (per-update plain text file, one line per release: `<sha1> <relative-path> <size-in-bytes>`), plus per-package **`.nuspec`** (NuGet manifest). No JSON. |
| Signing | **Authenticode** on the package (the `.exe` / `.nupkg` artifact itself). The RELEASES file is *not* cryptographically signed — Squirrel relies on Authenticode + the fact that Squirrel.Windows itself runs as a desktop updater outside an AppX/MSIX context. |
| Provider | Any HTTP/S host serving `RELEASES` + NuGet packages (typically GitHub Releases, S3, Azure Blob). |
| Channel | None natively — channel selection is by pointing the client at a different feed URL. |
| Delta | **No native binary delta.** Squirrel ships full NuGet packages per release; partial updates are by NuGet's own package delta, which is poor. |
| Cache path | `%LocalAppData%\<AppName>\packages` (NuGet-style staging). |
| Rollback | **None.** Squirrel will only move forward (`releases` is append-only by convention). Downgrades are caller-implemented. |
| Store constraints | Not for Microsoft Store (Squirrel ships Win32, not MSIX). Windows SmartScreen is the only friction layer. |
| Known issues since 2022 | Project is in maintenance-only mode (last meaningful release Squirrel.Windows 1.5.2, 2017; sporadic fixes since). Electron-forked variant in `electron-winstaller` follows the same format. |

**Takeaway for unified layer.** RELEASES is the only format among the nine here that is *plain text + SHA-1*. SHA-1 is collision-vulnerable and should be replaced with SHA-256 minimum in any new design.

## 2. Sparkle (macOS)

| Field | Value |
|---|---|
| Manifest | **`appcast.xml`** — RSS 2.0 feed with `<rss><channel>` wrapping one `<item>` per release. Each item carries `<enclosure>` (url, length, type), `<sparkle:version>`, `<sparkle:shortVersionString>`, `<sparkle:edSignature>` (base64 ed25519 signature over enclosure URL+length), optional `<sparkle:delta>`, `<sparkle:minimumSystemVersion>`, `<pubDate>`, and `<description>`/`releaseNotesLink`. |
| Signing | **EdDSA (ed25519)** since Sparkle 2.0. Legacy DSA is deprecated; Sparkle still verifies DSA for backward compat. Optional **signed feed** (`SURequireSignedFeed`, Sparkle 2.9+) signs the appcast XML itself, validated against `<sparkle:edSignature>` over the canonicalized feed. Public key embedded in `Info.plist` as `SUPublicEDKey`. |
| Provider | Any HTTP/S host serving `appcast.xml`. Notarized DMG/ZIP/tar.xz are the canonical artifacts. |
| Channel | None native. Multi-channel via multiple feed URLs (e.g. `appcast-beta.xml`). `<sparkle:channel>` is documented in the schema for self-routing. |
| Delta | **`*.delta`** binary delta patches (Bsdiff-derived, Sparkle-specific container). Generated by `generate_appcast`. Falls back to full enclosure if delta fails checksum. |
| Cache path | `~/Library/Caches/<bundle-id>/Sparkle/` (download staging); final swap via DMG/ZIP replace-and-restart. |
| Rollback | No native rollback. Version comparison is forward-only (`CFBundleVersion` increment required). |
| Store constraints | **Not** for Mac App Store — App Sandbox disallows the XPC installer service Sparkle uses. Apple notarization + Developer ID required for distribution outside the App Store. |
| Known issues since 2022 | Sparkle 2.0 GA (2022) replaced DSA with ed25519 by default; 2.7 added Apple Archive support; 2.9 added signed feeds and md release notes. `SUVerifyUpdateBeforeExtraction` is the recommended safety posture. |

**Takeaway for unified layer.** Sparkle is the most opinionated schema (RSS + custom namespace) but the cleanest security model (ed25519 + optional feed signing). Delta is non-trivial to replicate.

## 3. electron-updater

| Field | Value |
|---|---|
| Manifest | **`latest.yml`** (Windows/Linux), **`latest-mac.yml`** (macOS), **`latest-linux.yml`** (Linux-specific). YAML with keys: `version`, `files[]` (each: `url`, `sha512`, `size`, optional `blockMapSize`), `path`, `sha512`, `releaseDate`. Companion blockmap files (`*.blockmap`) for differential. |
| Signing | **ed25519** keypair, public key injected at build time (`signtool`-equivalent or `@electron/asar` integrated signing). The `.yml` is **not** itself signed — the binary payload is. (Caveat: malicious server can swap `latest.yml` to redirect URL; mitigation is to use a provider with signed releases or validate `sha512` against a known manifest.) |
| Provider | First-class: **GitHub Releases**, **S3**, **generic HTTP** (`GenericProvider`). Also Bazaar, Bintray (deprecated), custom. |
| Channel | `channel` field in updater config + filename convention (`latest.yml` for `latest`, etc.). Multi-channel via `channels` array or per-channel file. |
| Delta | **Differential updates** via `blockMapSize` / `*.blockmap`. `differentialDownload` module (blockmap + binary diff) ships smaller payloads. Falls back to full download. |
| Cache path | OS-conventional: `%LocalAppData%\`<productName>`\UpdateCache\` (Windows), `~/Library/Caches/<bundle-id>/` (macOS), `~/.cache/<productName>/` (Linux). |
| Rollback | None native. Forward-only version comparison. |
| Store constraints | None (designed for direct distribution). Mac App Store disallows `electron-updater` because Sparkle-style code swap violates Guideline 2.5.2 (see §5). |
| Known issues since 2022 | `electron-updater` has been moved into `electron-builder` namespace; maintained by `develar`. The yml-only-signing model has produced a recurring class of "attacker compromises CDN and serves a tampered yml with a malicious payload" issues — community mitigations include custom `verifyUpdateCodeSignature` hooks. |

**Takeaway for unified layer.** YAML is the odd one out (everyone else is JSON/XML). The signed-yaml gap is exactly the gap a unified R2-signed-manifest layer should close.

## 4. @tauri-apps/updater (Tauri 2.x)

| Field | Value |
|---|---|
| Manifest | **Signed JSON.** Either a **static JSON** (`latest.json`, `macos.json`, etc.) with `{version, notes, pub_date, platforms: {<target>: {url, signature}}}` or a **dynamic JSON response** (`{version, notes, pub_date, url, signature}`) from a server that can return 204 No Content when no update. |
| Signing | **ed25519.** Public key inlined in `tauri.conf.json` (cannot be a file path). Private key at build time via `TAURI_SIGNING_PRIVATE_KEY` env var (must NOT be `.env`). Mandatory — "This cannot be disabled." |
| Provider | Any HTTPS endpoint. Endpoint URL templates support `{{target}}`, `{{arch}}`, `{{current_version}}` interpolation. The plugin probes each endpoint and falls through on non-2xx. |
| Channel | Channel = endpoint selection. Stable practice: separate endpoint per channel (e.g. `https://releases.myapp.com/{{target}}/stable/{{current_version}}`). Runtime `endpoints()` builder API allows dynamic channel switching. |
| Delta | **No built-in delta.** Bundle formats: `.AppImage` (+ `.sig`), `.app.tar.gz` (+ `.sig`), `.msi`/`.exe` (+ `.sig`). Full payloads only. `v1Compatible` mode adds intermediate `.zip` wrappers for legacy migration. |
| Cache path | Tauri-managed inside the install dir; installer (`MSI`/`NSIS`/`.pkg`) handles staging. |
| Rollback | **Yes, opt-in.** Default is forward-only. `version_comparator` builder API lets the server return a lower version and have the client apply it (rollback). |
| **Platform constraint** | **DESKTOP ONLY.** The plugin targets `cfg(any(target_os = "macos", windows, target_os = "linux"))`. iOS and Android are explicitly **out of scope** — Tauri does not provide an OTA story for mobile; mobile updates must go through App Store / Play Store by rebuilding the binary. |
| Store constraints | Same as Sparkle on macOS (Developer ID + notarization), Authenticode on Windows. |
| Known issues since 2022 | Tauri 1.0 updater had several CVEs (signature bypass, path traversal) fixed in 1.0.x. Tauri 2.0 stable (late 2024) ships the current `tauri-plugin-updater` (v2). Windows installer limitation: app must exit before MSI install completes (uses `on_before_exit` hook). |

**Takeaway for unified layer.** This is the cleanest "modern" design — ed25519 over JSON, manifest cryptographically tied to payload, server-controlled version (rollback-friendly). It's the closest in shape to what AIRIZ needs. **The desktop-only constraint is a critical boundary**: anything we unify must keep a separate pathway for iOS/Android (Capacitor Live Update territory).

## 5. Capacitor Live Update (Capawesome + Capgo)

| Field | Value |
|---|---|
| Manifest | Per-channel **JSON manifest** served from a backend or from a Capgo/Capawesome cloud endpoint. Typical schema: `{id, version, channel, bundle: {url, checksum (sha256), signature?}, rollout?, minNativeVersion, mandatory?}`. Capgo adds metadata fields like `alias`, `stats`. |
| Signing | **Checksum + optional signature.** Mandatory checksum is SHA-256 of the bundle. Optional RSA/ECDSA signature over the manifest. Capgo adds server-side signature pinning with a public key embedded in the Capacitor config. |
| Provider | Capgo cloud (managed), Capawesome Cloud, or self-hosted (any HTTP/S host + an `update` plugin that fetches the manifest). |
| Channel | **First-class**: `production`, `staging`, custom channels. Channels are server-side; client selects via `channel` in Capacitor config. |
| Delta | No binary delta — full bundle (JS + assets + Capacitor config patch). Some providers do server-side incremental bundling (Capgo's "partial" updates). |
| Cache path | Bundles cached at `<app-container>/Library/Application Support/<bundle-id>/capacitor-updates/` (iOS) or equivalent on Android. Next-launch swap. |
| Rollback | **Yes** — Capgo has explicit "revert to previous" CLI/API. Self-hosted: client pins to a `version` or `channel + version` and the server can serve an older bundle. |
| **Store constraints** | **iOS App Store: hard constraint.** Apple App Review Guideline **§2.5.2**: "Apps should be self-contained in their bundles, and may not read or write data outside the designated container area, nor may they download, install, or execute code which introduces or changes features or functionality of the app." Pure JS/asset updates are *tolerated* but functionally-changing updates are rejected. **Google Play: similar but looser** — `targetSdkVersion` rules matter; Play's own "targeted delivery" is preferred for staged rollouts. |
| Known issues since 2022 | Capgo forked from Capawesome Cloud in 2022 and is now the dominant managed provider. The two products are *not* protocol-compatible despite sharing the "capacitor-live-update" root. Apple's enforcement against code-changing OTA updates has tightened; many devs use Cordova-style HTML asset swaps to stay compliant. |

**Takeaway for unified layer.** The signing model here is the loosest of the nine. Any unified layer must explicitly handle the "Asset-only update on iOS" boundary — iOS-bound clients must refuse to apply any update that would change behavior.

## 6. Expo Updates (EAS Update)

| Field | Value |
|---|---|
| Manifest | Server-side **manifest JSON** fetched at runtime by `expo-updates`. Schema includes `id` (UUID), `createdAt`, `runtimeVersion`, `message`, `metadata`, `assets[]`, `launchAsset`, `exportedForEmbeddedOnly`, `channels[]`. Updates are signed bundles; the manifest is served by EAS. |
| Signing | **Server-controlled.** EAS Update is closed-source server; clients trust the HTTPS endpoint. Self-hosted option exists (`expo-updates` with a custom URL) but the manifest format is Expo-specific. No public-key pinning in the default config. |
| Provider | **EAS (managed)** or **self-hosted.** Self-hosting requires serving the manifests at an endpoint defined in `app.json`'s `updates.url`. |
| Channel | **First-class.** `eas update --channel production` is the headline feature. Channels = branches in EAS; clients point at a channel and the server routes. Branching supports merging, forking, and rollouts. |
| Rollout | **Per-channel percentage rollout** is built in: `eas update --branch production --rollout 25%` ships to a fraction of devices via hash-bucketed assignment. Plus "Republish" for instant revert. |
| Delta | **No binary delta.** Full update bundles. Native code can't be replaced (separate binary build required). |
| Cache path | `<app-container>/Documents/ExponentExperienceData/<%40 anonymous id>/EXUpdates/` (managed by `expo-updates`). |
| Rollback | **Yes.** "Republish for reverting mistakes" + `runtimeVersion` policy ensures updates only land on builds with compatible native code. |
| Store constraints | Apple §2.5.2 still applies — Expo Updates explicitly notes that changes to *native code or native dependencies* require a new binary submission. JS/asset updates are fine. Google Play allows but recommends Play's own delivery. |
| Known issues since 2022 | **CodePush sunset 2025-03-31** pushed many CodePush users here. Migration guide is in `docs.expo.dev/eas-update/codepush`. Classic Updates (`expo publish`) was deprecated Dec 2021. **Recent issue: `expo-updates` runtime-version mismatch errors are noisy and the recovery path is non-obvious.** |

**Takeaway for unified layer.** Best-in-class channel + rollout story. The manifest format is non-portable (Expo-proprietary), but the **semantics** (channel + rollout % + runtime-version pin) are exactly what AIRIZ needs to standardize on.

## 7. CodePush

| Field | Value |
|---|---|
| Manifest | CodePush server returns a JSON `UpdateCheckResponse` with `{updateAvailable: bool, updateMetadata?: {deploymentKey, appVersion, label, packageHash, isMandatory, ...}}`. Client then downloads a `.zip` package from CodePush CDN. |
| Signing | No public-key signing. HTTPS-only trust on CodePush's CDN (managed by App Center). Self-hosted is theoretically possible but unsupported. |
| Provider | **App Center** (was Microsoft's, now sunset). |
| Channel | `deploymentKey` per environment (Production, Staging). No native rollout % — release trains via deployment keys. |
| Delta | **No delta.** Full `.zip` per release. |
| Cache path | `<app-container>/Library/Caches/com.microsoft.appcenter` (iOS) or app-private storage on Android. |
| Rollback | Manual via CLI: `code-push rollback <appName> <deploymentName>` re-promotes the previous package label. |
| **Status** | **SUNSET.** Microsoft announced CodePush retirement aligned with App Center retirement on **2025-03-31**. Servers stopped accepting new uploads; read-only archive remains. Recommended replacement: **EAS Update** for Expo apps, **Capgo** for non-Expo. |
| Store constraints | Same Apple §2.5.2 / Google Play targeted-delivery rules as Capacitor Live Update. |
| Known issues since 2022 | Long-running complaint: CodePush's lack of cryptographic signing meant any compromise of App Center or a mirror is catastrophic. The 2025-03-31 sunset triggered a multi-month scramble; several orgs moved to EAS, several to Capgo, a minority to self-hosted forks (`code-push-server` Go-based or `react-native-code-push` fork). |

**Takeaway for unified layer.** **Do not target CodePush.** It is read-only archive. The schema it left behind is the historical *de facto* standard many teams still reference when designing an OTA layer — so the schema is worth diffing against, but the product is dead.

## 8. PWA Service Worker (Workbox + W3C + MDN)

| Field | Value |
|---|---|
| Manifest | **None in the classic sense.** The "manifest" is the **`sw.js` script itself** + the **`manifest.webmanifest`** (web app manifest for installability — different concern, unrelated to updates). The Service Worker spec is the closest thing to a manifest: it's just a JS file the browser fetches bytewise and compares by content (semver-less). Updates are detected by byte-level change in the registered `sw.js`. |
| Signing | **None at the manifest level.** Trust comes from the **secure context requirement** (HTTPS) + the browser's same-origin policy. Subresource Integrity (SRI) is available for scripts loaded by the SW, but not for the SW registration itself. |
| Provider | Any HTTPS origin hosting the SW. Service Workers are same-origin-only. |
| Channel | **None.** Workbox supports custom update messaging via `BroadcastChannel` but the SW lifecycle itself is single-version. |
| Delta | **N/A.** Browser-managed fetch cache (Cache Storage API). Strategies: `cache-first`, `network-first`, `stale-while-revalidate`, etc. Per-resource, not per-update. |
| Cache path | Browser-managed (origin-scoped Cache Storage + IndexedDB). No app-controlled path. |
| Rollback | **None native.** You can implement by checking an older version flag and calling `self.skipWaiting()` / `clients.claim()`, but the browser offers no rollback primitive. |
| Store constraints | **None for stores** (PWA is web). Browser security model is the only constraint. Safari is the slowest to ship SW features (Background Sync, Periodic Sync absent); iOS Safari has restrictions on SW lifetime and persistent storage. |
| Known issues since 2022 | `workbox-window` (Google's recommended wrapper) exposes the lifecycle as events: `installing`, `installed`, `waiting`, `activating`, `activated`, `controlling`. `messageSkipWaiting()` is the standard "force update" lever. **Common pitfall**: refreshing the page does not always activate a waiting SW (documented in MDN/Workbox). |

**Takeaway for unified layer.** PWA SW is the **outlier** — it's not a manifest-driven system, it's a byte-comparison-driven system with no signing. **Do not try to fit it into the same signed-manifest envelope.** What we *can* borrow: lifecycle event naming conventions and the `skipWaiting` semantic as the "force update" primitive.

## 9. Microsoft.AutoUpdater / AppInstaller (MSIX)

| Field | Value |
|---|---|
| Manifest | **`AppInstaller` file** (`.appinstaller`, XML), with `<Package>`, `<MainPackage>` / `<OptionalPackages>`, `<UpdateSettings>`, `<RepairItems>`, `<Dependencies>`. Bundled alongside the MSIX/APPX. |
| Signing | **MSIX package is Authenticode-signed.** The `.appinstaller` file may also be signed (recommended). `ForceUpdateFromAnyVersion` allows version regression but is gated by signature chain. |
| Provider | Any HTTPS endpoint serving the `.appinstaller`. Microsoft Store auto-update path bypasses the `.appinstaller` entirely (uses the Store). |
| Channel | Not in the file itself. Channel = deployment endpoint (Dev, Test, Production). Some enterprises use multiple `.appinstaller` files for ring deployments. |
| Delta | **Differential updates** are built into MSIX (block-level) and triggered by the AppInstaller declaration. `HoursBetweenUpdateChecks` and `AutomaticBackgroundTask` (every 8 hours) are the cadence knobs. |
| Cache path | `%LocalAppData%\Microsoft\WindowsApps\` (system-managed). |
| Rollback | **Partial** — `ForceUpdateFromAnyVersion="true"` allows the AppInstaller to downgrade, but the binary itself must be signed. Windows 10 introduced OS-level rollback within the last two feature updates; AppInstaller doesn't directly manage it. |
| Store constraints | **Microsoft Store path is exclusive:** if the app is in the Store, you cannot also publish via `.appinstaller` (Store is the channel). Direct distribution requires code signing (EV cert recommended to avoid SmartScreen friction). |
| Known issues since 2022 | `UpdateSettings` elements: `OnLaunch` (1709), `HoursBetweenUpdateChecks` (1803), `AutomaticBackgroundTask` (1803), `UpdateBlocksActivation` (1903), `ShowPrompt` (1903), `ForceUpdateFromAnyVersion` (1903). Windows Package Manager (`winget`) is a related-but-distinct path. **Known issue**: WinGet does not honor `.appinstaller` — it has its own MSIX submission flow. |

**Takeaway for unified layer.** The **cleanest enterprise update manifest** of the nine. The XML schema is rich but the *minimal* subset (`version`, `uri`, `signature`, `UpdateSettings/@HoursBetweenUpdateChecks`) is small and portable. Worth studying as the canonical "Microsoft-flavored" design.

## Common Subset — Initial Diff Result

The **intersection** of what these nine systems actually need from a manifest:

| Field | Present in |
|---|---|
| `version` (SemVer) | Tauri ✓, electron-updater ✓, MSIX ✓, Expo ✓, Capacitor ✓, CodePush (label), Sparkle (`sparkle:shortVersionString`), Squirrel (NuGet `version`), PWA (workbox-version) |
| `url` / download URL | All except PWA SW |
| `signature` (cryptographic) | **Tauri ✓, Sparkle ✓, electron-updater (binary-only) ✓, MSIX ✓**; Capacitor (optional); CodePush/Expo/PWA/Squirrel (none) |
| `pub_date` / `releaseDate` / `pubDate` | Tauri, electron-updater, Sparkle, MSIX, Expo (createdAt) |
| `notes` / `releaseNotes` | Tauri, electron-updater, Sparkle, MSIX (DisplayName), Expo (`message`) |
| `channel` (or surrogate) | Tauri (URL), electron-updater (config/filename), Sparkle (multiple feeds), **Capacitor ✓, Expo ✓**, CodePush (deploymentKey), MSIX (separate files) |
| `rollout` % | **Expo ✓** only; rest are all-or-nothing per version |
| `blockmap` / delta | electron-updater, MSIX (built-in), Sparkle (`*.delta`); not present elsewhere |
| `platforms` map | Tauri ✓, electron-updater (separate files), MSIX (separate files) |

**Conclusion for R2 signed-manifest design.** The minimum universal subset is:

```jsonc
{
  "version": "<semver>",            // all
  "pub_date": "<rfc3339>",          // all except CodePush/PWA
  "url": "<signed URL to payload>", // all
  "signature": "<ed25519 over (url + size + sha256) >", // 4-5 of 9
  "platforms": { ... },             // Tauri, electron-updater, MSIX
  "channel": "<stable|beta|...>",   // 6 of 9 (with surrogate)
  "rollout": { "percentage": 0..100, "hashBuckets": "..." } // Expo-only today
}
```

Three differentiators the unified layer should *explicitly support*:
1. **ed25519 manifest signature** (Tauri model) — covers Tauri/Sparkle/electron-updater/MSIX; the rest can be coaxed into adopting it.
2. **Channel + rollout %** (Expo model) — covers what AIRIZ needs for staged rollouts; not natively present elsewhere.
3. **Platform constraint flag** (Tauri model: `desktop` / `mobile-asset-only`) — covers the iOS §2.5.2 boundary; the single most important policy gate.

Three things the unified layer should *not* try to subsume:
1. **PWA Service Worker lifecycle** — orthogonal system; link via a separate "PWA refresh hint" event, not the same manifest.
2. **MSIX differential blocks** — let MSIX handle its own block-level diff; the manifest just carries the MSIX URL.
3. **Sparkle's signed-feed XML** — feed-level signing is independent of payload-level signing; both can co-exist.
