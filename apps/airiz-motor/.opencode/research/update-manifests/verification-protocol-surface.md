## 1. Tauri 2.x updater

- **Phase 1 claim (1-line).** Tauri 2.x `tauri-plugin-updater` is **desktop-only** (macOS, Windows, Linux), uses **ed25519** signing (mandatory, cannot be disabled, public key inlined in `tauri.conf.json` not a file path), and serves updates via a **signed JSON** manifest (`latest.json` or dynamic JSON endpoint).
- **Canonical source fetched.** <https://v2.tauri.app/plugin/updater/> (last updated Nov 28, 2025).
- **Verification result.** **VERIFIED.**
- **Evidence.**
  - Desktop-only: `cargo add tauri-plugin-updater --target 'cfg(any(target_os = "macos", windows, target_os = "linux"))'` (Source: §Setup, step 1). Plugin initialization in `lib.rs` is gated with `#[cfg(desktop)]` (§Setup, step 2). The "Supported Platforms" table lists windows/linux/macos/android/ios but every code sample uses desktop-only guards. iOS/Android updater is not provided by this plugin.
  - Ed25519 / mandatory signing: "Tauri's updater needs a signature to verify that the update is from a trusted source. **This cannot be disabled.**" (§Signing updates). The pubkey field doc says: "It **cannot** be a file path!" (§Tauri Configuration). Algorithm is referenced as "signature" with a `.sig` file generated by the CLI's `signer generate` command (implicit ed25519 — Tauri's CLI generates ed25519 keys; the doc page does not name the curve explicitly, but the public-key/cannot-be-disabled posture matches Phase 1).
  - JSON manifest format: Two formats documented (§Server Support). Static JSON: `{ version, notes, pub_date, platforms: { "<OS-ARCH>": { signature, url } } }`. Dynamic JSON: `{ version, notes, pub_date, url, signature }`. Matches Phase 1 verbatim.
- **Minor drift noted.** Phase 1 calls the algorithm "ed25519" — the canonical Tauri doc says "signature" / `pubkey` / `.sig` without naming the curve on this page. The Tauri CLI's `signer generate` is documented elsewhere to produce ed25519 keys, but a strict reader could flag the curve name as Phase 1's own gloss. Not a contradiction; just a thin spot in the cited URL.
- **Final verdict.** **CONSISTENT.**

## 2. Sparkle 2.x

- **Phase 1 claim (1-line).** Sparkle 2.x uses an **appcast.xml** (RSS 2.0 + sparkle namespace) manifest, with **EdDSA (ed25519)** signing on the enclosure archive and (since 2.9) optional signed feeds.
- **Canonical source fetched.** <https://sparkle-project.org/documentation/publishing/>.
- **Verification result.** **VERIFIED.**
- **Evidence.**
  - appcast.xml format: Sample XML in §"Update your appcast" uses `<rss version="2.0" xmlns:sparkle="http://www.andymatuschak.org/xml-namespaces/sparkle">` with `<channel>` wrapping `<item>` elements. Standard fields include `<title>`, `<link>`, `<sparkle:version>`, `<sparkle:shortVersionString>`, `<sparkle:releaseNotesLink>`, `<pubDate>`, `<enclosure url length type sparkle:edSignature="…">`. Matches Phase 1.
  - EdDSA signing: §"Secure your update" — "Sparkle includes a tool to help you make a EdDSA signature of the archive." Sample output is `sparkle:edSignature="…"` base64 over `enclosure` URL+length. Optional signed release notes via `sign_update` (for `SURequireSignedFeed`). Matches Phase 1.
  - 2.9 features: Phase 1 claims signed feeds since 2.9 and Apple Archive since 2.7. Page confirms: §"Archive your app" — "Sparkle 2.7 / macOS 10.15+ support this format" (Apple Archive / .aar); §"Secure your update" — `SURequireSignedFeed` requires `sign_update` of release notes (consistent with 2.9).
- **Final verdict.** **CONSISTENT.**

## 3. Capacitor Live Update (Capgo)

- **Phase 1 claim (1-line).** Capgo / Capacitor Live Update uses a **JSON manifest** (`{id, version, channel, bundle: {url, checksum (sha256), signature?}, rollout?, minNativeVersion, mandatory?}`) with **SHA-256 checksum + optional RSA/ECDSA signature**, and is constrained by **Apple App Review Guideline §2.5.2** on iOS (no behavior-changing OTA updates).
- **Canonical source fetched.** <https://capgo.app/>.
- **Verification result.** **MINOR DRIFT.**
- **Evidence.**
  - Manifest + signing: The fetched Capgo **homepage is marketing material**; it does not publish the manifest schema. It does state "Signed and encrypted bundles" (§Safe defaults out of the box) and references the OSS `Cap-go/capacitor-updater` plugin. The exact schema `{id, version, channel, bundle: {url, checksum (sha256), signature?}, …}` in Phase 1 line 86 comes from the capacitor-updater plugin docs on GitHub, not from capgo.app/. So Phase 1's schema details are *plausible and consistent* with the Capacitor ecosystem, but not strictly verified by the URL cited.
  - iOS App Store constraint: The homepage *does* explicitly support the spirit of §2.5.2 — §"Keep store review for native changes": "Update JavaScript, CSS, copy, runtime flags, and assets while native code and Capacitor config keep going through normal App Store and Play review." There is also a link to the "App Store compliant OTA updates guide" (capgo.app/blog/ultimate-guide-to-app-store-compliant-ota-updates/). However, **the homepage does not cite §2.5.2 verbatim**; the verbatim §2.5.2 quote in Phase 1 ("Apps should be self-contained in their bundles…") is from Apple's guidelines page, not from Capgo.
- **Final verdict.** **MINOR DRIFT.** Substantive claims (signed/encrypted bundles; native stays in store review; JS/assets can ship via OTA) are confirmed by the Capgo homepage. The specific schema fields and the §2.5.2 verbatim quote are sourced from elsewhere (capacitor-updater plugin docs, Apple developer guidelines) — not from capgo.app/ itself. Not a contradiction, but Phase 1's provenance note (line 5) lists developer.apple.com as the §2.5.2 source, which is correct.

## 4. PWA service worker `skipWaiting`

- **Phase 1 claim (1-line).** `self.skipWaiting()` is the standard "force update" lever in a PWA service worker lifecycle (paired with `clients.claim()`); refreshing the page does not always activate a waiting SW.
- **Canonical source fetched.** <https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting>.
- **Verification result.** **VERIFIED.**
- **Evidence.**
  - Definition: "The `skipWaiting()` method of the `ServiceWorkerGlobalScope` interface **forces the waiting service worker to become the active service worker**." Direct match for "force update lever".
  - Pairing with `Clients.claim()`: "Use this method with `Clients.claim()` to ensure that updates to the underlying service worker take effect immediately for both the current client and all other active clients." Confirms Phase 1's pairing claim.
  - When it takes effect: "While `self.skipWaiting()` can be called at any point during the service worker's execution, it will only have an effect if there's a newly installed service worker that might otherwise remain in the `waiting` state." Consistent with the "refreshing does not always activate" pitfall Phase 1 mentions (line 150).
  - Baseline / availability: "Widely available… available across browsers since April 2018." Secure context only (HTTPS).
- **Final verdict.** **CONSISTENT.**

## 5. Microsoft.AutoUpdater / AppInstaller (MSIX)

- **Phase 1 claim (1-line).** The `AppInstaller` (`.appinstaller`) XML manifest carries an `UpdateSettings` element with six child elements: `OnLaunch` (1709), `HoursBetweenUpdateChecks` (1803), `AutomaticBackgroundTask` (1803), `UpdateBlocksActivation` (1903), `ShowPrompt` (1903), `ForceUpdateFromAnyVersion` (1903).
- **Canonical source fetched.** <https://learn.microsoft.com/en-us/windows/msix/app-installer/update-settings> (last updated 2025-06-10).
  - *Note.* The user-requested URL `…/app-installer/app-installer-file` returns 404. The correct canonical page is `…/app-installer/update-settings`, which is the URL Phase 1's provenance note (line 5) actually cites. Verified against the correct URL.
- **Verification result.** **VERIFIED.**
- **Evidence.**
  - The page's "App Installer file update setting" table reproduces all six elements verbatim, with the exact Windows 10 version floors Phase 1 lists:

    | Element | Min Windows 10 |
    |---|---|
    | OnLaunch | 1709 |
    | HoursBetweenUpdateChecks | 1803 |
    | AutomaticBackgroundTask | 1803 |
    | UpdateBlocksActivation | 1903 |
    | ShowPrompt | 1903 |
    | ForceUpdateFromAnyVersion | 1903 |

  - Behavioral semantics also match Phase 1 (lines 162–168): `OnLaunch` checks on launch; `AutomaticBackgroundTask` runs every 8 hours in the background; `ForceUpdateFromAnyVersion` allows downgrade; `UpdateBlocksActivation` requires `ShowPrompt=true`.
- **Final verdict.** **CONSISTENT.**

## 6. CodePush / App Center sunset

- **Phase 1 claim (1-line).** Microsoft announced CodePush retirement aligned with App Center retirement on **2025-03-31**; servers stopped accepting new uploads; read-only archive remains.
- **Canonical source fetched.** <https://learn.microsoft.com/en-us/appcenter/retirement> (last updated 2026-04-15).
- **Verification result.** **VERIFIED.**
- **Evidence.**
  - "Visual Studio App Center is scheduled for retirement on **March 31, 2025**. After that date, it will not be possible to sign in with your user account nor make API calls." Direct match.
  - CodePush is explicitly listed in the "Alternative solutions" table: "**CodePush** — We have prepared a special version of **CodePush** that can be integrated into your app and run independently from App Center. You can access the source code and the documentation… in this [GitHub repository](https://github.com/microsoft/code-push-server)." Confirms CodePush was retired alongside App Center.
  - 2026 update note: "**Analytics & Diagnostics**" was *separately* extended to **March 2027** for migration to Azure Monitor; the **March 31, 2025** retirement still applies to everything else (Build, Test, Distribution, CodePush).
- **Final verdict.** **CONSISTENT.**
