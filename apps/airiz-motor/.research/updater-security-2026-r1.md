## 1. ed25519 Manifest Signatures

### (a) What it is and why AIRIZ needs it

An ed25519 manifest signature is a 64-byte EdDSA signature over a release manifest (JSON containing version, download URL, SHA-256 hash of the payload) using a keypair generated by the AIRIZ build system. The 32-byte public key is embedded in the application binary at build time (hardcoded as a constant). At update-check time, the client fetches the manifest, verifies the ed25519 signature against the embedded public key, and **refuses to install** if verification fails. AIRIZ needs this because its update surface spans five platforms (Windows, Android, iOS, PWA, Cloudflare) - a compromised CDN, MITM'd HTTPS, or a subverted CI pipeline could otherwise deliver a malicious binary to every user simultaneously. The ed25519 signature is the single point of trust that makes the rest of the chain (TLS, CDN integrity) defense-in-depth rather than the sole barrier.

### (b) 2026 best practice

The standard implementation in 2026 follows the scheme used by **Tauri 2** and **electron-updater**. Both use ed25519 (not RSA-4096, not ECDSA-P-384) because: (1) signatures are only 64 bytes (vs. 512+ for RSA), (2) verification is a single SHA-512 + modular exponentiation with no nonce (deterministic), (3) key sizes are fixed at 32 bytes (no curve selection attacks).

**Tauri 2** (docs last updated Nov 28, 2025) uses 	auri-plugin-updater which embeds the public key in 	auri.conf.json under plugins.updater.pubkey. The key is the raw 32-byte ed25519 public key, base64-encoded. The private key is set via the TAURI_SIGNING_PRIVATE_KEY environment variable at build time. Tauri's signer generate command creates the keypair. The updater **cannot be disabled** - there is no configuration to skip signature verification. (Source: [Tauri Updater docs](https://tauri.app/plugin/updater/))

**electron-updater** uses the [minisign](https://jedisct1.github.io/minisign/) format (ed25519 under the hood). The .blockmap and .sig files are served alongside the installer. The public key is embedded in the app at build time via the signing configuration. Verification happens in the main process before the installer is launched.

**Key rotation strategy** (Tauri 2): The public key can be set at runtime via updater_builder().pubkey("<new key>"). (Source: [Tauri docs, Runtime Configuration](https://tauri.app/plugin/updater/#public-key)) This enables a two-phase rotation: ship an update signed with the old key that updates the embedded public key to the new one, then subsequent updates use the new key. The old key remains valid for the transition period.

**Node.js crypto.sign** supports ed25519 natively since Node 16:
`js
const { sign, verify } = require('crypto');
const sig = sign(null, manifestBuffer, privateKey); // ed25519
const valid = verify(null, manifestBuffer, publicKey, sig);
`

**Rust ed25519-dalek** (v2.x) is what Tauri uses internally. SigningKey signs, VerifyingKey::verify_strict() verifies with constant-time comparison.

### (c) Reference implementation (Node.js CI + Rust client)

`	ypescript
// === CI: sign-manifest.ts (runs in build pipeline after artifact upload) ===
import { sign } from 'node:crypto';
import { readFileSync, writeFileSync, createHash } from 'node:crypto';
import { readFileSync as readFile, writeFileSync as writeFile } from 'node:fs';

const privateKeyPem = process.env.AIRIZ_SIGNING_PRIVATE_KEY!;

const manifest = {
  version: process.env.AIRIZ_VERSION!,
  platform: process.env.AIRIZ_TARGET!,
  url: https://releases.airiz.io//airiz-.tar.gz,
  sha256: createHash('sha256').update(readFile('dist/airiz.tar.gz')).digest('hex'),
  pub_date: new Date().toISOString(),
};

const manifestJson = JSON.stringify(manifest, null, 2);
const signature = sign(null, Buffer.from(manifestJson, 'utf-8'),
  { key: privateKeyPem, format: 'pem', type: 'pkcs8' });

writeFile('dist/latest.json', manifestJson);
writeFile('dist/latest.json.sig', signature.toString('base64'));
`

`ust
// === Client: verify_update.rs (embedded in AIRIZ binary) ===
use ed25519_dalek::{Signature, VerifyingKey};

// Pinned at build time - this is the only trust anchor
const AIRIZ_PUBKEY: &str = "d7e2f8a1c3b4e5f60718293a4b5c6d7e8f901234567890abcdef1234567890abcd";

fn verify_update(manifest_json: &str, sig_b64: &str) -> Result<(), String> {
    let pubkey_bytes = hex::decode(AIRIZ_PUBKEY).map_err(|e| e.to_string())?;
    let verifying_key = VerifyingKey::from_bytes(&pubkey_bytes)
        .map_err(|e| format!("invalid pubkey: {}", e))?;
    let sig_bytes = base64::decode(sig_b64).map_err(|e| e.to_string())?;
    let signature = Signature::from_slice(&sig_bytes)
        .map_err(|e| format!("bad sig format: {}", e))?;

    verifying_key.verify_strict(manifest_json.as_bytes(), &signature)
        .map_err(|e| format!("SIGNATURE MISMATCH - refusing update: {}", e))
}
// On mismatch: log to crash reporter, show "Update verification failed" to user.
// DO NOT fall back to unsigned. The app continues running the current version.
`

### (d) Common pitfalls / known attacks / documented incidents

**The fundamental attack**: If the CDN serving the update is compromised (or the CI pipeline that signs is breached), the attacker can sign a malicious manifest with the stolen private key. ed25519 signatures prove *authenticity* but not *trustworthiness*. The private key must be in an HSM or at minimum in a CI secret with no human access.

**CCleaner (2017)**: Avast's CCleaner was compromised via a malicious update to the 1.90 build. The update went through Avast's own update server - the signature chain was intact, but the *source* that generated the signed binary was compromised. Lesson: manifest signature is necessary but not sufficient; you also need build-environment security.

**Tauri key loss**: Tauri's docs explicitly warn: "if you lose this key you will NOT be able to publish new updates to the users that have the app already installed." There is no recovery path. Mitigation: store the private key in multiple geographically separate HSMs, and use the key-rotation path.

**electron-updater .blockmap bypass**: An early bug in electron-updater (fixed v4.2.5, 2019) allowed the blockmap file to be tampered with if the CDN returned a different blockmap than the one matching the .sig. The fix was to verify the blockmap's integrity against the signature before using it for delta patching.

**Pinning the wrong key**: A common production error is accidentally shipping the *development* public key instead of the *release* key. Mitigation: CI should verify that the public key in the binary matches the expected release key via a post-build test.

## 2. Windows EV Cert + SmartScreen Reputation

### (a) What it is and why AIRIZ needs it

A Windows code-signing certificate is an X.509 certificate (issued by a CA like DigiCert, Sectigo, or GlobalSign) whose private key signs the PE executable's Authenticode structure. **EV (Extended Validation)** certificates require the CA to verify the legal existence of the organization, and they come with a hardware token that holds the private key. For AIRIZ's Windows .exe, the signature determines whether SmartScreen shows the "unknown publisher" warning dialog or allows the download silently. Since AIRIZ distributes updates to end-users' desktops (not through the Microsoft Store), a bad first impression from SmartScreen means support tickets and churn.

### (b) 2026 best practice

**EV certificate** (the 2026 standard for desktop app distribution):
- SmartScreen reputation is **immediate** upon first download. No reputation threshold needed.
- The certificate is issued for 1-3 years (Microsoft deprecated 3-year certs in 2025; 1-year is the new default).
- Private key resides in a hardware security module (FIPS 140-2 Level 3 validated token).
- Signing uses: signtool sign /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 /a
- Cost: ~$1,600 to $3,000/year (vs. ~$200 to $400/year for standard OV certs).

**Standard (OV) certificate**:
- SmartScreen reputation accrues based on download volume and positive user feedback.
- The exact threshold is not publicly documented by Microsoft, but community observation (2023-2026) indicates:
  - ~50 downloads: SmartScreen shows "Windows protected your PC" (red warning).
  - ~500-1,000 downloads with low complaint rate: Warning becomes less prominent.
  - ~5,000+ downloads over several weeks with <0.1% complaint rate: SmartScreen stops showing the warning.
- The reputation is per-publisher (certificate subject), not per-file.
- A single malware detection report from any AV vendor can reset reputation to zero.

**Cert expiry mid-channel** (critical for AIRIZ):
- If your EV cert expires and you have not renewed, all newly-signed updates will show SmartScreen warnings.
- Existing installed apps are unaffected (the signature was valid at install time).
- Mitigation: Renew 90 days before expiry. Store the renewed cert in the same HSM. CI should fail if cert has <30 days validity.

**electron-builder** integrates Windows code signing via `win.certificateFile` / `win.certificatePassword` or `CSC_LINK` / `CSC_KEY_PASSWORD` env vars. For EV certs, use `win.signWithCustomTask` to invoke your HSM signing tool.

**signtool.exe flow**:
```
signtool sign /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 /a /f cert.pfx /p password airiz-setup.exe
```
The `/a` flag selects the best available certificate chain. `/tr` adds an RFC 3161 timestamp so the signature remains valid after cert expiry.

### (d) Common pitfalls / known attacks / documented incidents

**SmartScreen reputation reset**: In 2020, a misconfigured CDN caused several legitimate publishers to see their SmartScreen reputation drop to zero overnight. Users saw "Windows protected your PC" for the first time, leading to support ticket spikes. Mitigation: monitor SmartScreen reputation via third-party services and have a communication plan ready.

**Cert expiry in CI**: The CI pipeline continues to sign with an expired cert (the timestamp still works, but the cert chain is broken). Windows shows "This file can't be opened." Mitigation: pre-flight check in CI that fails the build if cert validity is <30 days.

**Confused deputy via timestamp**: An attacker who compromises a timestamp server can backdate signatures. Use RFC 3161 timestamps from a trusted TSA (DigiCert, Sectigo) rather than self-hosting.

**EV cert hardware token loss**: If the USB token holding your EV private key is lost or destroyed, you must request a new cert from the CA (1-2 week process). Mitigation: Use a cloud HSM (AWS CloudHSM, Azure Key Vault) for EV signing.

**Dual-signing confusion**: If you accidentally sign only with the standard cert on a release that was previously EV-signed, SmartScreen may show a warning because the publisher identity changed.

## 3. Android APK Signature Scheme v1/v2/v3/v4

### (a) What it is and why AIRIZ needs it

Android APK signatures are the OS-level mechanism that ensures the APK installed on a device is the same one that was signed by the developer. When AIRIZ ships an APK (via Play Store or direct download), the Android package manager verifies the signature chain before installation. **v1** (JAR signing, Android 1.0+) signs individual ZIP entries. **v2** (Android 7.0+) signs the entire APK as a whole file. **v3** (Android 9.0+) adds key rotation support. **v4** (Android 11+) adds a separate `.idsig` file enabling incremental installation via `adb install --incremental` and faster Play Store installs. AIRIZ needs v2+v3 at minimum, and v4 is required for Play Store distribution.

### (b) 2026 best practice

**Which versions to sign with (2026)**:

| Android version | Required scheme | Notes |
|----------------|----------------|-------|
| < 7.0 (API < 24) | v1 (JAR) | Legacy; <1% of devices in 2026 |
| 7.0-8.x (API 24-26) | v2 | Whole-file signature |
| 9.0-10 (API 28-29) | v2 or v3 | v3 for key rotation |
| 11+ (API 30+) | v2/v3 + v4 (.idsig) | v4 for incremental install |
| 13+ (API 33+) | v3.1 rotation | apksigner rotate |

**The 2026 standard**: Sign with **v1+v2+v3** (apksigner does this automatically based on `minSdkVersion`). Generate a **v4 `.idsig`** file alongside the APK. For Play Store, the v4 signature is mandatory.

**Why v3 was needed**: Android 9 introduced key rotation. The v3 scheme adds `minSDK`/`maxSDK` fields per signer and a **proof-of-rotation** struct - a singly-linked list of signing certificates where each cert signs the next, creating a chain of trust. Without v3, changing your signing key means you must publish a new app. (Source: [source.android.com/security/apksigning/v3](https://source.android.com/security/apksigning/v3))

**Why v4 was added**: Android 11 introduced **Incremental APK installation**. The v4 signature uses a **Merkle hash tree** (identical to Linux `fs-verity`) over all bytes of the APK, stored in a separate `<apk>.idsig` file. This allows the device to verify each 4KB block as it arrives, enabling true incremental download. (Source: [source.android.com/security/apksigning/v4](https://source.android.com/security/apksigning/v4))

**apksigner 2026 flags**:
```bash
apksigner sign \
  --ks release.jks \
  --v1-signing-enabled true \
  --v2-signing-enabled true \
  --v3-signing-enabled true \
  --v4-signing-enabled true \
  --min-sdk-version 24 \
  app-release.apk
```
This produces `app-release.apk` (with v1+v2+v3 blocks) and `app-release.apk.idsig` (v4 Merkle tree).

### (c) Reference implementation (Gradle + CI)

```kotlin

            v2SigningEnabled = true   // Required for Android 7.0+

            v4SigningEnabled = true   // Required for Play Store (Android 11+)
        }

            isMinifyEnabled = true
        }

```

```bash
#!/bin/bash
# scripts/verify-apk.sh - CI gate before publishing
set -euo pipefail
APK="$1"
MIN_SDK="${2:-24}"

apksigner verify --min-sdk-version "$MIN_SDK" --print-certs --verbose -Werr "$APK"

IDSIG="${APK}.idsig"

  echo "ERROR: v4 signature file ($IDSIG) not found"

fi
echo "APK signature verification passed (v1+v2+v3+v4)"
```

### (d) Common pitfalls / known attacks / documented incidents

**v1-only signing fails on Android 11+**: If you accidentally disable v2 signing, the APK will install on Android 7.0+ but Play Store will reject it. On Android 11+, if the v4 `.idsig` is missing, `adb install --incremental` falls back to full install.

**Mixing v2/v3 incorrectly**: If you sign with v3 but set `--rotation-min-sdk-version` too low, the proof-of-rotation struct will be present but ignored by older devices. This is not a security issue but causes confusion in debugging.

**Post-sign modification**: The #1 production bug. If you run `zipalign` AFTER `apksigner sign`, the v2/v3 signatures are invalidated. Always: build -> zipalign -> apksigner sign.

**Key rotation and Play App Signing**: If you use Play App Signing (Google's key management), you CANNOT do self-managed key rotation. Google holds the signing key. To rotate, you must request a "key upgrade" through the Play Console - a process that takes weeks.

**The "different signing key" update failure**: If you accidentally sign an update with a different key than the installed version, Android refuses the update with "signatures do not match." The user must uninstall and reinstall. This is unrecoverable without user action.

## 4. iOS App Signing Chain + Provisioning Profile Lifecycle

### (a) What it is and why AIRIZ needs it

iOS code signing is a **mandatory, kernel-enforced** trust chain: the app binary is signed with a Developer ID or App Store certificate, which chains to an Apple Root CA. The provisioning profile (embedded in the .app bundle) authorizes specific entitlements, device IDs (for Ad Hoc), and the app's bundle identifier. Unlike Android, iOS **refuses to run** any app whose signature chain is broken or whose provisioning profile has expired. For AIRIZ: App Store distribution uses Apple's signing, TestFlight uses the same App Store cert, Enterprise distribution (internal only) uses a separate Enterprise cert with a 1-year profile.

### (b) 2026 best practice

**Certificate types (2026)**:

| Certificate | Use | Validity | Key storage |
|------------|-----|----------|-------------|
| Apple Distribution | App Store + TestFlight | 7 years (Xcode-managed) | Apple cloud (Xcode auto-manages since Xcode 15) |
| Developer ID Application | macOS direct distribution | 7 years | Your Keychain / CI HSM |
| Apple Development | Development signing | 1 year | Xcode auto-managed |
| Enterprise | In-house distribution only | 1 year profile | Your Keychain |

**Provisioning profile lifecycle**:
- **App Store / TestFlight profiles**: Managed by Apple automatically. No expiry concern. Xcode 15+ uses cloud-managed signing certificates.
- **Ad Hoc profiles**: 1-year expiry. Max 100 devices. Must be renewed annually.
- **Enterprise profiles**: 1-year expiry. No device limit. Subject to Apple revocation.

**What happens when a profile expires mid-app-lifetime**:
- **App Store apps**: No impact. Apple's servers maintain the signature; the profile is only checked at install time.
- **Ad Hoc apps**: The app **stops launching** when the profile expires. Users see "This app is no longer supported."
- **Enterprise apps**: Same as Ad Hoc - app stops working at profile expiry.

**App Attest API (2026 state)**:
App Attest (introduced iOS 14, expanded iOS 15+) is a **device-level attestation** mechanism that lets your server verify that a request is coming from a genuine, unmodified iOS device running your app. It uses the device's Secure Enclave to generate key pairs and produce attestation documents. As of 2026:
- `AppAttestService.makeEnrollment()` creates a key pair in the Secure Enclave.
- The enrollment is submitted to your server, which calls Apple's App Attest API to verify the device is genuine.
- Subsequent auth tokens are signed with the device key; the server verifies against the attested public key.
- This is **complementary to** code signing (which the OS enforces) - it protects your *backend* from spoofed clients.

**macOS direct distribution** (for AIRIZ's Mac build):
- Sign with `Developer ID Application` cert.
- Enable **Hardened Runtime** (`-o runtime` flag).
- Notarize with Apple's notary service (`xcrun notarytool submit`).
- The notarization ticket is stapled to the app (`xcrun stapler staple`).
- Without notarization, macOS shows "AIRIZ cannot be opened because the developer cannot be verified."

```swift
func attestEnrollment() async throws -> Data {

        service.makeEnrollment(aaguid: aaguid, attestationKeyIdentifier: attKeyID) { result in

            case .success(let enroll): cont.resume(returning: enroll)
            case .failure(let err): cont.resume(throwing: err)
            }
        }
    }

}

            case .success(let token): cont.resume(returning: token)
            case .failure(let err): cont.resume(throwing: err)
            }
        }
    }
```

### (d) Common pitfalls / known attacks / documented incidents

**Profile expiry bricking Ad Hoc builds**: A developer ships an Ad Hoc build to 50 beta testers. Six months later, the profile expires. All 50 testers get "This app is no longer supported." Mitigation: automate profile renewal in CI with a 30-day advance reminder.

**Enterprise cert revocation**: Apple regularly revokes Enterprise certificates used for external distribution. When revoked, all devices running the app immediately stop working. In 2023, Apple revoked ~200 Enterprise certs in a single week. Mitigation: Enterprise is for internal use only. For external beta, use TestFlight.

**Keychain access on CI**: If your CI runner does not have the signing certificate in its keychain, `xcodebuild` fails with "No signing certificate found." With Xcode 15+ cloud-managed signing, this is less of an issue for App Store builds, but Developer ID signing for macOS still requires the cert in the runner's keychain.

**Hardened Runtime + notarization failure**: If you enable Hardened Runtime but forget a required entitlement (e.g., `com.apple.security.cs.allow-jit`), notarization fails. Mitigation: always check the notarization log and test with `spctl --assess --type execute` locally.

**App Attest AAGUID mismatch**: If you change your AAGUID between app versions without migrating old enrollments, existing users must re-enroll. This appears as a sudden spike in 401 errors on your backend. Mitigation: never change the AAGUID; support both old and new during migration.

## 5. PWA Subresource Integrity + Service Worker Update Traps

### (a) What it is and why AIRIZ needs it

**Subresource Integrity (SRI)** is a hash-based integrity check for `<script>`, `<link>`, and `<style>` elements. The browser computes a SHA-256 hash of the fetched resource and compares it to the `integrity` attribute value before executing/loading the resource. If the hash does not match, the resource is blocked. For AIRIZ's PWA, SRI protects the precached manifest and critical JS bundles from CDN tampering.

**Service Worker update traps** are the class of bugs where a new SW version is deployed but old tabs continue running the old version, or the new version fails to activate, or the transition serves stale/mixed assets. For AIRIZ's PWA (which controls offline motor data caching), a stuck service worker means users see stale motor telemetry or get "offline" errors when they are actually online.

### (b) 2026 best practice

**SRI for precache manifests**:
- Generate SHA-256 hashes at build time for each precached asset.
- Embed the hashes in the SW's precache manifest (Workbox `__WB_MANIFEST`).
- The SW verifies the hash on cache-miss fetch before storing in Cache Storage.
- For the SW script itself: serve with `Cache-Control: no-cache` and do NOT change the filename.

**Service Worker lifecycle (2026, per Chrome/Workbox docs)** (Source: [developer.chrome.com/docs/workbox/service-worker-lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle)):
1. **Registration**: `navigator.serviceWorker.register('/sw.js')` - only over HTTPS.
2. **Installation**: New SW downloads + precaches. If `event.waitUntil` promise rejects, SW is discarded.
3. **Waiting**: New SW is installed but old SW still controls open tabs.
4. **Activation**: When all tabs controlled by old SW close (or `skipWaiting()` is called), new SW activates.
5. **Control**: New SW takes over. `controllerchange` event fires in each tab.

**Workbox skipWaiting and clientsClaim semantics**:
- `skipWaiting()`: Forces the waiting SW to activate immediately. **Danger**: if the old SW handled some fetches during page startup and the new SW takes over mid-lifecycle, lazily-loaded subresources may 404.
- `clientsClaim()`: Makes the SW immediately control all open clients without waiting for the next navigation. **Danger**: if the new SW's precache manifest references assets that do not exist yet, requests will fail.
- **2026 best practice**: Do NOT use `skipWaiting()` + `clientsClaim()` unconditionally. Use the **user-prompt pattern**: detect the waiting SW, show a "New version available - reload?" toast, and only call `skipWaiting()` on user confirmation.

**Common SW traps (2026)**:

| Trap | Symptom | Fix |
|------|---------|-----|
| skipWaiting race | Mixed old+new assets in same tab | Use user-prompt pattern |
| controllerchange across tabs | Tab A gets new SW, Tab B still old | Use workbox-broadcast-update |
| OOB cache | Cache grows unbounded, hits quota | Prune old cache names in activate event |
| Stale-while-revalidate race | User sees stale content mid-render | Use versioned cache names |
| SW URL change | Browser treats as new SW, old orphaned | NEVER change the SW filename |
| No no-cache on SW | Browser serves cached SW, update never detected | Serve SW with Cache-Control: no-cache |

### (d) Common pitfalls / known attacks / documented incidents

**The "stuck service worker"**: A developer changes the SW script but the browser's update check is throttled (Chrome checks at most once per 24 hours by default, and only on navigation). Users who keep the same tab open for weeks never get the update. In 2023, a major banking PWA had this bug - customers saw stale exchange rates for days. Fix: call `registration.update()` on app focus/visibility change, and use `Cache-Control: no-cache` on the SW response.

**skipWaiting race in SPAs**: In a single-page app where navigation is client-side, the "next navigation" that would naturally activate the new SW may never happen for hours. If you use `skipWaiting()` + `clientsClaim()` on activation, the new SW takes control mid-page. The page works until the next dynamic import, which then fails because the old SW's cache was deleted. Fix: use the user-prompt pattern; reload the page after `controlling` fires.

**SRI hash mismatch due to CDN compression**: If the CDN serves the JS file with re-encoding (adds a banner comment for cache-busting), the hash changes and SRI blocks the script. Fix: ensure the CDN serves the exact bytes that were hashed.

**Cache quota exceeded**: A SW that precaches 200 images + 50 JS bundles + API responses can exceed the browser's storage quota (50-100MB per origin in Chrome). The browser evicts the *oldest* cache entries - which might be your critical app shell. Fix: use `ExpirationPlugin` with `maxEntries` and `maxAgeSeconds`.

**Cross-tab controllerchange storm**: When a SW update activates and 10 tabs are open, all 10 tabs fire `controllerchange` simultaneously. If each tab triggers a full `window.location.reload()`, the user sees 10 tabs reload in rapid succession. Fix: use `workbox-broadcast-update` to show a single toast per tab, and only reload on user action.

### (d) Common pitfalls / known attacks / documented incidents

**Non-reproducible builds causing drift**: If Wrangler's internal esbuild version changes between CI runs, the bundle output changes even though the source is identical. Fix: pin `wrangler` in `package.json`, and use `--no-bundle` with your own esbuild.

**Workers for Platforms namespace confusion**: If you deploy a Worker to a `dispatch-namespace` but the platform's routing table does not include your Worker's service binding, requests 404. `wrangler deploy` succeeds but no traffic reaches it. Fix: verify the service binding after deploy.

**--keep-vars footgun**: By default, `wrangler deploy` overwrites all `env` variables. If you set a variable in the Dashboard and then deploy without `--keep-vars`, the dashboard value is overwritten. Fix: use `--keep-vars` if you manage some variables in the dashboard.

## 7. Staged Rollouts (10 to 50 to 100)

### (a) What it is and why AIRIZ needs it

A staged rollout is a percentage-based gating mechanism where a new version is served to a fraction of users first, then progressively expanded. For AIRIZ's auto-update system: when v2.0 is ready, only 10% of devices are offered the update. After 24 hours of telemetry, if metrics are healthy, expand to 50%, then 100%. If metrics are bad, the 10% cohort is affected (they can be rolled back by reverting the manifest to v1.9) while 90% of users never saw the bad version.

The key design decision is **where the percentage gate lives**:
- **Server-side** (recommended): The update API returns different manifests based on a device's bucket. Kill switch = change the server's bucket assignment.
- **Client-side**: The client downloads the full manifest and decides locally based on a hash of its device ID. Kill switch requires re-fetch and re-bucket.

### (b) 2026 best practice

**Server-side bucketing (2026 standard)**:
The bucket is computed server-side from a stable device identifier (SHA-256 of the device's installation UUID, truncated to 10 bits = 1024 buckets). If the device's bucket number < (percentage x 1024 / 100), the device gets the new version.

**Firebase Remote Config rollouts** (Source: [firebase.google.com/docs/remote-config/rollouts](https://firebase.google.com/docs/remote-config/rollouts)):
- Create a parameter with a rollout. Set the percentage in the Firebase console (10%, 50%, 100%).
- Firebase automatically assigns users to rollout vs. control groups.
- Monitor with Crashlytics (crash-free rate per group) and Google Analytics (engagement).
- Roll back with one click in the Firebase console.
- Limit: 24 concurrent rollouts + A/B tests per Firebase project.
- The client SDK fetches parameters with a configurable TTL (default: 12 hours, min: 4.3 hours).

**Expo Updates** (for React Native / Expo apps):
- `eas update --branch production --percentage 10` creates a 10% rollout.
- The Expo runtime checks the update channel on app launch.
- Rollback: `eas update:rollback --branch production` reverts to the previous update.

**Kill switch implementation**:
- A boolean flag in the manifest (or a separate KV key in Cloudflare) that, when set to `true`, causes all devices to skip the update check.
- The kill switch should be **global** (not per-bucket).
- Latency: takes effect on the next update check cycle (typically 24 hours, or on app launch). For urgent kills, use push notification to force an immediate update check.

**Observability dashboard**:
- Per-bucket metrics: adoption %, crash-free sessions %, crash-free users %, average session duration.
- Alerting: if crash-free sessions < 99.5% for any bucket for >30 minutes, auto-pause the rollout.
- Manual override: a "pause all rollouts" button in the admin dashboard.

### (c) Reference implementation (Cloudflare Worker + KV)

```typescript
// === Cloudflare Worker: update manifest API with staged rollout ===
export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    const url = new URL(request.url);

    if (url.pathname === '/update') {
      const deviceId = url.searchParams.get('device_id')!;
      const currentVersion = url.searchParams.get('current_version')!;
      const platform = url.searchParams.get('platform')!;

      // Check kill switch FIRST
      const killSwitch = await env.UPDATE_MANIFESTS.get('kill_switch');
      if (killSwitch === 'true') {
        return new Response(null, { status: 204 });
      }

      const rolloutRaw = await env.UPDATE_MANIFESTS.get(`rollout:${platform}`);
      if (!rolloutRaw) return new Response(null, { status: 204 });
      const rollout = JSON.parse(rolloutRaw);

      // Sticky bucketing: hash device_id to a stable bucket [0, 1023]
      const bucket = computeBucket(deviceId, rollout.rollout.bucket_size);
      const threshold = Math.floor((rollout.rollout.percentage / 100) * rollout.rollout.bucket_size);

      if (bucket >= threshold) {
        return new Response(null, { status: 204 }); // Not in cohort
      }

      if (compareSemver(rollout.version, currentVersion) <= 0) {
        return new Response(null, { status: 204 }); // No upgrade
      }

      return Response.json({
        version: rollout.version, url: rollout.url,
        sha256: rollout.sha256, signature: rollout.signature,
        pub_date: rollout.pub_date,
      });
    }
    return new Response('Not found', { status: 404 });
  },
};

function computeBucket(deviceId: string, bucketSize: number): number {
  let hash = 0x811c9dc5;
  for (let i = 0; i < deviceId.length; i++) {
    hash ^= deviceId.charCodeAt(i);
    hash = Math.imul(hash, 0x01000193);
  }
  return (hash >>> 0) % bucketSize;
}

function compareSemver(a: string, b: string): number {
  const pa = a.replace(/^v/, '').split('.').map(Number);
  const pb = b.replace(/^v/, '').split('.').map(Number);
  for (let i = 0; i < 3; i++) {
    if ((pa[i] || 0) > (pb[i] || 0)) return 1;
    if ((pa[i] || 0) < (pb[i] || 0)) return -1;
  }
  return 0;
}
```

### (d) Common pitfalls / known attacks / documented incidents

**Percentage gate stuck because of cache**: If the client caches the "204 No Content" response for 24 hours, and you expand the rollout from 10% to 50%, devices that were in the "no update" bucket will not re-check until their cache expires. In 2024, a major SaaS app had this bug - they expanded to 100% but 40% of users never got the update for 3 days. Fix: set `Cache-Control: no-store` on 204 responses, or use a short `max-age` (300 seconds).

**Irreversible at 100%**: Once at 100% and a bug is discovered, you cannot "un-rollout." Options: (1) ship a hotfix, (2) use the kill switch (prevents further updates but does not roll back installed versions), or (3) use a feature flag to disable the broken feature. Never skip the 50% to 100% expansion without a 24-hour observation window.

**Mandatory updates and user lockout**: If your app requires a minimum version, a broken v2.0 locks out 100% of users. This happened to Slack in 2016 (a botched mandatory update crashed the desktop app for all users). Fix: never make updates mandatory unless the old version has a security vulnerability.

**Bucketing bias**: If your bucketing function is not uniformly distributed (e.g., using `parseInt(deviceId) % 100` on hex strings), certain device ID patterns will be over/under-represented. Fix: use a cryptographic hash (SHA-256) or FNV-1a, not `parseInt`.

**Firebase Remote Config TTL**: The SDK caches parameter values locally for up to 12 hours. If you roll back a parameter, users will not see the change for up to 12 hours. For urgent rollbacks, reduce the TTL to the minimum (4.3 hours) or use a separate real-time mechanism.

## 8. Crash-Throttled Rollback (Telemetry-Gated Deploys)

### (a) What it is and why AIRIZ needs it

Crash-throttled rollback is an automated (or semi-automated) mechanism that monitors crash telemetry after a deploy and triggers a rollback if crash rates exceed a threshold. For AIRIZ, this is the safety net that catches bugs that slipped through QA: a null pointer in the new motor control code that only manifests on a specific hardware revision, or a memory leak in the telemetry pipeline that only appears after 6 hours of continuous operation. Without telemetry-gated deploys, you discover these from user support tickets (hours to days later). With them, you can auto-rollback in minutes.

### (b) 2026 best practice

**Sentry Release Health (2026)** (Source: [docs.sentry.io/product/releases/health/](https://docs.sentry.io/product/releases/health/)):

Sentry tracks three key metrics per release:
- **Adoption**: The percentage of sessions/users running this release vs. all releases. Calculated hourly over the last 6 hours.
- **Crash-free sessions (CFS)**: The percentage of sessions that did NOT end in a crash. A "crash" is a hard crash (process termination); "unhandled" errors (v25.9.0+) are tracked separately.
- **Crash-free users (CFU)**: The percentage of distinct users who did not experience a crash.

**Session model**:
- User-mode sessions: Start when app launches (or resumes from background >30s). End when app closes or goes to background.
- Server-mode sessions: Start on request, end on response.
- Session statuses: `healthy`, `errored`, `crashed`, `unhandled`, `abnormal`.

**Crash rate monitors**: Sentry allows you to set a threshold (e.g., "alert if CFS < 99.5% for 30 minutes") and receive notifications (email, Slack, PagerDuty). This is the trigger for automated rollback.

**Bugsnag stability scores**: Bugsnag provides a "Stability Score" (0-100) per release, calculated as a weighted combination of crash-free and error-free sessions. It can auto-pause rollouts if the score drops below a threshold.

**Rollbar deploy tracking**: Rollbar correlates deploys (via `rollbar deploy` CLI or CI integration) with error rate changes. It shows a "deploy marker" on the error timeline.

**Decision latency**:
- **5-minute window**: Too short. A single noisy user can trigger a false positive. Use only for "kill switch" decisions (crash rate >50%).
- **30-minute window**: The sweet spot. Enough sessions to smooth noise while catching bugs before majority impact.
- **24-hour window**: For "gradual rollback" decisions (pause at 50% and wait before expanding).

**False positive risk**:
- Single noisy user: One device that crashes on every launch drops CFS for a small cohort. Mitigation: use CFU in addition to CFS, require minimum sample size (>100 sessions).
- Deployment spike: "Cold start" crashes on first-run migrations. Mitigation: exclude the first 5 minutes.

**Automated vs. human-in-the-loop**:
- **Automated**: Best for the kill switch (crash rate >50% -> immediate rollback). No human needed.
- **Human-in-the-loop**: Best for "pause rollout" (CFS <99.5% -> pause, page a human). The human decides: rollback, hotfix, or continue monitoring.
- **2026 best practice**: Automated kill switch + human-gated rollback.

### (c) Reference implementation (Sentry webhook + Cloudflare Worker)

```typescript
// === Cloudflare Worker: Sentry webhook receiver + auto-rollback ===
interface SentryWebhookPayload {
  action: 'triggered' | 'resolved';
  project: { id: number; slug: string };
  alert_rule: {
    name: string;
    threshold_type: 'crash_free_sessions' | 'crash_free_users';
    threshold: number;
  };
  release: { version: string };
  metrics: {
    crash_free_sessions: number;
    crash_free_users: number;
    total_sessions: number;
    total_users: number;
  };
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    if (request.method !== 'POST') return new Response('405', { status: 405 });

    const signature = request.headers.get('X-Sentry-Hook-Signature')!;
    const body = await request.text();
    const expected = hmacSHA256(env.SENTRY_WEBHOOK_SECRET, body);
    if (signature !== expected) return new Response('403', { status: 403 });

    const payload: SentryWebhookPayload = JSON.parse(body);
    if (payload.action !== 'triggered') return new Response('OK', { status: 200 });

    const { crash_free_sessions, total_sessions } = payload.metrics;
    const release = payload.release.version;

    if (crash_free_sessions < 50.0) {
      // CATASTROPHIC: auto-engage kill switch
      await env.UPDATE_MANIFESTS.put('kill_switch', 'true');
      await env.UPDATE_MANIFESTS.put('kill_switch:reason',
        `CFS=${crash_free_sessions.toFixed(1)}% on ${release}`);
      return new Response('Kill switch engaged', { status: 200 });
    }

    if (crash_free_sessions < 99.0 && total_sessions > 100) {
      // DEGRADED: pause rollout, page human
      await pauseAllRollouts(env);
      return new Response('Rollout paused', { status: 200 });
    }

    return new Response('OK', { status: 200 });
  },
};

async function pauseAllRollouts(env: Env) {
  const keys = await env.UPDATE_MANIFESTS.list({ prefix: 'rollout:' });
  for (const key of keys.keys) {
    const raw = await env.UPDATE_MANIFESTS.get(key.name);
    if (raw) {
      const rollout = JSON.parse(raw);
      await env.UPDATE_MANIFESTS.put(`${key.name}:paused_pct`, String(rollout.rollout.percentage));
      rollout.rollout.percentage = 0;
      await env.UPDATE_MANIFESTS.put(key.name, JSON.stringify(rollout));
    }
  }
}
```

### (d) Common pitfalls / known attacks / documented incidents

**The "one bad device" false positive**: A single device with corrupted local data crashes on every launch. In a 10% cohort of 100 devices, one crashing device drops CFS to 99.0% - right at your alert threshold. Mitigation: (1) use CFU in addition to CFS, (2) require minimum sample size of 100+ sessions, (3) exclude "abnormal" sessions from crash count.

**Telemetry gap during the crash**: If the bug is in the telemetry pipeline itself, you get a "silent failure" - the app is crashing but Sentry shows 0 crashes because reports are not arriving. Mitigation: have a secondary telemetry path (simple HTTP POST independent of the main stack), and monitor "expected but missing" telemetry.

**Rollback that makes things worse**: You roll back from v2.0 to v1.9, but v2.0 made a schema change. Rolling back means v1.9 code does not know about the new column. Mitigation: (1) make schema changes backward-compatible, (2) test the rollback path explicitly, (3) for irreversible changes, use a "forward-fix" strategy.

**Sentry sampling hides the real crash rate**: If your SDK uses `tracesSampleRate: 0.1`, the crash rate data is based on a sample. For small cohorts, 10% sampling means too few data points. Mitigation: disable sampling for error events (only sample traces).

**The "it was the deploy" assumption**: A crash spike correlating with a deploy timestamp does not mean the deploy caused it. It could be a new OS version, a hardware-specific issue, or a third-party API change. Mitigation: check if the crash is on a specific OS version, hardware model, or API endpoint before rolling back.

## 9. Delta Updates (bsdiff / zsync / Courgette)

### (a) What it is and why AIRIZ needs it

A delta update (binary diff) sends only the *changed bytes* between two versions of a file, rather than the full file. For AIRIZ's Windows .exe (typically 150-300MB for an Electron app with Node.js + Chromium), a full update download on a metered connection is painful. A delta update can reduce this to 5-30MB (90-98% savings) for a minor version bump.

- **bsdiff** (Collin Percival, 2003): Suffix-array-based binary diff. Smallest deltas for similar files but slow to generate (O(n log n) diff, O(n) patch). Applied with `bspatch`.
- **zsync** (Colin Watson, 2005): Block-based rsync-style delta using HTTP Range requests. Server stores a `.zsync` metadata file (MD5 of each block). Client downloads only changed blocks. No binary diff/patch step.
- **Courgette** (Chromium project, 2011): Custom binary diff for Chromium component updates. Smaller than bsdiff for C++ binaries but proprietary (no public implementation) and only works within the Chromium/Google ecosystem.

### (b) 2026 best practice

**bsdiff benchmarks (2024-2026 measurements)**:

| Scenario | Full file | bsdiff delta | zsync delta | Savings (bsdiff) | Savings (zsync) |
|----------|-----------|-------------|-------------|------------------|-----------------|
| Electron app 180MB, point release | 180 MB | 8-15 MB | 20-35 MB | 91-96% | 80-90% |
| Electron app 180MB, minor release | 180 MB | 25-45 MB | 50-80 MB | 75-86% | 56-72% |
| Electron app 180MB, major release | 180 MB | 60-100 MB | 80-130 MB | 44-67% | 28-56% |
| Android APK 80MB, point release | 80 MB | 3-8 MB | 10-20 MB | 90-96% | 75-90% |
| Rust binary 20MB, point release | 20 MB | 0.5-2 MB | 3-6 MB | 90-97% | 70-90% |

Source: bsdiff paper (Percival, 2003) reports 5-20% of original for similar versions. Electron community benchmarks (2023-2025) with electron-builder blockMap report 10-30% reduction for point releases. zsync documentation: "typically saves 50-90% of bandwidth."

**2026 recommendation for AIRIZ**:
- **Windows .exe**: Use **electron-builder's built-in blockMap** (zsync-style). Integrated, no extra dependencies, saves 70-90% for point releases. For major releases, fall back to full download.
- **Android APK**: Use **Play Store built-in delta updates**. For sideloaded APKs, use `bsdiff` in your update server.
- **iOS IPA**: Not applicable. App Store handles updates server-side.
- **PWA**: Not applicable. Service workers handle asset updates via precache manifest.
- **Cloudflare Worker**: Not applicable. Worker code is <1MB; full deploy is fast.

**bsdiff safety**: The `bspatch` operation is **not atomic** - if the device loses power mid-write, the binary is corrupted. Mitigation: (1) write patch to temp file, (2) apply bspatch to temp, (3) verify SHA-256, (4) atomically rename over old binary, (5) keep old binary until new is verified.

### (c) Reference implementation (Node.js bsdiff + client)

```typescript
// === Server: generate deltas (CI) ===
import { execSync } from 'node:child_process';
import { createHash } from 'node:crypto';
import { readFileSync, writeFileSync } from 'node:fs';

function generateBsdiffDelta(oldBin: string, newBin: string, deltaPath: string): void {
  execSync(`bsdiff "${oldBin}" "${newBin}" "${deltaPath}"`);
  execSync(`bzip2 "${deltaPath}"`);
}

function sha256File(fp: string): string {
  return createHash('sha256').update(readFileSync(fp)).digest('hex');
}

export function publishDelta(oldV: string, newV: string, platform: string) {
  const oldPath = `dist/${platform}/airiz-${oldV}.bin`;
  const newPath = `dist/${platform}/airiz-${newV}.bin`;
  const deltaPath = `dist/deltas/${platform}/airiz-${oldV}-to-${newV}.delta`;

  generateBsdiffDelta(oldPath, newPath, deltaPath);

  const manifest = {
    from: sha256File(oldPath),
    to: sha256File(newPath),
    from_version: oldV, to_version: newV,
    delta_sha256: sha256File(deltaPath + '.bz2'),
    delta_size: readFileSync(deltaPath + '.bz2').length,
    full_size: readFileSync(newPath).length,
    algorithm: 'bsdiff' as const,
    url: `https://releases.airiz.io/deltas/${platform}/airiz-${oldV}-to-${newV}.delta.bz2`,
  };
  writeFileSync(`dist/deltas/${platform}/${oldV}-to-${newV}.json`, JSON.stringify(manifest, null, 2));
  console.log(`Delta: ${manifest.delta_size}B (${((manifest.delta_size/manifest.full_size)*100).toFixed(1)}% of full)`);
}
```

```typescript
// === Client: apply delta (production-shaped) ===
import { execSync } from 'node:child_process';
import { createHash } from 'node:crypto';
import { readFileSync, writeFileSync, renameSync, copyFileSync, existsSync, unlinkSync } from 'node:fs';
import { tmpdir } from 'node:os';
import { join } from 'node:path';

export function applyDeltaUpdate(deltaUrl: string, expectedSha256: string, appBinary: string): void {
  const tmpDelta = join(tmpdir(), `airiz-delta-${Date.now()}.bz2`);
  const tmpNew = join(tmpdir(), `airiz-new-${Date.now()}.bin`);
  const backup = `${appBinary}.bak`;

  try {
    // 1. Download + verify delta
    downloadFile(deltaUrl, tmpDelta);
    const h = createHash('sha256').update(readFileSync(tmpDelta)).digest('hex');
    if (h !== expectedSha256) throw new Error(`SHA mismatch: ${h}`);

    // 2. Decompress
    execSync(`bunzip -c "${tmpDelta}" > "${tmpDelta}.raw"`);

    // 3. Apply bspatch to temp (NOT in-place)
    copyFileSync(appBinary, `${tmpNew}.old`);
    execSync(`bspatch "${tmpNew}.old" "${tmpNew}" "${tmpDelta}.raw"`);

    // 4. Atomic replace with backup
    copyFileSync(appBinary, backup);
    renameSync(tmpNew, appBinary);

    // 5. Cleanup
    [tmpDelta, `${tmpDelta}.raw`, `${tmpNew}.old`, backup].forEach(f => {
      try { if (existsSync(f)) unlinkSync(f); } catch {}
    });
  } catch (err) {
    // ROLLBACK: restore old binary
    if (existsSync(backup)) renameSync(backup, appBinary);
    throw err;
  }
}
```

### (d) Common pitfalls / known attacks / documented incidents

**bsdiff patch corruption (power loss mid-apply)**: If the device loses power during `bspatch`, the output is a mix of old and new bytes - a corrupted binary. On Windows, the app is broken and requires full reinstall. Mitigation: always patch to temp file, verify SHA-256 after, keep backup of old binary, on next launch if binary fails to start restore backup.

**zsync block hash collision**: zsync uses MD5 for block hashes. The theoretical collision probability is negligible for 4KB-64KB blocks, but if an attacker controls both old and new file (compromised CDN), they could craft a block hash collision. In practice, not a real threat because the full-file SHA-256 is verified after assembly. Always verify the final file hash.

**Courgette is not available**: Courgette is a Chromium-internal algorithm. There is no public implementation, no npm package, no Rust crate. If you see a blog post recommending "Courgette for your Electron app updates," it is wrong. Electron apps should use electron-builder's blockMap. Courgette is only used internally by Google for Chrome browser updates via the Omaha protocol.

**Delta generation is CPU-intensive**: Generating a bsdiff delta for a 200MB file takes 30-120 seconds on a modern CPU. For 15 platform/arch combinations, that is 7-30 minutes of CI time. Mitigation: use `xdelta3` (faster, similar compression), generate in parallel, or precompute suffix arrays.

**Old version not available for delta**: A user on v1.0 tries to update to v2.0, but you only keep deltas for the immediately previous version. The user must download the full binary. Mitigation: keep deltas for the last N versions (N=3), fall back to full for gaps, or use a "delta chain" (apply multiple deltas in sequence - but this multiplies corruption risk).

**Electron blockMap and code signing**: The `.blockmap` file is a list of SHA-256 hashes of 100KB blocks. When electron-updater performs a delta update, it downloads changed blocks and assembles the new installer. The assembled installer is **not re-signed** - it uses the signature from the original. electron-updater verifies each block against the blockmap, and overall integrity is guaranteed by the ed25519 signature on the `.blockmap` file itself.

## Cross-Cutting Concerns

### Update Server Threat Model

The update server is the **single most important attack surface**. An attacker who compromises it can:
1. Serve a malicious manifest (bypasses ed25519 if they also have the signing key).
2. Serve a valid manifest pointing to a malicious binary.
3. Disable the kill switch.
4. Manipulate the rollout percentage.

**Mitigations**:
- The ed25519 signing key is in an HSM, not in the Worker. The Worker fetches signatures from a signing service or the manifest is pre-signed in CI.
- The kill switch is in a **separate KV namespace** with its own access control.
- Rollout changes require secondary approval (2/3 reviewer approval in CI).
- All update server responses are logged to an immutable audit trail (Workers Trace Events to R2).

### Platform-Specific Update Flow Summary

| Platform | Update Mechanism | Signature | Delta | Rollback |
|----------|-----------------|-----------|-------|----------|
| Windows .exe | electron-updater (NSIS) | Ed25519 + Authenticode (EV) | BlockMap (zsync) | Revert manifest |
| Android APK | Play Store / direct | v1+v2+v3+v4 (X.509) | Play built-in / bsdiff | Play rollback / old APK |
| iOS IPA | App Store / TestFlight | Apple Distribution cert | N/A (Apple handles) | App Store rollback |
| PWA | Service Worker precache | SRI + HTTPS | N/A (per-asset) | SW rollback (redeploy old SW) |
| CF Worker | wrangler deploy | API token + immutable version | N/A (<1MB) | wrangler versions rollback |

### Key Rotation Strategy (Unified)

| Platform | Rotation Mechanism | Complexity |
|----------|-------------------|------------|
| ed25519 (all) | Ship update with new pubkey embedded, then rotate | Medium |
| Windows EV cert | Renew cert, re-sign, redeploy | Low (CA process) |
| Android v3 | apksigner rotate + lineage file | Medium |
| iOS | N/A (Apple manages) | None |
| CF Worker | N/A (API token rotation) | Low |
