# OpenForge — Subsystem Design

## 1. Auth

Auth handles user identity, credential storage, and session lifecycle for the entire platform. Required functionality: (1) email/password signup with single-use verification links expiring in 24 hours, (2) login via password entry with constant-time comparison and progressive locking after 5 failures, (3) OAuth authorization-code flows for GitHub, Google, and GitLab with automatic account linking on verified-email match, (4) two-factor authentication supporting TOTP (RFC 6238, ±30 s drift) and WebAuthn/FIDO2 for phishing-resistant passwordless login, (5) session management with 30-day sliding expiration, a concurrent-session cap of 5, and instant server-side revocation propagated to all connected API gateways, (6) password reset via single-use tokens (15-min expiry, 3-attempt-per-email rate limit). Key edge cases: OAuth email collision (same address, different provider) triggers merge-or-reject before creation; WebAuthn credential loss requires re-enrollment without blocking primary login; TOTP backup codes are consumed atomically. Sessions use a random 256-bit token in Postgres referenced by a JWT httpOnly cookie, giving O(1) revocation without distributed cache invalidation.

**Lucia v4** (Postgres-native, TypeScript) for the full session/OTP/WebAuthn model, paired with **@simplewebauthn/server v13** for FIDO2 ceremony—Lucia's row-per-session design maps directly to the Postgres schema already in use, eliminating a separate Redis session store.

## 2. Repo Storage

Repo storage manages all Git objects and large files for every project. It must (1) store Git blobs, trees, and commits as content-addressed objects on S3 with a Postgres metadata index, (2) handle Git LFS objects (up to 5 GB per file) with deduplication via SHA-256, (3) produce and serve packfiles (thin/full) for clone and fetch, (4) implement incremental fetch by computing wanted/have negotiation (bitmap index) so clients download only new deltas, (5) enforce per-repo storage quotas with soft-warn at 80 % and hard-reject at 100 %, (6) provide garbage collection that removes unreachable objects after a 7-day grace period. Key edge cases: partial packfile writes on network failure must be atomic (write-to-temp, rename); LFS pointer files in the git tree must be validated before accepting a push; concurrent pushes to the same branch use optimistic locking on the ref (compare-and-swap in Postgres). The packfile generation pipeline runs off the hot path in a worker pool.

**git2 (libgit2)** via the **isomorphic-git** or **@octokit/git** layer for server-side packfile negotiation, with **S3 multipart upload** for LFS objects—libgit2's C core is the only library that correctly implements the bitmap-based incremental fetch protocol at production scale.

## 3. Webhooks

Webhooks deliver outbound HTTP notifications for platform events to user-registered endpoints. It must (1) accept endpoint registration with event-type filtering (push, issue, PR, CI), (2) deliver payloads as POST requests with a 10-second timeout per attempt, (3) sign each payload with HMAC-SHA256 using a per-endpoint secret, including a timestamp in the signature to prevent replay, (4) retry failed deliveries using exponential backoff (1 s, 5 s, 30 s, 2 min, 10 min, 1 h, 6 h) with jitter, (5) move payloads that exhaust all retries into a dead-letter queue with full delivery history for manual re-dispatch, (6) enforce per-endpoint rate limits (100 deliveries/min) to prevent a misconfigured loop. Key edge cases: clock skew between OpenForge and the receiving server means the replay window must tolerate ±5 min; secret rotation must allow a 5-minute overlap where both old and new secrets are accepted; endpoints behind a firewall that time out must be distinguished from 4xx/5xx responses for backoff strategy.

**BullMQ** (Redis-backed) for the delivery queue and retry scheduler, with **node:crypto** for HMAC signing—BullMQ's native exponential backoff, repeatable jobs, and dead-letter channel match the retry ladder exactly without custom timer logic.

## 4. CI Runners

CI runners execute build and test jobs in isolated environments. The system must (1) accept jobs into a priority queue (user-triggered > scheduled > batch) with per-org concurrency limits, (2) provision executor environments—Docker containers for standard workloads, Firecracker micro-VMs for untrusted code, or ephemeral K8s pods for GPU jobs—selected by job label, (3) stream job logs in real time via WebSocket to the web UI with a 10 MB in-memory ring buffer for late-joining viewers, (4) upload artifacts (tar.gz, ≤ 2 GB) to S3 at job completion with a signed-URL download endpoint, (5) enforce a hard timeout (default 60 min, configurable to 24 h) with SIGKILL escalation, (6) support job cancellation by the user or by a newer commit on the same branch. Key edge cases: a runner pod crash mid-upload must not lose partially written artifacts (S3 multipart + conditional commit); log streaming must survive executor restart via S3-backed log offset; Firecracker snapshot restore must be deterministic for reproducible builds.

**BullMQ** for the priority job queue (same Redis instance as webhooks, different queue name), **Firecracker** (via **firecracker-jailer** or the **Kata Containers** shim) for untrusted isolation, and **S3 multipart upload** for artifact durability—BullMQ's priority + concurrency-limit API covers scheduling without a custom dispatcher.

## 5. Billing / Stripe

Billing manages subscription plans, metered usage, and customer-facing invoicing. It must (1) support three plans—Free (1 GB storage, 300 CI min/mo), Pro ($20/mo, 50 GB, 3000 min), Team ($50/seat/mo, 200 GB, 10 000 min)—with self-serve upgrade/downgrade, (2) meter storage (GB-months, sampled hourly) and CI minutes (per-job duration, rounded up to seconds) in a Postgres metering table, (3) generate monthly Stripe Invoices with line items for base plan + overage charges at published per-unit rates, (4) prorate credits/charges on mid-cycle plan changes (daily proration, rounded to cents), (5) expose a Stripe Customer Portal for card updates, invoice downloads, and plan changes without support intervention, (6) handle dunning: 3 email attempts at day 1, 3, 7 of failed payment, then suspend CI at day 14 and soft-delete repos at day 30. Key edge cases: a user upgrading from Free to Team mid-cycle gets a credit for unused Free minutes (zero, since Free is included); a Team seat removal mid-cycle prates the seat charge; metering data must be idempotent (re-ingest safe via event ID).

**Stripe SDK v17+** (TypeScript, `stripe@17.x`) with **Stripe Billing** for subscriptions, metered billing for usage, and the embedded **Customer Portal**—Stripe's native proration engine and dunning sequences eliminate custom credit math; the SDK's idempotency-key support makes metering ingestion safe against retry storms.

## 6. Org Permissions

Org permissions governs access via a hierarchical RBAC model. It must (1) define three scopes—org, team, repo—with role inheritance flowing top-down (org owner → team admin → repo maintainer), (2) support four base roles (owner, admin, member, guest) at each scope with a fixed permission matrix, (3) allow per-repo role overrides that grant or deny specific permissions to a single user, bypassing team inheritance, (4) log every permission check and grant/revoke to an append-only audit table with actor, target, action, timestamp, and source IP, (5) propagate membership changes (user leaves a team) to all child repos within 5 s via an event-driven cascade, (6) enforce that an org always retains at least one owner and that the last owner cannot be demoted. Key edge cases: a user who is both a team member (admin) and a repo override (guest) resolves to the union of permissions unless the override is an explicit deny; audit log entries must survive org deletion for 90 days (legal hold); concurrent role changes use row-level locking in Postgres.

**OpenFGA** (v1.5, open-source) for the authorization model and check API—its tuple-backed relationship model natively expresses org→team→repo inheritance with per-node overrides, and its `Check` API returns in <10 ms with a Postgres backend, matching the existing database without adding a separate graph store.

## 7. Issue Tracker

The issue tracker manages issues, cross-references, and team workflows. It must (1) provide full CRUD on issues with title, body (Markdown), labels, assignees, and milestones, (2) support full-text search across title + body + comments using a dedicated search index, (3) render @mentions with real-time notification to mentioned users (email + in-app), (4) auto-link cross-references: `#123` links to an issue/PR, a 40-char SHA links to a commit, and `project#123` links to another project's issue, (5) organize issues into milestones with due dates and a progress bar (closed/total), (6) let users save named filters (query + sort + grouping) and share them as a URL. Key edge cases: deleting an issue renumbers nothing (IDs are stable) but orphaned cross-references render as "deleted issue"; a mention of `@everyone` is limited to admin+ to prevent notification spam; search index must be updated within 2 s of a write (near-real-time, not eventual). Issue bodies are rendered server-side to prevent client-side XSS from embedded HTML.

**Meilisearch** (v1.8, self-hosted) for full-text search with typo tolerance and instant filtering—its <50 ms p99 latency at 1 M documents and native `filters` field make it ideal for the label/milestone/status compound queries without a custom query DSL layer.

## 8. Wiki

The wiki provides per-project collaborative documentation. It must (1) render pages as GitHub Flavored Markdown (GFM spec: tables, task lists, strikethrough, autolinks, footnotes) with syntax-highlighted code blocks via a server-side highlighter, (2) maintain full version history per page (every save creates a new revision, no auto-squash), with a diff view between any two revisions, (3) support file attachments (PDF, images, up to 50 MB each) stored on S3 with MIME-type validation and virus scanning (ClamAV sidecar), (4) provide full-text search across all wiki pages in a project with per-page result snippets, (5) render pages in the project's configured theme (light/dark) with a responsive layout, (6) allow page reordering via drag-and-drop with an explicit page-order field. Key edge cases: a page deleted while a user has it open shows a soft "page removed" banner (not a hard 404) for 30 days; attachment MIME spoofing is prevented by magic-byte detection, not just the Content-Type header; the GFM renderer must escape raw HTML to prevent stored XSS.

**react-markdown** (v10) + **remark-gfm** (v4) for GFM rendering on the client, with **highlight.js** (v11) server-side for code block tokens—react-markdown's plugin architecture (remark/rehype) cleanly handles the GFM extension set without a full server render pass, and highlight.js supports 190 languages with a small per-language CSS bundle.

## 9. PR Review

PR review implements the code-review workflow from diff computation to merge. It must (1) compute a 3-way diff (base, head, merge-base) using Myers' O(ND) algorithm, producing unified diff hunks with context, (2) support inline comments anchored to a specific file + line range (or diff hunk), with threading and resolution, (3) implement review states (approved, changes-requested, comment) with a configurable minimum-approvals rule per repo, (4) enforce required status checks (CI, review, code-owner) as merge gates—merge button is disabled until all pass, (5) support draft PRs that are hidden from the PR list until the author marks them ready, (6) render suggested changes as an applyable diff patch with one-click accept/reject. Key edge cases: a force-push on the PR head invalidates all existing review approvals (they become "stale"); comments anchored to deleted lines persist but render with a "line removed" badge; the merge-base must be recomputed if the base branch receives new commits (rebase-aware). Code-owner rules are evaluated against a YAML `.codeowners` file.

**diff2** (the `diff2` npm package, Myers implementation) for 3-way diff computation, with a **state-machine pattern** (XState v5) for review lifecycle transitions—diff2 handles the O(ND) algorithm in pure JS with no native binding (safe on serverless), and XState's typed state machine prevents invalid transitions like "approve → changes-requested" without an explicit re-review action.

## 10. Actions / Workflows

Actions/Workflows executes user-defined CI/CD pipelines from YAML. It must (1) parse a constrained subset of the GitHub Actions workflow spec (`on`, `jobs`, `steps`, `runs-on`, `uses`, `env`, `if`, `strategy.matrix`, `timeout-minutes`) with a strict JSON-Schema validator that rejects unknown keys, (2) register and manage self-hosted and cloud runners (heartbeat every 30 s, evict after 90 s silence), (3) manage encrypted secrets (AES-256-GCM, per-org key) with scoped access (org-level vs repo-level) and injection into step environments, (4) expand matrix builds into parallel job instances with a configurable max-parallelism cap, (5) store artifacts (per-job, per-matrix-combo) on S3 with a retention policy (default 90 days), (6) provide a workflow run log viewer with per-step timing and a replay button for failed steps. Key edge cases: a workflow YAML with a circular `needs` dependency must be rejected at parse time with a clear error; a secret referenced in an `env` block must never appear in logs (redaction regex on secret values); matrix expansion of 4×4×2 = 32 jobs must respect the org's concurrent-job cap by queueing the excess.

**jsonschema** (v1.x) for YAML validation, **yaml** (eemeli/yaml v2) for parsing, and **BullMQ** for matrix-job fan-out—eemeli/yaml is the reference YAML 1.2 parser with full error recovery (line/column reporting), and BullMQ's per-queue concurrency limit directly enforces the org-level parallelism cap without a custom scheduler.
