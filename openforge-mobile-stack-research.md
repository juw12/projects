# OpenForge Mobile Stack — 6-Topic Deep Dive

**Date:** 2026-11-03
**Scope:** Architecture decision support for OpenForge mobile app (github.com/juw12/openforge)
**Total:** ~1200 words across 6 topics (200 words each)

---

## A. Push Transport

The 2024+ state of art splits into two distinct camps. Mainstream production apps use FCM on Android and APNs on iOS, with a backend (Firebase, OneSignal, or a custom server) handling token registration, device lifecycle, and delivery retries. FOSS and self-hosted teams use UnifiedPush distributors that replace FCM entirely, giving users full control over their notification delivery path and server. GitHub Mobile (github.com/mobile) ships FCM+APNs natively with no third-party SDK, keeping the notification path minimal. ntfy.sh (github.com/binwiederhier/ntfy, 35K stars, v2.36.0 released Oct 2026) runs on a single Go binary over WebSocket with zero external dependencies, and acts as a UnifiedPush distributor so other apps can deliver pushes without Google. NextPush (github.com/nextcloud/notify_push, v0.7.0 released Jul 2024) provides the equivalent for Nextcloud installations. For React Native, @react-native-firebase/messaging v27.1.0 (Oct 2026) is the dominant production library; expo-notifications covers Expo-based projects with a simpler API surface. The critical gotcha is Android Doze mode: even high-priority FCM data messages are suppressed when the device is idle (github.com/firebase/quickstart-android/issues/100), and Chinese OEMs (Xiaomi, Huawei, OPPO, Vivo) go further and kill the app process entirely, blocking all FCM delivery (github.com/pushy/pushy-demo-android/issues/5). On iOS, the 18.1 Apple Intelligence notification classifier introduced 10+ second delays on time-sensitive pushes, breaking MFA app workflows (developer.apple.com/forums/thread/764848).

## B. Auth Flow

Modern mobile auth converges on WebAuthn/passkeys for interactive login and RFC 8628 OAuth Device Flow for PAT-based or headless scenarios where no browser is available. Passkeys require iOS 15+/Android API 28+, a domain association file (AASA on iOS, assetlinks.json on Android), and the native `webcredentials` entitlement or `get_login_creds` relation declared in the manifest. GitHub Mobile uses WebAuthn for 2FA and session management. Expo added a device-flow sign-in PR (github.com/expo/expo/pull/48864) following RFC 8628 with QR pairing and an in-app browser fallback. Libraries: react-native-passkey (github.com/f-23/react-native-passkey) provides native FIDO2 `create`/`get` with silent authentication via `getImmediate()`; react-native-passkeys (github.com/peterferguson/react-native-passkeys) wraps the same API for Expo and adds AASA/assetlinks hosting instructions. For secret storage (SSH keys, personal access tokens), iOS Keychain and Android Keystore are the only cryptographically acceptable options. The 8-digit user code in device flow should use the RFC-recommended base-20 character set (BCDFGHJKLMNPQRSTVWXZ) to avoid accidental word formation (rfc-editor.org/info/rfc8628). Gotchas: (1) Android caches assetlinks.json for up to 24 hours, so certificate rotation silently breaks passkeys until reinstall (github.com/peterferguson/react-native-passkeys). (2) RFC 8628 §5.4 explicitly warns the device grant is phishable — an attacker can send a victim a pre-filled verification link, so the approval page must use POST with CSRF protection, never GET (dev.to/ahmet_gedik778845/building-an-rfc-8628-device-authorization-flow-for-smart-tv-video-apps-3cki).

## C. Offline Cache & Sync Engine

The 2024+ local-first consensus is SQLite on-device with a dedicated sync engine streaming from Postgres. PowerSync (powersync.com) streams PostgreSQL changes into client SQLite via WebSocket, supports declarative YAML sync rules scoped per-tenant, and ships a React Native SDK (@powersync/react-native) built on op-sqlite (github.com/OP-Engineering/op-sqlite) with SQLCipher encryption support. ElectricSQL (github.com/electric-sql/electric) hit 1.0 GA in March 2025 and is used in production by Google, Supabase, and Trigger.dev; its HTTP-based shape protocol is CDN-native and requires no persistent sockets, making it ideal for serverless and edge backends. WatermelonDB (github.com/Nozbe/WatermelonDB, 12K stars) pioneered reactive offline-first in React Native but has no first-party sync engine — you build your own push/pull logic. PowerSync publishes head-to-head benchmarks comparing op-sqlite, react-native-quick-sqlite, and expo-sqlite across 15 query patterns (powersync.com/blog/react-native-database-performance-comparison, Jul 2024). For OpenForge, PowerSync + op-sqlite gives the least custom code; ElectricSQL 1.0 is the stronger choice if the backend is Postgres and you want CDN fan-out. Gotchas: (1) WatermelonDB's bidirectional sync produces "Cannot update a record with pending changes" errors when batch operations leave `_preparedState` set while `_status='synced'` (github.com/Nozbe/WatermelonDB/discussions/1948, Oct 2025). (2) WatermelonDB silently duplicates records during pull sync when the server returns the same row in both created and updated arrays (github.com/Nozbe/WatermelonDB/issues/1881, Jan 2025).

## D. Conflict Resolution for Review Comments

For comment threads, reactions, and draft reviews on a shared PR/MR, the 2024+ state of art is: LWW (last-write-wins) for scalar fields like reaction counts and resolve status; CRDTs only when concurrent text editing of the same thread body is actually required. Yjs v13.6.33 (npm: yjs, updated Sep 2025, 15M weekly downloads) is the de facto standard for real-time text collaboration; Automerge v3.5.0 (npm: automerge, released Sep 2025) cut memory usage 10x and is better suited to immutable app-state sharing workflows. The defensestation/y-comments project (github.com/defensestation/y-comments) demonstrates the correct production pattern for review comments: store comment threads in a database behind an authenticated API, anchor them to Yjs `RelativePosition` objects (not integer offsets), and render highlights as ProseMirror decorations — keeping the CRDT document byte-pure content with no comment data embedded. A Medium writeup (medium.com/@faisalmujtaba/our-comments-kept-sliding-onto-the-wrong-words-heres-how-we-anchored-them-to-the-crdt-b6e3751e3f93) documents the production bug this pattern fixes: integer `from`/`to` positions silently drift when concurrent edits shift the document, causing comments to highlight the wrong sentence. Gotchas: (1) Automerge had an eventual-consistency failure where two documents with identical sync state diverged after partial sync (github.com/automerge/automerge/issues/870, fixed in v3.0.0-beta, May 2025). (2) Yjs list interleaving occurs when concurrent clients insert elements in reverse order using different client IDs (github.com/automerge/automerge-classic/issues/395).

## E. Image Diff on Mobile

The 2024+ approach for before/after image comparison on mobile is Canvas 2D clipping (no WebGL needed for the swipe divider itself), with GPU acceleration reserved for blur and overlay effects on API 31+ via `RenderEffect.createBlurEffect`. GitHub Mobile's code review ships a horizontally-scrollable diff with a line-wrapping toggle (github.blog/news-insights/product-news/even-better-code-review-in-github-for-mobile); image diffs use a swipe divider overlay rendered via Canvas 2D for maximum compatibility across mid-range devices. GitLab added touch events for its swipe and onion-skin image diff views in MR !26971 (gitlab.com/gitlab-org/gitlab-foss/-/merge_requests/26971), fixing a `pageX` coordinate bug on Chrome/Firefox for Android. For native Android, RevealSlider (github.com/theadityatiwari/RevealSlider) provides a production-ready before/after comparison slider with GPU-accelerated blur on API 31+ and an optimized software box-blur fallback for API 24–30 devices; DiffSlider (github.com/hypersoftdev/DiffSlider) is a lighter XML-declarative alternative for simpler use cases. The critical mid-range Android finding: TBDR GPUs (PowerVR GM9446 on OPPO Reno3 Pro) make `glReadPixels` cost 8.5ms per frame versus 0.5ms on Mali — 17x slower — because tile-based deferred rendering must resolve all tiles to linear memory before CPU readback. Using `TextureView` instead of `glReadPixels` for output eliminates this penalty entirely (github.com/ezoushen/blur-cmp/blob/main/docs/performance-analysis.md). Gotchas: (1) WebGL shader branching causes thread divergence on older Mali GPUs (G72), making branchless sampling necessary (github.com/ezoushen/blur-cmp).

## F. Deep-Link Routing

The 2024+ standard is verified Universal Links on iOS (AASA file at `/.well-known/apple-app-site-association`) and verified App Links on Android (`android:autoVerify="true"` + `assetlinks.json`), with custom scheme as a development-only fallback. Android 12+ (API 31) blocks unverified web intents from auto-opening apps, closing the pre-12 hijacking vector where any app could intercept a URL. Libraries: react-native-url-polyfill v4.0.0 (github.com/charpeni/react-native-url-polyfill, 6.2M weekly downloads, updated Jul 2026) provides WHATWG-compliant URL parsing in the RN runtime; react-native-deeplink-manager (npm) handles both custom schemes and universal/app links with auth guards and deferred deep-link support. React Navigation's `linking` prop integrates all of this natively (reactnavigation.org/docs/deep-linking). The most severe production bug class is OAuth callback hijacking via `autoVerify=false`: a malicious app registers the same host and path in its manifest, and the OS shows a disambiguation dialog; if the user taps the wrong app, the authorization code is disclosed (security.lauritz-holtmann.de/post/sso-android-autoverify/, reported to Google Nov 2024, fixed in Android 12). A second vector: OpenProject allowed custom URI schemes for OAuth callbacks without PKCE, enabling token interception on the device (github.com/opf/openproject/security/advisories/GHSA-w92f-h4wh-g4w4, patched v17.0.5, Feb 2026). Shopify's HackerOne report #1087744 demonstrated that appending `../` to a deep-link path bypassed prefix restrictions, loading arbitrary URLs in the app's WebView with JavaScript bridge access (hackerone.com/reports/1087744).
