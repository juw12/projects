### 1. electron-builder NSIS Auto-Update

**Spec version:** electron-builder v27+ / electron-updater >= 7.0 (2025-2026)
**Manifest format:** YAML (`latest.yml`, `latest-mac.yml`, `latest-linux.yml`)
**Signature:** Ed25519 (manifest signing, v27+)
**Primary source:** [electron-builder auto-update docs](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md)

#### 1.1 Architecture Overview

electron-builder's auto-update system has three layers:

1. **Build-time**: electron-builder generates `latest.yml` metadata and `.blockmap` files alongside the installer artifact.
2. **Publish-time**: The configured provider (GitHub, S3, R2, Generic, etc.) receives the artifact + metadata.
3. **Runtime**: `electron-updater` (the `AppUpdater` class) queries the provider, validates the manifest signature, downloads the update (differentially if possible), verifies checksums, and installs.

The built-in `autoUpdater` from `electron` is replaced by `electron-updater`'s `AppUpdater` subclass (`NsisUpdater`, `MacUpdater`, `AppImageUpdater`).

> **Note:** Squirrel.Windows is explicitly **not supported** by electron-builder. The NSIS target uses its own Squirrel-based update logic internally but does not consume `RELEASES` files.
> — [electron-builder auto-update.md, line 28](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md#L28)

#### 1.2 `latest.yml` Schema (v27+ `files[]` Format)

The canonical update manifest for Windows NSIS builds:

```yaml
# latest.yml — generated by electron-builder, signed in v27+
version: 1.2.0
files:
  - url: "MyApp Setup 1.2.0.exe"
    sha512: "Dj51I0q8aPQ3ioaz9LMqGYujAYRbDNblAQbodDRXAMxmY6hsHqEl3F6SvhfJj5oPhcqdX1ldsgEvfMNXGUXBIw=="
    size: 62021782
    blockMapUrl: "MyApp Setup 1.2.0.exe.blockmap"   # optional; defaults to <url>.blockmap
  # For nsis-web installers, a companion 7z package:
  - url: "MyApp 1.2.0.7z"
    sha512: "..."
    size: 55000000
stagingPercentage: 10   # optional; 0-100; omitted = 100% rollout
# Legacy fields (electron-updater < 2.16.0 only):
# path: "MyApp Setup 1.2.0.exe"
# sha512: "..."
# sha2: "..."
```

**Field semantics:**

| Field | Type | Required | Semantics |
|-------|------|----------|-----------|
| `version` | `string` | yes | SemVer string (e.g. `1.2.0`). Must be greater than the running app's version for the update to be offered (unless `allowDowngrade`). |
| `files` | `array` | yes (v27+) | Array of file descriptors. Each entry is an artifact that may be downloaded. The first entry is the primary installer. |
| `files[].url` | `string` | yes | Relative or absolute URL to the artifact. Relative URLs resolve against the feed base URL. |
| `files[].sha512` | `string` | yes | Base64-encoded SHA-512 digest of the file. Verified after download. |
| `files[].size` | `integer` | yes | File size in bytes. Used for progress reporting and sanity checks. |
| `files[].blockMapUrl` | `string` | no | Optional. URL to the `.blockmap` file for differential updates. Defaults to `.blockmap`. Required when using pre-signed URLs. |
| `stagingPercentage` | `integer` | no | 0-100. If present, only a percentage of users (determined by a hash of the app's machine ID) receive the update. **Must be re-signed if changed after initial signing.** |
| `path` | `string` | no (legacy) | Legacy single-file URL. Deprecated in v27; only emitted when `electronUpdaterCompatibility` includes `< 2.16.0`. |
| `sha512` (top-level) | `string` | no (legacy) | Legacy top-level SHA-512. Same deprecation as `path`. |
| `sha2` | `string` | no (legacy) | Legacy SHA-256. **Deprecated in v27; rejected in v28.** |

> **Signaling note:** The `stagingPercentage` field is **not written by electron-builder itself** — it must be added manually (or by a CI script) after the build, and the manifest must be re-signed.
> — [electron-builder auto-update.md, lines 336-351](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md#L336-L351)

#### 1.3 Provider Configuration

The `publish` block in `electron-builder.yml` (or `package.json` -> `build`) selects the provider:

```yaml
# electron-builder.yml
publish:
  provider: github          # | s3 | spaces | r2 | generic | keygen | bitbucket | gitlab
  # --- GitHub ---
  owner: my-org
  repo: my-app
  # private: true           # requires GH_TOKEN
  # --- S3 / R2 / Spaces ---
  bucket: my-bucket
  region: auto              # or explicit region
  path: /releases
  # --- Generic (HTTP) ---
  url: https://updates.example.com/releases
```

**Provider-specific notes:**

| Provider | Auth | Notes |
|----------|------|-------|
| `github` | `GH_TOKEN` env var (for private repos) | Uses GitHub Releases API. Rate limit: 5000 req/user/hr. Up to 3 API calls per update check. |
| `s3` | AWS credentials (env vars or instance profile) | Supports any S3-compatible endpoint. |
| `r2` | Cloudflare R2 credentials | Same interface as S3; R2 is S3-compatible. |
| `spaces` | DigitalOcean Spaces credentials | S3-compatible. |
| `generic` | None (or `addAuthHeader`) | Static HTTP(S) server. You must upload files manually. |
| `keygen` | Keygen API token | Keygen Auto-Updates service. |
| `bitbucket` | `BITBUCKET_TOKEN` | Bitbucket Downloads API. |
| `gitlab` | `GITLAB_TOKEN` | GitLab Releases API. |

> **Bintray is deprecated** and no longer supported as a provider.
> — [electron-builder auto-update.md, line 384](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md#L384): "for all providers except `bintray` (because not required, `bintray` doesn't use `latest.yml`)" — this is the last vestige; bintray shut down in 2021.

#### 1.4 Runtime Configuration (electron-updater)

```typescript
import { NsisUpdater } from "electron-updater";

const updater = new NsisUpdater({
  provider: "generic",
  url: "https://updates.example.com/releases",
  requestHeaders: {
    "Authorization": Bearer ,
  },
});

// --- Install-on-next-launch (v27+) ---
// Default: "onQuit" — installs when app quits
// Planned v28 default: "onNextLaunch"
updater.autoInstallEvent = "onNextLaunch";

// --- Allow downgrades ---
// By default, the updater rejects updates with a version <= current.
updater.allowDowngrade = true;

// --- Custom verification hook ---
updater.verifyUpdateFile = async ({ updateFilePath, originalUpdateFileName }) => {
  // Return { response: "success" } or { response: "failure", message: "..." }
};
```

**`autoInstallEvent` values:**

| Value | Behavior |
|-------|----------|
| `"onQuit"` (default v27) | Spawns the installer as a detached process when the app quits. **Risk:** OS session-end can kill the installer mid-install. |
| `"onNextLaunch"` | Persists the downloaded update; installs at the start of the next app launch. **Safer** — no session-end race. |
| `"manual"` | No automatic install. The developer must call `quitAndInstall()` explicitly. |

> **Session-end guard (v27+):** When the OS signals session end (shutdown, reboot, log off), the on-quit install is skipped and the update stays cached for the next regular quit.
> — [electron-builder auto-update.md, lines 184-238](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md#L184-L238)

#### 1.5 Differential Updates (`.blockmap`)

electron-builder publishes a **block map** file (`.blockmap`) alongside each artifact. The updater compares the new map with the cached previous map and downloads only changed byte ranges using HTTP `Range` requests.

**Blockmap formats (v27+):**

| Format | electron-updater | Block size | Transfer mode |
|--------|-----------------|-----------|---------------|
| `"v3"` (default for `>=7`) | >= 7.0 | 512 B (stored) / 8-32 KiB (compressed) | Fetches only changed parts via `Range` requests; three-level layout (super-groups -> groups -> 10-byte records) |
| `"v2"` (default for `<7`) | >= 1.0 | ~16 KiB | Downloaded in full on every update |

```json
// electron-builder config to control blockmap format
{
  "electronUpdaterCompatibility": ">=7",
  "blockmap": "v3"
}
```

**Key properties:**
- One `.blockmap` per artifact; independent of any previous version.
- Server only needs HTTP `Range` support (no delta computation server-side).
- Max blockmap size: 1/16 of update size, min 8 MiB, max 64 MiB.
- Gaps < 8 KiB between changed ranges are fetched rather than copied.
- Max 200 ranges per `multipart/byteranges` request (Apache `MaxRanges` default).

> — [electron-builder auto-update.md, lines 386-431](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md#L386-L431)

#### 1.6 Staged Rollouts

```yaml
# latest.yml with staged rollout
version: 1.1.0
files:
  - url: "TestApp Setup 1.1.0.exe"
    sha512: "..."
    size: 62021782
stagingPercentage: 10   # 10% of users
```

- The percentage is applied client-side: electron-updater hashes the machine ID and checks if the hash falls within the percentage.
- **To pull a bad release:** you must increment the version number above the broken release. Re-publishing the same version will not reach users already on the broken version.
- **Signing:** Changing `stagingPercentage` in a signed manifest invalidates the signature. The manifest must be re-signed with the same key(s) before uploading.

> — [electron-builder auto-update.md, lines 332-381](https://github.com/electron-userland/electron-builder/blob/cdd9f7ec77007cdc9657b9f9faa0be2000564d59/website/docs/features/auto-update.md#L332-L381)

#### 1.7 `app-update.yml` (Internal Build Artifact)

electron-builder writes an internal `app-update.yml` into the app's `resources` directory at build time. This file tells `electron-updater` which provider to use at runtime. Developers should not edit it directly.

```yaml
# app-update.yml (generated, in resources/)
provider: generic
url: https://updates.example.com/releases
```

#### 1.8 Events

| Event | Payload | Fired when |
|-------|---------|------------|
| `error` | `Error` | Any error during the update lifecycle |
| `checking-for-update` | — | Update check started |
| `update-available` | `UpdateInfo` | A newer version is available; download starts if `autoDownload` is true |
| `update-not-available` | `UpdateInfo` | No update available |
| `download-progress` | `{ bytesPerSecond, percent, total, transferred }` | Download progress |
| `update-downloaded` | `UpdateInfo` | Download complete |
| `update-cancelled` | `UpdateInfo` | User cancelled or download aborted |
| `appimage-filename-updated` | `path: string` | AppImage moved to final location (Linux only) |

### 2. @tauri-apps/updater (Tauri 2.x)

**Spec version:** Tauri 2.x / `tauri-plugin-updater` (2024-2026)
**Manifest format:** JSON (static file or dynamic server response)
**Signature:** Ed25519 (`.sig` files, mandatory — cannot be disabled)
**Primary source:** [Tauri Updater docs](https://v2.tauri.app/plugin/updater/)
**Source repo:** [tauri-apps/plugins-workspace](https://github.com/tauri-apps/plugins-workspace) @ [`685d342`](https://github.com/tauri-apps/plugins-workspace/commit/685d3424a946346721d839add3bfb6521690eb6e)

#### 2.1 Architecture Overview

Tauri's updater is a Rust plugin (`tauri-plugin-updater`) with a JavaScript guest binding (`@tauri-apps/plugin-updater`). The update flow:

1. App calls `check()` (JS) or `updater().check()` (Rust).
2. The updater fetches the endpoint(s) from `tauri.conf.json`.
3. The server responds with a JSON manifest (or `204 No Content` if no update).
4. The updater verifies the Ed25519 signature against the embedded public key.
5. The updater downloads the update bundle.
6. The updater installs the bundle (platform-specific installer).
7. The app relaunches.

**Rust version requirement:** >= 1.90.

#### 2.2 `tauri.conf.json` — Updater Block

```json
{
  "bundle": {
    "createUpdaterArtifacts": true
  },
  "plugins": {
    "updater": {
      "pubkey": "dW50cnVzdGVkIGNvbW1lbnQ6IHN1ZmYgaGFzIG5ldmVyIHBhaW4gYW4gbW91c2U=\n",
      "endpoints": [
        "https://releases.myapp.com/{{target}}/{{arch}}/{{current_version}}",
        "https://github.com/user/repo/releases/latest/download/latest.json"
      ],
      "dangerousInsecureTransportProtocol": false
    }
  }
}
```

**Field semantics:**

| Field | Type | Required | Semantics |
|-------|------|----------|-----------|
| `createUpdaterArtifacts` | `boolean \| "v1Compatible"` | yes | `true` (v2 default): creates platform-native updater artifacts. `"v1Compatible"`: creates `.tar.gz`/`.zip` archives (for migrating from Tauri 1). **Will be removed in v3.** |
| `pubkey` | `string` | yes | The **content** of the public key PEM file (not a file path). Generated by `tauri signer generate`. Used to verify update signatures. |
| `endpoints` | `string[]` | yes | Array of URLs to check for updates. Tauri tries each in order; proceeds to the next only on a non-2XX response. TLS is enforced in production. |
| `dangerousInsecureTransportProtocol` | `boolean` | no | Set to `true` to allow `http://` endpoints. **Not recommended for production.** |

**Dynamic URL variables** (substituted before the request is made):

| Variable | Value |
|----------|-------|
| `{{current_version}}` | The running app's version (e.g. `1.2.0`) |
| `{{target}}` | OS name: `linux`, `windows`, or `darwin` |
| `{{arch}}` | Architecture: `x86_64`, `i686`, `aarch64`, or `armv7` |

#### 2.3 Static JSON Manifest

For static hosting (S3, R2, GitHub Releases, CDN):

```json
{
  "version": "1.2.0",
  "notes": "Bug fixes and performance improvements.",
  "pub_date": "2026-11-01T10:30:00Z",
  "platforms": {
    "linux-x86_64": {
      "signature": "MEUCIQ...",
      "url": "https://releases.myapp.com/linux-x86_64/myapp.AppImage"
    },
    "windows-x86_64": {
      "signature": "MEUCIQ...",
      "url": "https://releases.myapp.com/windows-x86_64/myapp-setup.exe"
    },
    "darwin-x86_64": {
      "signature": "MEUCIQ...",
      "url": "https://releases.myapp.com/darwin-x86_64/myapp.app.tar.gz"
    }
  }
}
```

**Required keys:** `version`, `platforms.<target>.url`, `platforms.<target>.signature`.
**Optional keys:** `notes`, `pub_date`, additional `platforms` entries.

**Platform key format:** `<OS>-<ARCH>` where:
- `OS`: `linux`, `darwin`, `windows`
- `ARCH`: `x86_64`, `aarch64`, `i686`, `armv7`

> **Note:** Tauri validates the **entire** JSON file before checking the version field. If any platform entry is malformed, the whole file is rejected.

#### 2.4 Dynamic Update Server Response

For a dynamic server (e.g. a custom API):

- **No update:** Respond with `204 No Content`.
- **Update available:** Respond with `200 OK` and:

```json
{
  "version": "1.2.0",
  "pub_date": "2026-11-01T10:30:00Z",
  "url": "https://releases.myapp.com/myapp-setup.exe",
  "signature": "MEUCIQ...",
  "notes": "Bug fixes and performance improvements."
}
```

**Required keys:** `url`, `version`, `signature`.
**Optional keys:** `pub_date`, `notes`.

The server can use the `{{current_version}}`, `{{target}}`, `{{arch}}` variables from the endpoint URL to determine if an update is needed.

#### 2.5 Signature Verification Flow

1. `tauri signer generate` produces a private key (`~/.tauri/myapp.key`) and prints the public key.
2. The public key is embedded in `tauri.conf.json` -> `plugins.updater.pubkey`.
3. At build time, `TAURI_SIGNING_PRIVATE_KEY` env var must be set. Tauri signs each update artifact and produces a `.sig` file.
4. The `.sig` file's **content** is placed in the JSON manifest's `signature` field (not a URL or path).
5. At update time, the updater verifies the downloaded bundle's signature against the embedded public key. **This check cannot be disabled.**

**Generated artifacts by platform (v2 default):**

| Platform | Standard bundle | Updater bundle | Signature file |
|----------|----------------|----------------|----------------|
| Windows | `myapp-setup.exe` (NSIS) or `myapp.msi` | Same file (reused) | `myapp-setup.exe.sig` / `myapp.msi.sig` |
| macOS | `myapp.app` | `myapp.app.tar.gz` | `myapp.app.tar.gz.sig` |
| Linux | `myapp.AppImage` | Same file (reused) | `myapp.AppImage.sig` |

#### 2.6 Windows `installMode`

```json
{
  "plugins": {
    "updater": {
      "windows": {
        "installMode": "passive"
      }
    }
  }
}
```

| Mode | Behavior |
|------|----------|
| `"passive"` (default) | Small progress window; no user interaction required. **Recommended.** |
| `"basicUi"` | Basic installer UI; user interaction required to finish. |
| `"quiet"` | No UI. Cannot request admin privileges. Only works for per-user installs. **Not recommended.** |

#### 2.7 Custom Target and Downgrades

**Custom target** (for universal macOS binaries, custom build flavors):

```javascript
const update = await check({ target: 'macos-universal' });
```

```rust
let update = app
    .updater_builder()
    .target("macos-universal")
    .build()?
    .check()
    .await?;
```

**Allowing downgrades:**

```rust
let update = app
    .updater_builder()
    .version_comparator(|current, update| {
        update.version != current
    })
    .build()?
    .check()
    .await?;
```

#### 2.8 Permissions (Capabilities)

```json
{
  "permissions": ["updater:default"]
}
```

`updater:default` includes: `allow-check`, `allow-download`, `allow-install`, `allow-download-and-install`.

### 3. Capacitor Live Update (Capawesome)

**Spec version:** `@capawesome/capacitor-live-update` 8.x (Capacitor 8, 2025-2026)
**Manifest format:** JSON (Capawesome Cloud API response or self-hosted metadata)
**Signature:** RSA (PEM-encoded public key, optional but recommended)
**Primary source:** [Capacitor Live Update plugin docs](https://capawesome.io/plugins/live-update/)
**Self-hosting:** [Capawesome Cloud self-hosting docs](https://capawesome.io/cloud/live-updates/self-hosting/)

#### 3.1 Architecture Overview

Capacitor Live Update is an OTA (Over-The-Air) update system for the **web layer** of Capacitor/Cordova/Electron apps. It does **not** update native code — it replaces the bundled web assets (HTML, CSS, JS) with a new bundle downloaded from a server.

Key characteristics:
- **No app store review required** for web-layer changes.
- **Rollback** to the default (native-bundled) bundle if a bad update is detected.
- **Channel-based** delivery for staged rollouts and QA.
- **Delta updates** supported (download only changed files).
- **Code signing** via RSA public key (optional).

#### 3.2 Plugin Configuration (`capacitor.config.ts`)

```typescript
import { CapacitorConfig } from '@capacitor/cli';

const config: CapacitorConfig = {
  plugins: {
    LiveUpdate: {
      appId: '6e351b4f-69a7-415e-a057-4567df7ffe94',
      autoBlockRolledBackBundles: true,
      autoDeleteBundles: false,
      autoUpdateStrategy: 'background',
      defaultChannel: 'production',
      httpTimeout: 60000,
      publicKey: '-----BEGIN PUBLIC KEY-----\\nMIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQDD...\\n-----END PUBLIC KEY-----',
      readyTimeout: 10000,
      serverDomain: 'api.cloud.capawesome.io'
    }
  }
};
```

**Field semantics:**

| Field | Type | Default | Required | Semantics |
|-------|------|---------|----------|-----------|
| `appId` | `string` | — | yes (Cloud) | Unique app identifier from Capawesome Cloud (UUID). **Not** the same as the app bundle ID. |
| `autoBlockRolledBackBundles` | `boolean` | `false` | no | Automatically block bundles that caused a rollback (up to 100). |
| `autoDeleteBundles` | `boolean` | `false` | no | Automatically delete unused bundles after `ready()` is called. |
| `autoUpdateStrategy` | `'none' \| 'background'` | `'none'` | no | `'background'`: auto-download and apply at app startup and on resume. |
| `defaultChannel` | `string` | — | no | Default channel. Overridden by `setChannel()`, native config, or `sync()` parameter. |
| `httpTimeout` | `number` | `60000` | no | HTTP request timeout in milliseconds. |
| `publicKey` | `string` | — | no | PEM-encoded RSA public key for bundle signature verification. **Strongly recommended for production.** |
| `readyTimeout` | `number` | `0` | no | Milliseconds to wait for `ready()` before rolling back. **Strongly recommended to set** (e.g. `10000`). `0` disables. |
| `serverDomain` | `string` | `'api.cloud.capawesome.io'` | no | API domain for Capawesome Cloud. |

#### 3.3 Bundle Metadata (Cloud API Response)

```json
{
  "artifactType": "zip",
  "bundleId": "1e42e1df-f4b3-4564-90d0-2303ca8fbd49",
  "url": "https://server.tld/downloads/1e42e1df-f4b3-4564-90d0-2303ca8fbd49.zip",
  "signature": "base64-rsa-signature...",
  "customProperties": { "version": "1.2.0", "notes": "..." },
  "rollout": 50,
  "channel": "production"
}
```

| Field | Type | Required | Semantics |
|-------|------|----------|-----------|
| `artifactType` | `string` | yes | `'zip'` (standard) or `'delta'` (incremental). Self-hosting currently requires `'zip'`. |
| `bundleId` | `string` | yes | Unique identifier for the bundle (UUID or custom string). |
| `url` | `string` | yes | URL to download the bundle file. |
| `signature` | `string` | no | RSA signature of the bundle (base64). Verified against `publicKey`. |
| `customProperties` | `object` | no | Key-value metadata attached to the bundle. |
| `rollout` | `number` | no | Percentage rollout (0-100). |
| `channel` | `string` | no | The channel this bundle belongs to. |

#### 3.4 Channel Model

**Channel resolution order** (highest priority first):
1. `channel` parameter of `sync()` — one-time, not persisted.
2. Native config (`Info.plist` / `strings.xml` / `capacitor.electron.config.ts`).
3. Capacitor config `defaultChannel`.

**Versioned channels:** Tie a channel to the native version code at build time:

```groovy
// Android build.gradle
resValue "string", "capawesome_live_update_default_channel",
  "production-" + defaultConfig.versionCode
```

#### 3.5 Rollback (Reset-on-Failure)

1. App starts with a new bundle.
2. Plugin starts a timer (`readyTimeout` ms).
3. If the app calls `LiveUpdate.ready()` before the timer expires -> new bundle confirmed.
4. If the timer expires **before** `ready()` is called -> plugin **resets to the default bundle** and reloads.

```typescript
import { LiveUpdate } from '@capawesome/capacitor-live-update';
await LiveUpdate.ready();
```

If `autoBlockRolledBackBundles` is enabled, the bundle that caused the rollback is added to a blocked list (up to 100 entries).

#### 3.6 Code Signing

```bash
npx @capawesome/cli apps:liveupdates:register \\
  --url https://domain.tld/bundle.zip \\
  --private-key ./key.pem \\
  --path ./bundle.zip
```

Code signing for self-hosted bundles requires plugin **6.9.0+** (Cap 6), **7.5.0+** (Cap 7), or **8.0.0+** (Cap 8).

#### 3.7 Delta Updates

- Supported when using Capawesome Cloud (not yet for self-hosting).
- The `artifactType` in the metadata will be `'delta'` instead of `'zip'`.
- The client applies the delta to the current bundle to produce the new bundle.

#### 3.8 Electron Platform Notes

- App version is read from `electron/package.json` -> `version`.
- Only `zip` artifact type is supported.
- Bundles stored in `capawesome-live-update` directory inside `userData`.
- Rollback is **kill-safe**: if the app crashes before `ready()`, rollback occurs on next start.

### 4. Squirrel.Windows RELEASES + release.nuspec

**Spec version:** Squirrel.Windows `develop` branch (2025-2026; maintenance mode — [issue #1470](https://github.com/Squirrel/Squirrel.Windows/issues/1470))
**Manifest format:** Plain text (`RELEASES` file) + NuGet package (`.nupkg`)
**Signature:** None (relies on HTTPS + Authenticode on the `.exe`)
**Primary source:** [Squirrel.Windows GitHub](https://github.com/Squirrel/Squirrel.Windows) @ [`51f5e2c`](https://github.com/Squirrel/Squirrel.Windows/commit/51f5e2cb01add79280a53d51e8d0cfa20f8c9f9f)

#### 4.1 Architecture Overview

Squirrel.Windows is a C#-based installation and update framework for Windows desktop apps. It uses **NuGet packages** (`.nupkg`) as the distribution unit and a plain-text `RELEASES` file as the update manifest.

The update flow:
1. `UpdateManager.CheckForUpdate()` fetches the `RELEASES` file from the update URL.
2. It compares the installed version against the versions listed in `RELEASES`.
3. It downloads the required full and/or delta packages.
4. It applies the updates (extracts to a new version directory, updates shortcuts, cleans up old versions).
5. The app restarts on the next launch.

> **Important:** Squirrel.Windows is **not supported** by electron-builder. The two systems use different manifest formats and update mechanics.

#### 4.2 `release.nuspec` Schema

The `release.nuspec` file is a standard NuGet package metadata file. Squirrel reads specific fields from it.


**Mandatory fields for Squirrel:**

| Field | Type | Required | Semantics |
|-------|------|----------|-----------|

#### 4.3 `RELEASES` File Format

The `RELEASES` file is a plain-text file where each line describes one package:

```
SHA1_HASH  FILENAME  FILE_SIZE_BYTES
```

**Real example from the Squirrel docs:**

```
E3F67244E4166A65310C816221A12685C83F8E6F MyApp-1.0.0-full.nupkg 600725
0D777EA94C612E8BF1EA7379164CAEFBA6E24463 MyApp-1.0.1-delta.nupkg 6030
85F4D657F8424DD437D1B33CC4511EA7AD86B1A7 MyApp-1.0.1-full.nupkg 600752
```

**Format specification:**

| Column | Format | Semantics |
|--------|--------|-----------|
| 1 | 40-char uppercase hex | SHA-1 hash of the `.nupkg` file |
| 2 | Filename | Name of the `.nupkg` file (relative to the `RELEASES` file location) |
| 3 | Integer | File size in bytes |

**Lines are separated by newlines. No header. No trailing newline required.**

> — [Squirrel.Windows updating docs](https://github.com/Squirrel/Squirrel.Windows/blob/51f5e2cb01add79280a53d51e8d0cfa20f8c9f9f/docs/getting-started/5-updating.md)

#### 4.4 Delta Package Naming Convention

| Package type | Filename pattern | Example |
|-------------|-----------------|---------|
| Full package | `{AppName}-{Version}-full.nupkg` | `MyApp-1.0.1-full.nupkg` |
| Delta package | `{AppName}-{Version}-delta.nupkg` | `MyApp-1.0.1-delta.nupkg` |

The delta package is a **binary diff** between the previous full package and the new full package, computed by `Squirrel --releasify`. The delta is significantly smaller than the full package (6,030 bytes vs 600,752 bytes in the example above).

The `--releasify` command:
1. Creates the `Releases` directory.
2. Creates `Setup.exe` (contains the latest full package).
3. Creates/appends the `RELEASES` file.
4. Creates the `-full.nupkg` package.
5. Creates the `-delta.nupkg` package (if a previous version exists).

#### 4.5 `.nupkg` + `.exe` Relationship

```
Releases/
+-- Setup.exe                    <- bootstrapper (contains MyApp-1.0.1-full.nupkg)
+-- RELEASES                     <- manifest
+-- MyApp-1.0.0-full.nupkg       <- full package v1.0.0
+-- MyApp-1.0.1-delta.nupkg      <- delta from 1.0.0 to 1.0.1
+-- MyApp-1.0.1-full.nupkg       <- full package v1.0.1
```

1. **`.nupkg`** = The distribution unit. Contains all app files under `lib\net45\`.
2. **`Setup.exe`** = The bootstrapper. Contains the latest full `.nupkg` embedded. Runs on first install.
3. **`Update.exe`** = The update agent. Installed alongside the app. Fetches `RELEASES`, downloads packages, applies updates.
4. **`RELEASES`** = The manifest. Lists all available packages with SHA-1 hashes.

#### 4.6 Update Flow (UpdateManager)

From the `UpdateManager` source code:

```csharp
// src/Squirrel/UpdateManager.cs
public async Task<UpdateInfo> CheckForUpdate(
    bool ignoreDeltaUpdates = false,
    Action<int> progress = null,
    UpdaterIntention intention = UpdaterIntention.Update)
{
    var checkForUpdate = new CheckForUpdateImpl(rootAppDirectory);
    await acquireUpdateLock();
    return await checkForUpdate.CheckForUpdate(
        intention,
        Utility.LocalReleaseFileForAppDir(rootAppDirectory),
        updateUrlOrPath,
        ignoreDeltaUpdates,
        progress,
        urlDownloader
    );
}
```

The update process:
1. `CheckForUpdate` fetches `RELEASES` from `updateUrlOrPath`.
2. Parses each line: SHA-1, filename, size.
3. Compares installed version against listed versions.
4. Determines which packages to download (delta if available, else full).
5. `DownloadReleases` downloads the required packages.
6. `ApplyReleases` extracts to a new version directory, updates shortcuts, cleans up old versions.

> — [Squirrel.Windows UpdateManager source](https://github.com/Squirrel/Squirrel.Windows/blob/51f5e2cb01add79280a53d51e8d0cfa20f8c9f9f/src/Squirrel/UpdateManager.cs#L44-L55)

#### 4.7 Channels

Squirrel supports channels by using different `RELEASES` files:

```
https://releases.example.com/
+-- stable/RELEASES
+-- beta/RELEASES
+-- dev/RELEASES
```

The channel is specified in the `UpdateManager` constructor via the `updateUrlOrPath` parameter.

### 5. Sparkle Appcast XML

**Spec version:** Sparkle 2.10.1 (2025-10-25)
**Manifest format:** XML (RSS 2.0 with `sparkle` namespace extensions)
**Signature:** EdDSA (Ed25519) via `sparkle:edSignature` attribute
**Primary source:** [Sparkle documentation](https://sparkle-project.org/documentation/)
**Publishing guide:** [Sparkle publishing an update](https://sparkle-project.org/documentation/publishing/)
**Source repo:** [sparkle-project/Sparkle](https://github.com/sparkle-project/Sparkle) @ [`ab7d712`](https://github.com/sparkle-project/Sparkle/commit/ab7d71291238df6e0492143b120c9b696a35f603) (v2.10.1)

#### 5.1 Architecture Overview

Sparkle is a software update framework for macOS. It uses an **appcast** — an RSS 2.0 feed with custom `sparkle:` namespace elements — to communicate update information to the client.

The update flow:
1. The app's `SPUStandardUpdaterController` fetches the appcast from `SUFeedURL`.
2. It parses the `<item>` elements and compares `sparkle:version` against the installed `CFBundleVersion`.
3. If a newer version is found, it validates the EdDSA signature on the `<enclosure>`.
4. It downloads the archive (dmg, zip, tar, aar).
5. It extracts and replaces the app bundle.
6. The app relaunches.

> **Security:** As of Sparkle 2.9, **signed feeds** (`SURequireSignedFeed`) are supported. The appcast file itself can be signed, preventing a compromised server from redirecting users to a malicious update URL.

#### 5.4 EdDSA (Ed25519) Signature Flow

1. **Key generation** (one-time): `./bin/generate_keys` — private key in Keychain, public key printed.
2. **Embed public key** in `Info.plist`: `<key>SUPublicEDKey</key><string>pfIShU4dEXqP...</string>`
3. **Sign each update archive**: `./bin/sign_update path_to_update.dmg`
4. **Add signature** to the `<enclosure>` in the appcast.
5. **Verify**: At update time, Sparkle computes the Ed25519 signature and verifies against `SUPublicEDKey`. **Update aborted on failure.**

**Key rotation:** For Developer ID-signed apps, Sparkle allows rotating keys by issuing a new update that changes either the Apple code signing certificate **or** the EdDSA keys (but not both simultaneously).

#### 5.5 Signed Feeds (Sparkle 2.9+)

- Enable `SURequireSignedFeed` in `Info.plist`.
- `SUVerifyUpdateBeforeExtraction` must also be enabled.
- `generate_appcast` signs the appcast and release notes files.
- `SUSignedFeedFailureExpirationInterval` allows limited fallback via key rotation.

#### 5.6 Delta Updates

- `generate_appcast` automatically creates `.delta` files.
- `<enclosure>` includes `sparkle:deltaFrom="1.9"` to indicate the base version.
- The app must be on **exactly** the `deltaFrom` version to use the delta.

#### 5.7 Channels

```xml

  <sparkle:channel>beta</sparkle:channel>
```

- By default, updaters only see updates on the **default** channel.

- An updater **cannot** exclude itself from the default channel.

- `phasedRolloutInterval` in **seconds** between groups.

- A random group ID is generated per app install.
- Not applied to critical updates or manual update checks.
- `pubDate` is required.

### 6. PWA Service Worker Update Lifecycle

**Spec version:** W3C Service Worker Standard (Working Draft) + Workbox 7.x (2025-2026)
**Manifest format:** JavaScript module (service worker script) + precache manifest (JSON array)
**Signature:** None (relies on HTTPS / TLS)
**Primary source:** [Workbox documentation](https://developer.chrome.com/docs/workbox/)
**Precaching:** [workbox-precaching docs](https://developer.chrome.com/docs/workbox/modules/workbox-precaching/)
**Window:** [workbox-window docs](https://developer.chrome.com/docs/workbox/modules/workbox-window/)
**Update handling:** [Workbox update handling guide](https://developer.chrome.com/docs/workbox/handling-service-worker-updates/)
**Source repo:** [GoogleChrome/workbox](https://github.com/GoogleChrome/workbox) @ [`4ea3138`](https://github.com/GoogleChrome/workbox/commit/4ea3138a120fd2c87389b54130e25f47e0fd7089)

#### 6.1 W3C Service Worker Lifecycle

The W3C Service Worker specification defines the following lifecycle states:

```
+----------+    +------------+    +------------+    +----------+
|   Null   |--->| Installing |-->|  Activating|-->|  Active  |
+----------+    +------------+    +------------+    +----------+
                      |                   |               |
                      v                   v               v
               (install event)     (activate event)  (fetch events)
```

**Key lifecycle events:**

| Event | Phase | Semantics |
|-------|-------|-----------|
| `install` | Installation | Fired when a new SW is registered or the script changes. Used for precaching. If install fails, the worker is discarded. |
| `activate` | Activation | Fired after install, before the worker takes control. Used for cleanup (removing old caches). |
| `fetch` | Runtime | Fired for every intercepted request. Worker calls `event.respondWith()`. |
| `message` | Runtime | Fired when a client sends `postMessage()`. Window-to-SW communication. |
| `sync` | Runtime | (Non-standard, Chrome) Background Sync event. |
| `push` | Runtime | (Non-standard) Push message received. |

**Update flow (W3C):**

1. Browser periodically fetches the SW script.
2. If the script changed (byte-comparison), a new SW starts installing.
3. The old worker remains `active`; the new worker is `installing`.
4. After `install`, the new worker is `installed`.
5. If the old worker has no controlled clients, the new worker moves to `activating` -> `active`.
6. If the old worker **still has** controlled clients, the new worker stays `waiting`.
7. The new worker only activates when all old clients close **or** it calls `self.skipWaiting()`.

> **Key insight:** Simply refreshing a page does **not** activate a waiting service worker. The page must be fully closed or the new worker must call `skipWaiting()`.
> — [Workbox window docs](https://developer.chrome.com/docs/workbox/modules/workbox-window/#important_service_worker_lifecycle_moments)

#### 6.2 Workbox Precache Manifest Format

```javascript
import {precacheAndRoute} from 'workbox-precaching';

precacheAndRoute([
  {url: '/index.html', revision: '383676'},
  {url: '/styles/app.0c9a31.css', revision: null},
  {url: '/scripts/app.0d5770.js', revision: null},
]);
```

**Field semantics:**

| Field | Type | Required | Semantics |
|-------|------|----------|-----------|
| `url` | `string` | yes | The URL to precache. Relative URLs resolve against the SW location. |
| `revision` | `string \| null` | yes | `null` = URL already contains versioning. A string = content hash for URLs that cannot contain versioning. |
| `integrity` | `string` | no | Subresource Integrity hash (e.g. `sha384-...`). Precaching fails on mismatch. |

> **Deprecation note:** Previous Workbox versions allowed string URLs. In Workbox v5 this is deprecated; in v6 it is removed. Always pass objects with explicit `revision: null`.
> — [Workbox precaching docs](https://developer.chrome.com/docs/workbox/modules/workbox-precaching/#explanation_of_the_precache_list)

**Generating the manifest:**

```javascript
const {injectManifest} = require('workbox-build');

injectManifest({
  swSrc: './src/sw.js',
  swDest: './dist/sw.js',
  globDirectory: './dist/',
  globPatterns: ['**/*.{js,css,html,svg,png}'],
});
```

#### 6.3 Workbox Strategies

| Strategy | Class | Behavior |
|----------|-------|----------|
| `CacheFirst` | `workbox-strategies` | Try cache first; fall back to network. Best for immutable static assets. |
| `NetworkFirst` | `workbox-strategies` | Try network first; fall back to cache. Best for HTML / API responses. |
| `StaleWhileRevalidate` | `workbox-strategies` | Return cached response immediately; fetch network in background. |
| `NetworkOnly` | `workbox-strategies` | Always go to network. No caching. |
| `CacheOnly` | `workbox-strategies` | Always serve from cache. No network. |
| `PrecacheStrategy` | `workbox-precaching` | Cache-first for precached URLs. Fallback to network on cache miss. |

**Example route registration:**

```javascript
import {registerRoute} from 'workbox-routing';
import {NetworkFirst, CacheFirst, StaleWhileRevalidate} from 'workbox-strategies';

registerRoute(
  ({request}) => request.mode === 'navigate',
  new NetworkFirst({cacheName: 'pages'}),
);

registerRoute(
  ({request}) => ['style','script','worker','image'].includes(request.destination),
  new CacheFirst({cacheName: 'assets'}),
);

registerRoute(
  ({url}) => url.pathname.startsWith('/api/'),
  new StaleWhileRevalidate({cacheName: 'api'}),
);
```

#### 6.4 `skipWaiting` + `clients.claim`

**In the service worker (`sw.js`):**

```javascript
addEventListener('message', (event) => {
  if (event.data && event.data.type === 'SKIP_WAITING') {
    self.skipWaiting();
  }
});

self.addEventListener('activate', (event) => {
  event.waitUntil(self.clients.claim());
});
```

- `self.skipWaiting()`: Moves the worker from `waiting` to `activating` immediately.
- `self.clients.claim()`: Makes the newly activated worker take control of all existing tabs immediately.

**In the window (page JS), using `workbox-window`:**

```javascript
import {Workbox} from 'workbox-window';

const wb = new Workbox('/sw.js');

wb.addEventListener('waiting', async (event) => {
  const updateAccepted = await promptForUpdate();
  if (updateAccepted) {
    wb.messageSkipWaiting();
  }
});

wb.addEventListener('controlling', () => {
  window.location.reload();
});

wb.register();
```

> — [Workbox update handling guide](https://developer.chrome.com/docs/workbox/handling-service-worker-updates/)

#### 6.5 `workbox-window` Lifecycle Events

| Event | `isUpdate` | `isExternal` | Semantics |
|-------|-----------|-------------|-----------|
| `installing` | false / true | — | A new worker started installing. |
| `installed` | false / true | — | Installation complete. |
| `waiting` | true | — | Worker installed but stuck waiting. |
| `activating` | — | — | Worker is activating. |
| `activated` | false / true | — | Activation complete. |
| `controlling` | — | — | Worker now controlling this page. Only fires if `clients.claim()` was called. |
| `redundant` | — | — | Worker was discarded (install failed). |
| `message` | — | — | A `postMessage()` was received. |

**`WorkboxLifecycleWaitingEvent`** (extends `WorkboxLifecycleEvent`):
- `wasWaitingBeforeRegister: boolean` — true if the worker was already waiting before `register()`.

#### 6.7 Window-to-SW Communication

Workbox uses a structured message format:

| Property | Required | Type | Semantics |
|----------|----------|------|-----------|
| `type` | yes | `string` | Unique message type. Uppercase with underscores. |
| `meta` | no | `string` | Name of the Workbox package sending the message. |
| `payload` | no | `*` | The data being sent. |

**`messageSkipWaiting()`** (Workbox v6+): Sends `{type: 'SKIP_WAITING'}` to the waiting worker. Silently does nothing if no worker is waiting.

#### 6.8 Precache Update Flow (End-to-End)

```
1. Deploy new assets + updated sw.js to server
2. Browser navigates to the site
3. navigator.serviceWorker.register('/sw.js') -> updatefound event
4. New SW starts installing -> workbox-precaching install()
5. New assets are downloaded and added to the precache
6. Old SW is still active -> new SW enters "waiting"
7. workbox-window fires "waiting" event -> prompt user
8. User accepts -> messageSkipWaiting() -> self.skipWaiting()
9. New SW activates -> workbox-precaching activate()
   - Removes stale entries from cache
10. clients.claim() -> new SW takes control of existing tabs
11. workbox-window fires "controlling" event -> window.location.reload()
12. Page reloads with new assets served from the updated precache
```

- **W3C Service Worker:** Working Draft. [W3C spec](https://w3c.github.io/ServiceWorker/).
- **Workbox:** v7.x (current). MIT licensed.
- **Browser support:** All major browsers. `skipWaiting` and `clients.claim` universally supported.
- **Background Sync API:** Chrome-only. Workbox provides a fallback.

### 7. Microsoft AppInstaller Schema

**Spec version:** MSIX App Installer 1.23+ / Windows 10 1903+ / Windows 11
**Manifest format:** XML (`.appinstaller` file)
**Signature:** Authenticode (the `.appinstaller` file is code-signed); package integrity via SHA-256 checksum
**Primary source:** [Microsoft Learn — App Installer file](https://learn.microsoft.com/en-us/windows/msix/package/installer-file)

#### 7.1 Architecture Overview

MSIX App Installer (`.appinstaller` file) is a declarative XML file that tells Windows how to find, download, install, update, repair, and uninstall an MSIX or MSIXBundle package. It is the successor to AppV and the modern equivalent of a ClickOnce `.application` file.

The flow:
1. User double-clicks the `.appinstaller` file (or registers via `Add-AppxPackage`).
2. Windows App Installer parses the XML.
3. It downloads the main package (and optional packages) from the specified URIs.
4. It verifies the SHA-256 checksum.
5. It installs the package via the AppX deployment service.
6. On subsequent updates, it checks the `UpdateSettings` policy.

> **Note:** The `.appinstaller` file is **not** the package itself — it is a lightweight manifest that points to the package(s). The actual `.msix` / `.msixbundle` files are downloaded separately.

#### 7.4 Security Model

1. **Authenticode:** The `.appinstaller` file must be Authenticode-signed. Windows validates before parsing.
2. **SHA-256 checksum:** `MainPackage/Checksum` ensures the downloaded package hasn't been tampered with.
3. **TLS:** All URIs must use HTTPS.
4. **Package signing:** `.msix` / `.msixbundle` files must be signed.
5. **Capability display:** `Capabilities` shown to the user in the install prompt.

#### 7.5 Update Flow

1. App Installer fetches the `.appinstaller` from `Uri`.
2. Compares `MainPackage/Version` against the installed version.
3. If newer: applies `Background`, `PromptToInstall`, `DisplayReleaseNotes` policies.
4. Downloads the new package, verifies SHA-256.
5. Installs via the AppX deployment service.
6. `InstallDeadlineInDays` enforces a deadline.

#### 7.6 Spec Version and Platform Requirements

- **Minimum Windows:** Windows 10 version 1903 (build 18362) or later.
- **Minimum App Installer version:** 1.23.230812001.
- **Schema namespace:** `http://schemas.microsoft.com/appx/appinstaller/2018`.
- **Status:** Actively maintained by Microsoft.

> **Note:** The Microsoft Learn page for the AppInstaller file schema is at
> [learn.microsoft.com/windows/msix/package/installer-file](https://learn.microsoft.com/en-us/windows/msix/package/installer-file).

**R2-specific notes:**
- Use **R2 presigned URLs** for authenticated artifact downloads if the bucket is private.
- Enable **R2 versioning** for rollback capability.
- Set **Cache-Control: no-cache** on `latest.json` manifests; **Cache-Control: max-age=31536000, immutable** on versioned artifacts.
- Use **R2 Custom Domains** with a dedicated subdomain (e.g. `releases.airiz.dev`) for TLS-terminating CDN delivery.
- **Range requests** are natively supported by R2, enabling electron-builder's `.blockmap` differential downloads.

### B.6 Protocol Selection Matrix for AIRIZ

| AIRIZ Surface | Recommended Protocol | Rationale |
|---------------|---------------------|-----------|
| Windows desktop (NSIS installer) | electron-builder | Mature, supports R2 via S3-compatible provider, differential updates via blockmap |
| macOS desktop | Sparkle | Native macOS update framework, EdDSA signing, delta updates, phased rollouts |
| Windows MSIX (Store / enterprise) | AppInstaller | Microsoft-native, policy-driven updates, repair support |
| Web / PWA | Workbox | Standard web update mechanism, precaching, offline support |
| Android (Capacitor web layer) | Capacitor Live Update | OTA web bundle updates without Play Store review |
| iOS (Capacitor web layer) | Capacitor Live Update | OTA web bundle updates without App Store review |
| Linux (AppImage) | electron-builder | AppImage updater built-in, R2 via S3 provider |
| Tauri (if adopted) | Tauri Updater | Rust-based, Ed25519 signing, R2 via generic HTTP provider |
