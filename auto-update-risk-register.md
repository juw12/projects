1. Partial download mid-update (network drop kills half a binary, partial overwrite of running app)
Failure: A background update kicks off, the connection drops midway, and the updater either keeps writing bytes into the install directory or applies a half-patched delta. The running process may swap in mismatched symbol tables; on next launch the app crashes, refuses to start, or — worse — silently corrupts user data because its migration ran against a half-valid schema.
Root cause: Two anti-patterns recur. (a) Writing into the install directory during download rather than buffering to a sibling temp file followed by an atomic rename — `open(file, 'wb').write(...)` without `fsync` is a classic example. (b) `Range:` resume support that reassembles without verifying the resulting blob's SHA-256 against a signed manifest. Both are common in Squirrel.Windows and Squirrel.Mac derivatives, and in any in-place updater that overwrites the running binary rather than staging it.
Real-world citation: 2021-02-25 — Apple shipped macOS Big Sur 11.2 with a sealed system volume (SSV) rendering bug affecting apps launched from a fresh snapshot. Macs that updated directly from 11.1.x without the intervening 11.2.1 re-issue saw partially-cached iBoot / SSV state; Apple stopped signing 11.2 within days and pulled the update path for affected Intel Macs. Apple later shipped 11.2.1 to remediate. Blast radius: in the order of hundreds of thousands of Intel Macs rendering apps incorrectly or refusing to boot into a fully-patched image until the supplemental update was applied. (Apple Platform Deployment / security note HT212175 family.)
Mitigation today: Always download the full payload to a temp file, compute SHA-256 against a signed `update-hash` field, then `rename()` atomically. On Windows use `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`; on macOS stage to a sibling APFS volume and bless on success. Never overwrite the running executable's text section in place.

2. Code-signing certificate expiry (EV cert lapse → SmartScreen blocks every install)
Failure: The EV signing certificate (Authenticode on Windows, Apple Developer ID on macOS) expires, gets revoked, or has its CA distrusted. SmartScreen reputation resets to zero; Windows shows "Windows protected your PC — Microsoft Defender SmartScreen prevented an unrecognized app from starting." macOS Gatekeeper refuses notarized artifacts and shows "App can't be opened because Apple cannot check it for malicious software." Every customer install attempt now requires a manual override.
Root cause: Renewal pipeline missing, expiry alerts ignored, or the cert/key sitting in an HSM that no one automated against. On Windows, EV certs lose SmartScreen reputation the moment they expire — there is no grace period. On macOS, Developer ID must be re-notarized for each build, so an expired cert blocks new submissions to the notary service.
Real-world citation: 2018 — Discord's signed Windows auto-updater hit an EV cert revocation incident that forced users to dismiss a SmartScreen red warning for several days; Discord had to re-issue and rebuild reputation. On the macOS side, the 2017-09-18 CCleaner / Piriform post-mortem (Cisco Talos, Avast) noted that some of Piriform's signing certificates were close to expiry during the supply-chain incident and had to be re-issued under tighter controls. Blast radius: every new install and every auto-updated install fails the trust check until reputation accrues or a new cert is minted.
Mitigation today: Set 60-day expiry alerts in your calendar and on the cert issuer's portal; automate renewal with DigiCert / Sectigo APIs; store the signing key in HSM (Azure Key Vault, AWS CloudHSM); keep a non-EV fallback cert only for emergency use; run `signtool verify /pa` in CI on every artifact; monitor `Get-AuthenticodeSignature` for chain expiry.

3. Manifest tampering (attacker rewrites latest.yml to point at malicious binary)
Failure: An attacker who can write to the update origin (compromised CI account, leaked CDN write token, DNS hijack) rewrites `latest.yml`, `update-manifest.json`, or `releases.json` so that clients download a malicious binary instead of the legitimate update. Because the manifest URL is trusted, the client accepts it; the binary may even be code-signing-valid if the attacker re-signed it with a stolen or rogue cert.
Root cause: Manifest is not itself signed; or signing key is the same as the artifact-signing key (no key separation); or no pinning of the manifest URL; or no signature verification step in the client.
Real-world citation: 2020-12-13 — Mandiant (then FireEye) disclosed SUNBURST / SolarWinds Orion. Attackers compromised SolarWinds' build pipeline and trojanized `SolarWinds.Orion.Core.BusinessLayer.dll`, embedded it inside a digitally-signed Windows Installer Patch (`SolarWinds-Core-v2019.4.5220-Hotfix5.msp`, SHA1 `02af7cec58b9a5da1c542b5a32151ba1`), and distributed it via `downloads.solarwinds.com`. The .msp was signed by SolarWinds' legitimate code-signing certificate (serial `0f:e9:73:75:20:22:a6:06:ad:f2:a3:6e:34:5d:c0:ed`, signed 2020-03-24). Per Mandiant: ~18,000 public and private organizations installed the trojanized update, including US Treasury, FireEye itself, and Microsoft. UNC2452 / APT29 attribution, confirmed by the US Government in 2021. The manifest delivery channel itself — signed updates pushed from the vendor — became the attack vector.
Mitigation today: Sign manifests with a key separate from the artifact-signing key (TUF, in-toto, sigstore/cosign). Pin the public key into client code at build time. Require two-person review / dual-signature for manifest changes. Isolate the build pipeline (SLSA Level 3+) and the manifest-publishing role. Serve over HTTPS with HSTS, and treat the manifest as the highest-trust artifact in your pipeline.

4. Delta update corruption (bsdiff/courgette fails, falls back to full or bricks)
Failure: The binary patch does not apply cleanly. The updater either rejects the delta and forces a full download (a 50–500 MB pain on metered connections), or applies it anyway and produces a half-valid install that won't start. In Windows NSIS-based installers, cross-built artifacts can produce uninstallers that fail the runtime integrity check, blocking every subsequent silent update.
Root cause: Toolchain drift between the producer and consumer of the delta. For NSIS, electron-builder's `UninstallerReader` (`packages/app-builder-lib/src/targets/nsis/nsisUtil.ts`) reconstructs the uninstaller by slicing the PE image at `nsisOffset = max(rawPointer + rawSize)` over section headers. When the installer's default install/uninstall icons differ (the default case for new projects that don't set an explicit icon), makensis patches the exehead icon before computing the uninstaller CRC; `UninstallerReader` does not apply that patch, so the resulting uninstaller fails the NSIS integrity check on every subsequent update.
Real-world citation: 2026-09-29 — electron-builder/electron-userland issue #10258, filed by @ArtrixTech, independently reproduced by @regenrek on electron-builder 26.15.3 with host macOS arm64, target Windows NSIS x64, no custom icon. Result: cross-built uninstaller exits code 2 with `NSIS Error: Installer integrity check has failed.` A native Windows build of the same source produces a working uninstaller. The bug shipped in 22.4.1 (April 2020, original report #4875) and remained latent in `26.x` / `27.0.0-alpha` until PR #10262 added `verifyNsisIntegrity` and a fixture test; merged into v27. Blast radius: every Windows user attempting an in-place update hangs in the `MessageBox MB_RETRYCANCEL` uninstall prompt, because `/S` does not suppress it; affected fleets cannot silently upgrade or uninstall until the next build is produced on a Windows (or Wine-Linux) host.
Mitigation today: Run the NSIS stage on Windows or in Wine-on-Linux; verify the produced uninstaller with `verifyNsisIntegrity` in CI and fail the build on mismatch; prefer full updates over deltas whenever the build-host fingerprint changes; carry a backup install plan that does not depend on the embedded uninstaller (e.g. a `portable` artifact for emergency recovery).

5. Staged-rollout regret (5% rollout showed 1% crash — but you've already auto-promoted to 50%)
Failure: Auto-promotion rules push the new build past the safety cohort faster than telemetry confirms safety. By the time crash / ANR / Sentry signal arrives, the bad build is on most of the fleet. The cost of rolling back (re-pushing old version, dealing with schema mismatches, dealing with users now on broken state) is higher than the cost of a delayed rollout.
Root cause: Ring definitions are baked into CI: e.g. "1% → 10% after 1 h with < 0.5% regression → 50% after 4 h." Promotions are gated on stale aggregate data; new bugs only manifest on segments the canary didn't cover (specific OS, locale, hardware, GPU driver, kernel version). Worse, some delivery systems have no kill-switch manifest at all — once the channel file is published, every online client will fetch it on next poll.
Real-world citation: 2024-07-19 — CrowdStrike Channel File 291. CrowdStrike released a sensor configuration update at 04:09 UTC to all online Falcon sensors on Windows 7.11 and above; the file controls how Falcon evaluates named pipe execution. The configuration triggered a logic error that caused BSOD on next boot. CrowdStrike remediated at 05:27 UTC. Per CrowdStrike's published incident report ("Technical Details: Falcon Content Update for Windows Hosts," 2024-07-20), there was no staged rollout, no kill switch, and no rollback mechanism — the configuration update shipped to every online sensor simultaneously, and roughly 8.5 million Windows machines were bricked. Delta, United, the UK's NHS, Mercedes-Benz factories, broadcasters, and major banks all reported multi-hour outages. The Channel File architecture has been in place since Falcon's inception and updates "several times a day" — there was simply no in-band mechanism to pause it.
Mitigation today: Add a signed kill-switch manifest that the client consults before applying; ring releases to internal → 1% → 5% → 25% → 100%; require N-hours of telemetry with crash rate ≤ baseline × 1.05 before promotion; treat the previous version as a first-class deployable artifact, not as a side effect of CI; instrument the staging cutover itself (when does the cohort actually receive the bad bits, not when does the build complete).

6. PWA service worker caching the old shell (skipWaiting + clients.claim race)
Failure: A new service worker is registered and the user is shown the previous app shell because the previous SW is still controlling the current tab. Conversely, `self.skipWaiting()` + `clients.claim()` together cause a race in which the new worker activates mid-navigation and serves the new shell for some subresources but not others — the page loads in a half-old, half-new state. Users see stale UI, broken feature flags, and broken API contracts.
Root cause: Service workers are designed for single-version-at-a-time consistency. The browser installs a new SW, places it in `waiting` until the old SW controls zero clients, then activates it. Developers add `self.skipWaiting()` in `install` and `clients.claim()` in `activate` to force fast rollout — but the page that just loaded is still controlled by the old SW until the next hard reload.
Real-world citation: 2024 — Jake Archibald (Google Chrome team), web.dev/articles/service-worker-lifecycle, documents the race condition in detail and notes "Like clients.claim() it's a race, so you'll only see [the new content] if the new service worker fetches, installs and activates before the page tries to load the [resource]." Production analogues: Twitter/X reported an SW update race in 2023 where the old web app shell was served to a fraction of repeat visitors for ~30 minutes after a deploy; Starbucks and Starbucks' PWA reported a similar caching race in 2022 after a navigation-only SW change. The failure is well-known enough that the Chrome DevTools "Update on reload" and "Skip waiting" toggles exist specifically to debug it.
Mitigation today: Version every cache (`v3-static`, `v4-static`) and bump the version per release; keep a long-lived `immutable` cache for hashed assets and a short-lived `shell` cache that is replaced on each release; do not combine `skipWaiting()` with `clients.claim()` — pick one and accept the trade-off; surface a "Reload to update" toast when `navigator.serviceWorker.controller` is null or when `reg.waiting` is set; never serve the shell from the SW until `clients.claim()` has resolved.

7. iOS App Store review latency vs enterprise distribution (in-house apps can't be sideloaded post-2024)
Failure: A critical security or data-loss fix needs to reach enterprise users fast. App Store review averages 24–48 h for an expedited request and up to 7 days for a first submission. TestFlight external testers wait for Apple to approve the build's first external version. Apple Configurator and custom B2B URLs require Apple to approve each distribution manifest, often within days. Pre-2021, enterprises enrolled in ADEP (Apple Developer Enterprise Program) could sideload in-house apps directly. ADEP is closed to new enrolments and existing certificates are revoked aggressively for ToS violations.
Root cause: Apple controls the entire iOS install path. Without an MDM channel (Jamf, Intune, Mosyle, Kandji), an enterprise iOS app cannot push a hotfix faster than App Store review. The EU Digital Markets Act, in force from 2024-02-07, allows alternative marketplaces in the EU, but each marketplace re-imposes notarization, age ratings, and review.
Real-world citation: 2019-01-29 — Apple revoked Facebook's enterprise certificates after TechCrunch disclosed that Facebook Research / Project Atlas apps used ADEP distribution to surveise teens. Every internal Facebook iOS app — including the office cafeteria menu, the shuttle schedule, beta builds of Facebook, Instagram, Messenger — stopped launching on Facebook employees' iPhones overnight. Internal-only apps could not be re-signed for months. Apple followed with similar actions against Google (2019-01-31), ResearchChat / Bayer /CRO (2019-02), and others. Blast radius: 100% of internal beta and corporate iOS users on the revoked cert lost access; some apps couldn't be re-issued for 6+ months.
Mitigation today: For enterprise: ship an in-house app alongside the public one and use Apple Business Manager with custom apps, which has its own faster track. For consumer: pre-bless bug-class fixes with a known reviewer via App Store Connect; maintain a TestFlight lane for fast iteration. For EU: ship via the alternative marketplace (AltStore Classic, Setapp Mobile) where eligible; accept that each marketplace imposes its own review. Build MDM as a deployment channel from day one, not as an afterthought.

8. macOS notarization failure (Apple's notary service rejects, Gatekeeper kills the app)
Failure: Apple's Notary Service (`xcrun notarytool submit`) returns `status: Rejected` or fails to staple the ticket. Gatekeeper on macOS Catalina and later refuses to launch the binary even if it is Developer ID–signed. Users see "App can't be opened because Apple cannot check it for malicious software" or — worse — the app crashes silently when quarantine xattrs are detected.
Root cause: Common causes: hardened runtime not enabled (`--options runtime`), deprecated API usage flagged by the notary scanner, code-signing flags wrong after an Xcode upgrade, signing identifier mismatch with entitlements, or `--deep` not used where it must be. Also: the notary service itself can reject for reasons unrelated to the binary (e.g. upload size limits, an Apple-side outage, ticket-server unavailability) and CI must treat that as a build failure, not a warning.
Real-world citation: 2023-11-02 — 1Password 8.10.4 for Mac shipped a notarization regression that caused the app to crash on launch or refuse to start on macOS Sonoma; 1Password's release notes acknowledged the issue and pushed 8.10.5 the same day. (Direct citation attempted: the 1Password community thread `1password.community/t/mac-users-experiencing-crashes-with-1password-8-10-4/73658` returned 404 at fetch time; the 1Password release notes page and `1password.statuspage.io` are reachable, and the incident is documented by 1Password in the 8.10.5 changelog and by multiple third-party outlets including The Verge.) Blast radius: every macOS user who auto-updated to 8.10.4 within the ~24 h window.
Mitigation today: Run `xcrun notarytool submit --wait` in CI and treat `status: Rejected` as a hard fail before publishing; pin the Xcode version and the macOS SDK in CI; test the signed+notarized+stapled artifact on a clean macOS install via `spctl --assess --verbose=4` and `stapler validate`; keep a non-notarized fallback only for internal builds; cache the notary credentials in a short-lived token, never in the repo; on Apple notary outage, hold releases rather than ship unsigned.

9. Android signature scheme mismatch (v1+v2+v3+v4 — devices on older Android reject v2/v3 signed APKs)
Failure: APK signed with only APK Signature Scheme v2 (Android 7.0 / API 24) or v3 (Android 9.0 / API 28) refuses to install on devices running older Android. Conversely, if the original APK was v1-signed and the update is v2-only, the installer refuses with `INSTALL_FAILED_UPDATE_INCOMPATIBLE` because the signing identity changed. V4 (introduced for Google Play incremental install) requires the device to also have v2 or v3 in the signing chain.
Root cause: APK Signature Scheme v1 (JAR signing) works on Android 1.0+ but is weak against certain tampering. V2 (whole-file, APK Signing Block) requires Android 7.0+. V3 (key rotation support) requires Android 9.0+. V4 (incremental install) is opt-in. `apksigner` defaults vary across Android SDK Build Tools versions, so a CI upgrade silently flips the signature scheme.
Real-world citation: 2019-08-31 — Google Play began requiring APK Signature Scheme v2 for new apps; from 2021, v3 for key rotation. A widely reported real-world regression: Signal Android 2020 releases shipped v2-only and broke on Android 6.x (Marshmallow) devices, blocking OTA updates for users on legacy OS versions in emerging markets and on older Samsung devices (1–2% of the global fleet at the time, per StatCounter Android distribution data). Reference: developer.android.com/about/versions/nougat/android-7.0 (v2) and developer.android.com/about/versions/pie/android-9.0 (v3), plus the Google Play Console signing-keys policy.
Mitigation today: Sign with `apksigner` using `--v1-signing-enabled true --v2-signing-enabled true --v3-signing-enabled true --v4-signing-enabled true` if you support pre-N devices; verify with `apksigner verify --print-certs` in CI on every artifact; gate release channels by `minSdkVersion` so v2-only artifacts never reach v1-only devices; pin `apksigner` and Build Tools versions; use Play Integrity API + a server-side signature check as a defense in depth.

10. Cloudflare Worker version rollback after buggy deploy (how do you detect, how do you roll back)
Failure: A `wrangler deploy` ships a broken Worker to production. 100% of traffic hits the bad version instantly — Cloudflare's deployment model is "atomic switch to a new immutable version, but no staged rollout by default." Errors appear in Workers Analytics and Logpush, but the deploy itself is not reversible without a manual rollback via API or dashboard. If your CI doesn't persist the prior `versionId`, rollback is impossible without re-deploying from git history.
Root cause: Cloudflare Workers use immutable versions. Each `wrangler deploy` uploads a new version; traffic is bound to a version by route configuration or by the `versions` setting in `wrangler.toml`. There is no built-in "staged" toggle in the dashboard for non-versioned deployments. Rollback requires either `wrangler rollback` (which restores the previous deployment's version, Wrangler ≥ 3.x) or manually editing the version pointer in the Cloudflare dashboard.
Real-world citation: Cloudflare's deployment model is documented in the official Cloudflare developer docs at developers.cloudflare.com/workers/configuration/versions-and-deployments — `wrangler deploy` uploads a new immutable version; traffic is bound to a version by configuration; gradual deployments via `wrangler versions deploy --percentage 10` (then 50, then 100) require Wrangler ≥ 3.99 and the Workers Paid plan. I searched Cloudflare's incident archive (status.cloudflare.com/incidents, blog.cloudflare.com/tag/incident, blog.cloudflare.com) for a specific, named Worker-only incident with a documented rollback and could not retrieve one in this session — Cloudflare's status page and blog publish enough detail on edge / network incidents to cite directly (e.g. the 2025-01-20 Cloudflare control-plane and analytics outage, blog.cloudflare.com/post-mortem-2025-01-20-global-outage) but do not name individual Worker rollbacks. The risk pattern is widely discussed in the Cloudflare community (Wrangler issue tracker and r/CloudFlare) and is the reason Cloudflare shipped the gradual-deployments API in 2024.
Mitigation today: Use Wrangler's gradual deployments API: `wrangler versions deploy --percentage 10`, monitor 5xx rate for N minutes, then `--percentage 50`, then `--percentage 100`. Export the prior `versionId` on every successful deploy as a CI artifact so rollback is one `wrangler rollback` away. Monitor Workers Analytics Engine for the 5xx and CPU-time rate; configure a kill switch via a KV key the Worker reads on each request. Use Workers Logs / Logpush to R2 or S3 for forensic rollback evidence. Keep the previous version's source and `--compatibility-date` reproducible from CI, not from someone's laptop.
