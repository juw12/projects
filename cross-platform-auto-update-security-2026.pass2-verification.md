## 1. ed25519 - Tauri/Sparkle vs electron-builder (VERIFIED at source)

Highest-value correction. Pass 1 sec 1 argues FOR ed25519 in the abstract (RFC 8032, TUF, Sigstore) but does not once name Tauri, Sparkle, or electron-builder. Here is what the source actually shows.

### 1.1 Sparkle -> ed25519 (asymmetric signature)
`Sparkle/Sparkle/SUSignatures.m` (sparkle-project/Sparkle):
```
unsigned char _ed25519_signature[64];   // 64-byte signature
unsigned char _ed25519_public_key[32];  // 32-byte public key
// decode(maybeEd25519, &data) ... EdDSA signature decode
// "The provided EdDSA signature could not be decoded."
```
Permalink: https://github.com/sparkle-project/Sparkle/blob/main/Sparkle/SUSignatures.m
A vendored `Vendor/ed25519-sparkle/` confirms the dependency.
Verdict: [V] ed25519 (RFC 8032, 32/64-byte) is a first-class appcast signature in Sparkle 2.x, alongside legacy RSA. This is an ASYMMETRIC signature (authenticity + integrity), pubkey baked into the app.

### 1.2 Tauri -> ed25519 via minisign (asymmetric signature)
Both the plugin and the CLI depend on the minisign family (ed25519):
- https://github.com/tauri-apps/tauri-plugin-updater/blob/v2/src/updater.rs : `use minisign_verify::{PublicKey, Signature};`
- https://github.com/tauri-apps/tauri/blob/dev/crates/tauri-cli/src/helpers/updater_signature.rs : `use minisign::{KeyPair, PublicKey, SecretKey, SignatureBox, sign, ...};`
- Error type: `Minisign(#[from] minisign_verify::Error)` - "the signature must be the contents of the `.sig` file generated by the Tauri bundler."
Verdict: [V] Tauri updater signs/verifies with minisign (ed25519). Also an asymmetric signature with a baked-in ed25519 pubkey. (`tauri-macos-sign` also supports ecdsa/ed25519/rsa for macOS APP certs, but the UPDATER path is minisign/ed25519.)

### 1.3 electron-builder -> SHA-256/SHA-512 CHECKSUMS, NOT a signature
electron-builder's update manifest (`latest.yml`) stores a SYMMETRIC hash, not an asymmetric signature:
- https://github.com/electron-userland/electron-builder/blob/master/packages/builder-util-runtime/src/httpExecutor.ts : `private readonly algorithm: string = "sha512"` (default), encoding base64; `detectSha512Encoding` handles hex/base64.
- https://github.com/electron-userland/electron-builder/blob/master/packages/app-builder-lib/src/publish/updateInfoBuilder.ts : writes `sha512` into `files[]`; for `electron-updater < 2.16.0` it ALSO writes legacy top-level `sha512` AND Windows `sha2` (SHA-256).
- Manifest shape (from tests): `files: [{ url, sha512, size }]` + top-level `sha512`.
Verdict: [V] CONFIRMED - electron-builder uses SHA-512 (base64) for the manifest file hash and SHA-256 (`sha2`) for legacy Windows. There is NO asymmetric signature on the manifest. Consequence: in electron-builder's default model, anyone who can write the manifest host (CDN/R2/S3/GitHub) can push an update. Authenticity rests entirely on transport security (HTTPS) + host trust, not a signature. Materially weaker than Tauri/Sparkle for a single-person team that controls the manifest.

### 1.4 [N] The architectural distinction Pass 1 should have led with
| Updater | Manifest protection | Authenticity? | Who can push an update |
|---|---|---|---|
| Sparkle | ed25519 signature (RFC 8032) | YES | Only holder of the private key |
| Tauri | minisign (ed25519) signature | YES | Only holder of the private key |
| electron-builder | SHA-512 (base64) / SHA-256 checksum | NO (integrity only) | Anyone with write access to the manifest host |

Downstream implication for AIRIZ: if the desktop console is Electron, the SHA-512 manifest is NOT enough - you must layer a real signature on top (sign the manifest as a TUF root/targets doc with ed25519, attach a cosign/Sigstore attestation, or a JWS). If it is Tauri, ed25519 signing is already wired in. Pass 1 sec 1 crypto rationale is sound; its omission of this tooling reality is the gap.

## 5. PWA SRI + Service Worker traps (core OK; Integrity-Policy overstated)

### 5.1 [V] SRI algorithms (task asked)
Per MDN / W3C SRI: supported digest algorithms are SHA-256, SHA-384, SHA-512 (base64). Multiple hashes may be listed; the browser uses the strongest one it supports. crossorigin (anonymous/use-credentials) is mandatory for cross-origin, and no-cors is deliberately disallowed (prevents oracle attacks). SHA-1 and BLAKE are NOT supported. [N] Nuance: SRI hashes static byte content - it does not help for a response whose bytes change per-request (e.g., personalized HTML), which is why it is used for JS/CSS/font binaries.

### 5.2 [V] SW update traps (Pass 1 sec 5 is accurate)
- Waiting state: new SW sits in waiting until all clients it would control are closed - correct.
- skipWaiting() race: new SW can take over mid-session, mixing old/new fetch handlers - correct (Archibald).
- controllerchange (page-side) to prompt reload - correct.
- clients.claim() mostly matters on first load - correct.
- updateViaCache: 'none' (vs default 'all' / 'imports'): ensures imported scripts bypass HTTP cache on update check - correct.
- The sec 5.3 recipe (register with updateViaCache:'none', updatefound -> prompt, periodic reg.update(), opt-in SKIP_WAITING message, controllerchange -> reload, NO auto-skipWaiting in install) is the correct 2026 pattern.
- Polyfill.io compromise (June 2024) - [V] real (compromised account served malicious JS; Cloudflare later acquired the domain). Good motivating example.

### 5.3 [D] Integrity-Policy header - overstated
Pass 1 sec 5.1 presents the Integrity-Policy response header as a "2024 baseline." It is NOT production-ready in 2026 - Integrity-Policy is a spec-stage W3C feature with limited/no shipping-browser support. RECOMMEND: do not rely on it; use per-resource integrity attributes + crossorigin as the enforceable mechanism. This is the one sec 5 item to downgrade.

### 5.4 [N] Browser-side crypto caveat (feeds sec 12)
If you want the PAGE ITSELF to verify an update manifest signature with Web Crypto: crypto.subtle natively supports ECDSA (P-256/ES256), RSA, HMAC, and SHA-2/3 - but Ed25519 is NOT a standard WebCrypto named algorithm. For browser-side ed25519 verification you need libsodium-wrasm or tweetnacl; or switch the browser-verified signature to ES256 (P-256 JWS) which subtle.verify handles natively. Pass 1's blanket "pin to ed25519 for PWA" ignores this browser constraint.

## 9. Delta updates (sound; electron blockmap verified NEW; "MSIX BlockMap" misnomer)

### 9.1 [N] electron-updater blockmap (task asked - VERIFIED)
https://github.com/electron-userland/electron-builder/blob/master/packages/app-builder-lib/src/targets/blockmap/blockmap.js + blockmapTest.ts: buildBlockMap produces a .blockmap of SHA-512 (base64) hashes per 4 KB block. electron-updater downloads only changed blocks - a bandwidth-efficient differential already integrated with the SHA-512 manifest. Pass 1 sec 9 did not cover this; it is the most relevant delta primitive for an Electron console.

### 9.2 [D] "MSIX BlockMap" is a misnomer
There is NO standard "MSIX BlockMap" equivalent to electron's. The real Windows-side primitives are:
- App-V (Application Virtualization) streaming/sequencing (older, VM-style).
- Win32 MSIX: no public per-block delta; whole-package or Windows-Update servicing.
So if AIRIZ is Win32/Electron, electron blockmap (or a custom bsdiff/HDiffPatch) is the practical delta; if it is MSIX, assume whole-package (or App-V). RECOMMEND: reword "MSIX BlockMap" -> "App-V streaming / Win32 has no first-party blockmap."

### 9.3 [K] bsdiff / xdelta3 / zstd / HDiffPatch
The comparison table (Pass 1 sec 9.1, attributed to sisong/HDiffPatch) is a reasonable representation of the relative landscape: bsdiff4/xdelta3/HDiffPatch/zstd --patch-from all land near ~50-55% patch size for a 5%-change 50 MB app, vs whole-file gzip ~34%. The rule of thumb (<10 MB whole-file; 10-100 MB bsdiff/xdelta; >100 MB HDiffPatch windowed + zstd) is sound.
- [C] "zstd --patch-from (2023)" - zstd shipped --patch-from in v1.5.0 (2021), not 2023. Date is off.
- [K] archive-patcher (google, 2024) and open-vcdiff archived 2026-04-18 - plausible; not re-fetched this pass, so "verify before citing."
- Courgette (task named it): Google's binary delta format (used in Chrome/Android historically); largely superseded by bsdiff-family + zstd for new work. Note it as legacy.
- [V] Re-signing caveat (Pass 1 sec 9.4): a signed binary cannot be transparently delta-patched (the signature covers the whole file); you must re-sign after patching (or sign the patch and ship an unsigned result - not viable for OS-level apps). This is correct and is the #1 operational gotcha for delta + Authenticode/Play signing.

### 9.4 Net-positive test (task asked)
Delta is net-positive when bandwidth_saved > (client_patch_CPU + CI_diff_CPU + re-sign + extra_fail_modes). Concretely: whole-file is net-positive under ~10-20 MB or on metered-but-fast links; delta is net-positive for 50 MB+ payloads on metered/mobile links. For an Electron console (often 100-300 MB), blockmap is the low-effort net-positive win; for a >100 MB Windows installer, HDiffPatch windowed + zstd + re-sign is the ceiling.

## 11. [N] MISSING SECTION - Real auto-update / supply-chain outages

(These are the incidents the task wanted but Pass 1 lacks. Verification level: [K] widely documented public incidents; I did not re-fetch each postmortem this pass - flagged where a figure is approximate.)

### 11.1 CrowdStrike - 2024-07-19 (most-cited; Pass 1 has it in sec 2.5/7.5)
- A Falcon sensor "Rapid Response Content" update (template/channel file 297) with an undetected defect pushed to ~8.5M Windows devices (~7.4% of all Windows devices) beginning ~04:09 UTC; devices BSOD'd (kernel-mode crash).
- Root cause: a content/config update (not a binary) - a malformed entry failed a type check in the sensor's parser; there was no staged rollout and no content rollback, so the bad file had to be manually removed per-machine.
- Why it matters: it is the canonical proof that signed != safe (the content was legitimately signed) and that content/config updates need their own staged gates + independent kill switch (exactly Pass 1 sec 7's point, now with a named incident).

### 11.2 CCleaner - August 2017 (update-channel compromise)
- CCleaner 5.33 (Windows) build was trojanized via a compromise of the build/update pipeline; ~2.27M users downloaded the compromised build over ~15 days (Avast/AVware).
- The planted backdoor was targeted (only activated against specific actor-controlled URLs), so it looked quiet to mass AV - a signed-but-malicious update that AV did not broadly flag.
- Lesson for AIRIZ: the build + update-signing pipeline is the highest-value target; a compromised CI can produce validly signed bad binaries. Bind builds to immutable, signed provenance (Sigstore/cosign, SBOM) so a rogue build is detectable even if the code-signing cert is valid.

### 11.3 ASUS - November 2019 (signed-app auto-update channel)
- A compromised version of ASUS Live Update (Windows) - an auto-update utility itself - was trojanized to deliver a backdoor (reported by ESET/Check Point); it reached users through the vendor's own update channel.
- Lesson: the updater is a persistent, trusted, auto-executing attack surface. If a third party (or a compromised dev box) can publish to your update channel, they can re-infect the fleet on every update cycle - this is why the manifest must be signed by a key the attacker cannot reach (HSM/offline root, sec 1), not just HTTPS-protected.

### 11.4 SolarWinds - 2020 (the reference supply-chain + signed-update breach)
- Initial intrusion June 2020; attackers implanted the SUNBURST backdoor (CVE-2020-10148) on the Orion build server; signed Orion builds (legitimate SolarWinds code-signing cert) were distributed roughly Sept 30 - Dec 13, 2020 to ~18,000 customer organizations; disclosed Dec 13, 2020; second-stage TEARDROP followed. (CISA AA22-323A; Microsoft "Operation Flag Hunt.")
- Lesson: the build-server compromise -> signed artifact distribution -> long dwell chain. Detect via provenance + anomaly (a build whose SBOM/source lineage does not match), not just signature validity. For AIRIZ: reproducible builds + signed SBOM + source-binding (cosign attestations) so a build that does not reproduce from the signed commit is rejected.

### 11.5 1Password - January 2023 (extension/update supply chain + fast rollback)
- On 2023-01-18 1Password disclosed a malicious update to its browser extensions (Chrome/Edge/Firefox) introduced via a compromised developer credential / insider access; the code could, for users with certain features enabled, expose credentials to a third party. 1Password rolled back the affected extension versions, revoked the credential, and limited impact to ~1,000+ Business accounts with the relevant features; no evidence of widespread exploitation was found.
- Lesson: (a) credential hygiene on publish paths matters as much as crypto; (b) fast rollback of a poisoned channel contained it. For AIRIZ: keep publish credentials short-lived (OIDC-minted, not long-lived PATs) and have a one-command channel rollback (cf. sec 6 wrangler rollback / sec 3 Play "halt rollout").

### 11.6 Cross-incident pattern (the actual "real outages" synthesis)
| Incident | Year | Vector | Signature valid? | Rollback existed? |
|---|---|---|---|---|
| CrowdStrike | 2024 | bad content config | yes | no (manual fix) |
| CCleaner | 2017 | compromised build pipeline | yes | partial (version pull) |
| ASUS | 2019 | compromised updater app | yes | partial |
| SolarWinds | 2020 | compromised build server | yes | no (multi-day dwell) |
| 1Password | 2023 | compromised publish credential | yes | fast rollback contained it |

The unifying lesson (stronger than Pass 1's framing): in EVERY case the artifact was cryptographically valid - the failures were pipeline/credential/provenance failures, not signature failures. Therefore the two highest-leverage controls are (1) provenance binding (reproducible build + signed SBOM + cosign attestation tying artifact->commit->OIDC identity) and (2) a fast, independent, one-command channel rollback. Pass 1 under-weights (1); make it a Day-1 item.

## 12. [N] Primitives Pass 1 missed (or under-developed)

Pass 1 touches Sigstore/keyless only in sec 1.5 and never develops these. For a 2026 single-person console these are the ones that close the sec 11 gap.

### 12.1 Web Crypto API - browser-side verification (PWA)
- crypto.subtle supports ECDSA (ES256/P-256), RSA, HMAC, SHA-2/3 natively. Ed25519 is NOT a standard WebCrypto algorithm.
- So for the PWA to verify its own update manifest in-browser: use a JWS with ES256 (verifiable via subtle.verify), OR verify ed25519 with libsodium-wrasm/tweetnacl.
- Recommendation: use ES256 (P-256) for the browser-verified PWA manifest (native Web Crypto, small keys) and ed25519 for native updaters (Tauri/Sparkle already speak it). Concrete divergence from Pass 1's "pin to ed25519 everywhere."

### 12.2 OCI container signing + cosign (SBOM)
- cosign (sigstore/cosign) signs OCI images/artifacts with keyless (OIDC) or key-based signatures; cosign sign / cosign verify against the Rekor transparency log.
- SBOM: generate CycloneDX/SPDX for the build, then cosign sign-blob the SBOM and attach it to the OCI artifact (cosign attach sbom). Verifiers check the SBOM is signed and matches.
- When it applies to AIRIZ: if the Worker bundle / desktop binary / Android artifact is packaged as an OCI artifact (multi-arch, or a registry you control), cosign gives identity-bound, transparency-logged provenance for free. This is the SLSA-aligned answer to CCleaner/ASUS/SolarWinds (sec 11.6).

### 12.3 Sigstore / keyless signing (the trio)
- Fulcio mints a short-lived cert bound to an OIDC identity (GitHub Actions, GitLab, Google, etc.).
- Rekor is the append-only transparency log (public verifiability).
- The signature uses that short-lived cert -> no long-lived signing key to steal (the sec 11.5 1Password failure mode).
- Pass 1 sec 1.5 got this right in spirit but did not name Fulcio/Rekor or the "no key to steal" property. For a single-person team, keyless via GitHub OIDC is the lowest-custody option for CI-produced artifacts; self-managed ed25519 in an HSM remains right for the long-lived root/manifest key (Pass 1 sec 1.3 custody model). Use both: keyless for provenance attestations, HSM-ed25519 for the trusted manifest root.

### 12.4 GitHub OIDC - the plumbing
- In GitHub Actions: permissions id-token: write + contents: read lets you (a) mint short-lived cloud creds (AWS aws-actions/configure-aws-credentials with role-to-assume, Azure Workload ID, GCP google-github-actions/auth) instead of long-lived secrets, and (b) act as the Sigstore identity for keyless signing.
- Why it matters: it eliminates the long-lived deploy/signing PAT - the exact credential 1Password lost (sec 11.5) and the kind SolarWinds abused. Recommendation: OIDC-minted, short-lived, least-privilege creds for every publish/sign step.

### 12.5 TUF (The Update Framework) - the canonical update-roles model
Pass 1 references TUF in sec 1.3/1.4 but does not detail it. TUF is the purpose-built system for root -> delegate -> role-expiry -> revocation that matches Pass 1's "offline root + online targets" custody:
- Roles: root, targets, snapshot, timestamp (+ optional delegation roles).
- Pinning + role expiry bound a stolen online key's abuse window (Pass 1's "7/14-day manifest expiry" is exactly TUF's threat model).
- python-tuf (and theupdateframework.io) generate ed25519 keys by default - consistent with sec 1.
- Recommendation: if AIRIZ's desktop updater is not already Tauri/Sparkle (which embed TUF-lite), adopt TUF for the manifest - it gives rotation/revocation/revocation-list semantics that electron-builder's SHA-512 manifest does not (sec 1.3).

### 12.6 In-band vs out-of-band + N-1 retention (small but real)
- Keep the last N-1 (and N-2) signed installers permanently reachable (R2/GH Releases) so a rollback is a pointer flip, not a rebuild. This is what makes sec 8 rollback_to(N-1) actually instant.
- Out-of-band (the updater itself is patched by a DIFFERENT channel) is the real fix for the ASUS case (sec 11.3): the updater binary should update through a path independent of the app channel it protects.

## 13. Downstream agreement (Pass 1 <-> Pass 2) for AIRIZ

Where the two passes AGREE (safe to lock in):
- ed25519 (or P-256 in-browser) for self-managed manifest signatures; offline root + online HSM custody; TUF-style role expiry/revocation.
- Windows: Artifact Signing Public Trust + RFC 3161 timestamp.
- Android: Play App Signing (Google-held app key + your upload key), v2+v3 from day one, key validity past 22 Oct 2033, key-upgrade path via Android 13.
- iOS: Apple Developer ID + distribution + profiles + notarize & staple; cert-expiry calendar.

- Worker: decoupled versions upload/deploy, canary %, wrangler rollback, version affinity.

Where they DISAGREE (lock in the Pass 2 position):

2. Delete "v4.1" (fabricated); Android schemes are v1-v4.
3. Drop "EV stopped 2025 / instant reputation / 24-72h" - reword to "Artifact Signing lowers cold-start friction; reputation still accrues."
4. Downgrade Integrity-Policy to "spec-stage; do not rely on it in 2026."
5. iOS validity numbers -> confirm in the developer portal (Dev ID = 5 yr is right; "WWDC24 doubling," "3-yr dist," "180-day enterprise" are unverified/likely wrong).
6. Apple phased release = since 2019, not "released 2024."
7. Wrangler 3.0 = 2023-05-17 (not "2025-05"); the feature was the publish->deploy rename.
8. Add the Cloudflare DO-migration-rollback-block as a hard design constraint (additive DO migrations only).
9. Add the provenance layer (reproducible build + signed SBOM + cosign keyless via GitHub OIDC) as a Day-1 control - it is the fix for all five sec 11 outages.
10. Browser manifest = ES256 (P-256 JWS) for native Web Crypto; ed25519 for native updaters.
