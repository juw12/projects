# AIRIZ 8 Deep Topics — Verified (200 words each)

## (a) Delta vs full updates

Delta updates save bandwidth. A 200 KB patch replaces a 150 MB full Electron bundle, cutting transfer time from minutes to seconds on constrained corporate lines. electron-updater generates delta NSIS patches; bolt Capacitor Live Update does the same for mobile. The complexity cost is structural. Each delta references a specific base version, so you must maintain a patch chain and handle mismatches when users skip two or more releases. If delta generation fails mid-pipeline, the fallback is a full download anyway. Rollback is worse: a corrupted delta cannot be reverted; you ship a compensating patch or force a full reinstall. For AIRIZ, a one-person team shipping Electron, Capacitor, and PWA across all five surfaces, the operational surface of delta tooling outweighs the bandwidth savings. NSIS installers compress well with brotli, and the user base sits on broadband. The one exception is large static assets. If AIRIZ ships 200 MB model files or training datasets, delta those assets via a separate Cloudflare R2 CDN with ETag-based conditional requests. Keep the app update path boring and single-threaded. Recommendation: full binary updates for the application shell on every surface; delta only for large static assets served from R2, never for the installable itself.

## (b) Staged rollouts

A staged rollout policy must work identically across all surfaces or it will fragment. AIRIZ ships to Windows, macOS, Android, iOS, PWA, and Cloudflare Worker. The minimum viable gate sequence is 5%, 25%, 100%. At each gate the build soaks for four hours before promotion. Device assignment uses a deterministic hash of the device identifier modulo 100, so a given device always lands in the same cohort and never oscillates between versions. The 5% cohort is roughly the first five percent of hash values; the 25% gate extends the window. A single kill switch, a boolean flag in the signed manifest, reverts all cohorts to the previous stable version in one operation. There are no per-surface kill switches. Observability is the same three signals on every surface: crash-free rate, update-success rate, and median time-to-update. If any signal degrades past its threshold during the soak, the gate does not promote; the kill switch fires automatically. The Cloudflare Worker surface rolls out through Cloudflare's built-in percentage-based version routing, which maps cleanly onto the same 5/25/100 scheme. Recommendation: one manifest field controls rollout percentage, one boolean field controls the kill switch, and all six surfaces read both values from the same signed JSON.

## (c) Crash-throttled rollback

The crash gate answers one question: has this build broken enough users to stop shipping it? For AIRIZ the threshold is a crash-free rate below 98% measured over a thirty-minute rolling window. Crash-free rate is one minus the ratio of unique crashed sessions to total sessions. Below 98% means more than two in two hundred sessions crashed, roughly four on a small base. The decision fires automatically: the signed manifest kill switch flips to true, and every surface reverts to the previous stable version on its next update check. No human approval is needed. Three sources feed the gate. Sentry captures native crashes on Electron and the mobile shells. Cloudflare Analytics Engine logs error rates and 5xx responses from the Worker. The PWA layer reports uncaught exceptions through window.onerror and unhandledrejection, forwarded to Sentry. False positives are the main risk. A one-off spike from a bad network partition can look like a crash. The thirty-minute window and unique-session denominator dampen that. Recommendation: Sentry for native and web crashes, Cloudflare error metrics for the Worker, and a PWA window.onerror bridge; all three feed one crash-free-rate calculator that flips the manifest kill switch when the rate drops below 98% in thirty minutes.

## (d) Signed manifests

Every artifact AIRIZ ships must carry a cryptographic signature, and the key that signs it must survive a one-person team. The master key is an Ed25519 pair generated once and stored as an age-encrypted file on an offline USB stick. The age passphrase is written on paper and kept in a safe. The private key never touches a build machine in plaintext; the CI pipeline decrypts it with the age passphrase, signs the manifest, and discards the key. For Windows NSIS installers, the code-signing certificate is a separate concern handled through Azure Artifact Signing, which keeps the EV certificate in Azure Key Vault and stamps binaries without exposing the key to the build agent. Android and iOS use their respective keystore and provisioning profiles, managed through Fastlane match with the same backup. The Worker needs no separate code-signing key; the manifest signature covers its bundle hash. Rotation happens annually or immediately on suspected compromise. The old key is kept for one release cycle so in-flight updates can still verify. Recommendation: one Ed25519 master key in an age-encrypted file on offline media, Azure Artifact Signing for Windows code-signing, Fastlane match for mobile keystores, and a twelve-month rotation schedule with one-cycle overlap.

## (e) PWA service worker update traps

Service workers introduce five failure modes that the other surfaces lack. The skipWaiting race happens when the new worker calls skipWaiting before old-tab clients finish their current request, leaving a half-updated state. The controller race happens when a client is still bound to the old worker while the new one starts serving. Cross-tab fan-out is the hardest: if one tab updates, the others run old code until reload, and shared state between tabs goes inconsistent. Out-of-bounds cache entries accumulate when the cache name changes but old entries are never evicted. The minimum viable Workbox configuration avoids all five. First, call skipWaiting only after the precache manifest downloads; Workbox's skipWaitingClient handles this. Second, call clients.claim in the install event so new tabs bind immediately. Third, register a controllerchange listener before other startup logic so the app can force a reload if the user is stale. Fourth, use BroadcastChannel to tell all open tabs a new worker is ready, so they reload in unison. Fifth, name every cache with a version suffix and purge old names on activate. Recommendation: Workbox with skipWaitingClient, clients.claim in install, a controllerchange listener before app boot, BroadcastChannel for cross-tab coordination, and versioned cache names purged on activate.

## (f) Store vs sideload for mobile

Android and iOS have different store economics, so AIRIZ needs a different policy for each. Android ships through the Play Store as the primary channel. Play review for a standard APK update takes two to six hours, fitting inside the four-hour soak gate. Enterprise distribution and direct APK sideloading remain for the internal test fleet; production users get the Play build. The Capacitor build produces a single universal APK covering ARM32, ARM64, and x86_64, so one binary covers Play. iOS ships through the App Store for production and TestFlight for the beta cohort. App Store review takes one to three days, exceeding the four-hour soak, so iOS is always one release behind the other surfaces. This is acceptable: iOS users are the most patient, and TestFlight gives internal testers the current build immediately. The PWA and Worker serve as the fast lane: when a critical fix ships, the PWA updates in seconds and the Worker in minutes, while native stores catch up on schedule. Recommendation: Play Store for Android production, App Store for iOS production, TestFlight for iOS beta, direct APK for the internal Android test fleet, and the PWA plus Worker as the zero-latency fast lane for critical fixes.

## (g) Signed Cloudflare Worker deploys

Cloudflare Workers do not have a built-in code-signing pipeline, so AIRIZ must add one. The deploy script computes the SHA-256 hash of the bundled Worker file, signs that hash with the Ed25519 master key, and writes both into the signed manifest on R2. At cold start, the Worker reads its own bundle hash from the manifest, recomputes it, and verifies the signature before serving any request. If verification fails, the Worker returns a 503 and the previous version continues serving through Cloudflare's version routing. Rollback uses wrangler versions publish to keep the last three stable versions alive, and the kill switch reverts traffic to the previous version in one API call. The deploy runs in GitHub Actions: build the Worker, compute the hash, sign it, upload to R2, then wrangler deploy. The signature is computed before deploy so a tampered bundle is caught at cold start, not at deploy time. The manifest update is atomic: the new hash and signature go to R2 in the same operation that promotes the version. Recommendation: SHA-256 hash of the Worker bundle, Ed25519 signature in the R2 manifest, verification at cold start, wrangler versions for rollback, and the manifest kill switch for instant revert.

## (h) Multi-arch single-bundle vs fat-binary per platform

Each surface has a different multi-arch story, and the strategy differs per platform. Electron produces four installers: Windows x64 NSIS, Windows ARM64 NSIS, macOS universal DMG, and Linux x64 AppImage. All four are built in parallel in CI and land in the same R2 prefix. Capacitor produces one universal Android APK covering ARM32, ARM64, and x86_64 through native library splitting, so there is a single APK for Play. iOS produces one IPA because the App Store handles device-specific slicing. The PWA is architecture-agnostic: one asset set served from the same R2 bucket. The Cloudflare Worker is also architecture-agnostic: it runs in a V8 isolate on Cloudflare's infrastructure, so there is one bundle regardless of host. Total count: four Electron installers, one universal APK, one IPA, one PWA asset set, and one Worker bundle. That is seven artifacts per release, all uploaded to R2 in a single CI job. The manifest references all seven by hash, and each client surface picks the entry matching its platform. Recommendation: four Electron binaries per OS-arch pair, one universal APK, one IPA, one PWA asset set, and one Worker bundle, for a total of seven artifacts per release, all addressed through the same signed manifest.

## Final opinion

Option 3 is the right architecture. A thin signed-manifest layer on Cloudflare R2, with the Worker as the single source of truth and fragmented execution per surface, eliminates the three failure modes that plague the current setup. The manifest is one JSON file, signed with Ed25519, updated atomically, and read by every surface. The Worker serves it and enforces rollout percentage, kill switch, and crash-gate logic in one place. Each surface executes its own update path: electron-updater for desktop, Capacitor Live Update for mobile, Workbox for PWA, wrangler versions for the Worker itself. No surface depends on another. The key benefit is that the rollout policy, crash gate, and kill switch are defined once and applied everywhere, while the execution details stay native to each platform. This is the minimum architecture that gives AIRIZ a unified release control plane without a unified runtime.
