## 1. ed25519 Manifest Signatures

### 2026 Best-Practice Summary

Every serious cross-platform updater in 2026 converges on Ed25519 (EdDSA) for update manifest and artifact signing. Tauri 2.x uses minisign-format Ed25519 keys generated by `tauri signer generate`; Sparkle 2.x mandates EdDSA (deprecating the older DSA scheme since v1.21); Go's sumdb transparency log signs commits with a single key type: Ed25519, algorithm identifier 1. The RFC 8032 specification defines the curve, the deterministic signing process (no random nonce - a security feature that makes it immune to the Sony PS3-style nonce-reuse attacks that broke ECDSA), and the 64-byte signature / 32-byte key format.

The performance case is overwhelming. On an Apple M4 Max, Ed25519 signs at ~243K ops/s (4.12 us) and verifies at similar rates. RSA-2048 signs at ~800 ops/s (1.2 ms) - a 300x penalty for the single operation that happens at build time. On the verification side (the one that matters at runtime on every client), Ed25519 verifies in ~45 us vs RSA-2048 at ~30 us - RSA is actually slightly faster to verify, but the signature is 4x larger (256 bytes vs 64 bytes), which matters when the signature is embedded in a JSON manifest fetched over the wire. The signature size difference (64 vs 256 bytes) is the more practical advantage: a Tauri updater manifest with an ed25519 signature stays small enough to inline in the JSON response rather than requiring a separate fetch.

Key handling in 2026 is a solved problem. The **minisign** format (used by Tauri, OpenBSD's `signify`, and `cargo-binstall`) stores the private key encrypted with scryptsalsa208sha256 (OPS_LIMIT_SENSITIVE / MEM_LIMIT_SENSITIVE) and includes a 32-byte Blake2b-512 checksum. The **age** format (FiloSottile/age) is the de-facto standard for encrypting the minisign private key at rest when it's committed to a repo as `minisign.key.age` - as seen in the jdx/mise project. Tauri 2.10+ now enforces `0600` permissions on generated keys and rejects filenames containing tabs or newlines (which would corrupt the trusted comment). The trusted comment feature in minisign is the 2025-2026 innovation: it binds the app version into the signature itself, so the updater can reject a manifest that pairs a version number with a different artifact. Tauri 2.12+ added `requireSignedVersion` to enforce this.

### Minimum Viable Implementation (Week 1)

1. **Tauri/Electron**: Run `tauri signer generate -w ~/.tauri/app.key --password ""` once. Embed the public key in `tauri.conf.json`. Set `TAURI_SIGNING_PRIVATE_KEY` in CI. Ship full artifacts (not delta) for the first 3 releases.
2. **macOS (Sparkle)**: Use `generate_appcast` with EdDSA keys in the Keychain. Ship `sparkle:edSignature` in the appcast. Do NOT ship DSA signatures.
3. **PWA / Worker**: No signature needed at the manifest level if you're behind Cloudflare (TLS terminates, WAF in front). The Worker code IS the update mechanism - its integrity is handled by Cloudflare's deploy pipeline.
4. **Key storage**: Encrypt the private key with `age` and store the `.age` file in your CI secrets. Never commit the raw private key.

### Common Pitfalls

- **Losing the private key = permanent loss of ability to update existing installs.** The public key is baked into the binary. There is no recovery path short of asking users to reinstall.
- **The manifest is NOT signed in Tauri 2.x.** Only the artifact is signed. An attacker who controls the update endpoint can serve a genuinely-signed *older* release. Mitigation: enforce `requireSignedVersion` (Tauri 2.12+) and add a downgrade guard (reject any version below the current).
- **Sparkle 2.6.4 fixed a critical bypass** where an attacker could replace a signed update with a different payload. Ensure you're on Sparkle >= 2.6.4.
- **DSA is dead.** If you're migrating from Sparkle 1.x, ship both DSA + EdDSA keys in one transition update, then drop DSA.
- **minisign trusted comment** (new in 2025) is the anti-downgrade mechanism. If you're not on Tauri 2.12+, implement your own version check.

## 2. Windows EV Certificate + SmartScreen Reputation

### 2026 Best-Practice Summary

The single most important fact about Windows code signing in 2026: **EV certificates no longer bypass SmartScreen.** Microsoft removed the EV instant-reputation behavior in 2024. An EV-signed file now builds reputation exactly like an OV-signed file - through accumulated download counts from a diverse audience. Microsoft's own documentation states: "Paying the EV premium solely to avoid SmartScreen warnings is no longer justified."

SmartScreen evaluates two independent signals: (1) **publisher reputation** - is the file signed with a certificate from a known, trusted publisher? And (2) **file hash reputation** - has this specific file been downloaded many times without malicious behavior reports? A newly-compiled binary, even signed with a 5-year-old certificate, may still show a SmartScreen warning on first download if its hash has no history. Over time, as clean downloads accumulate, the warning disappears. Microsoft states there is no exact threshold but it "can take several weeks and hundreds of clean installs from a wide audience."

**The practical 2026 landscape for a one-person team:**

| Option | Cost/year | SmartScreen | Notes |
|--------|-----------|-------------|-------|
| Azure Artifact Signing | ~120 | Same as OV (reputation builds) | Best value for US/CA/UK/EU orgs |
| SSL.com OV | 129 | Reputation builds | Cheapest traditional OV |
| DigiCert OV | 696 | Reputation builds | Enterprise-grade |
| DigiCert EV | 972 | Same as OV (since 2024) | Only for kernel drivers |
| Self-signed | 0 | Blocks install | Dev/testing only |

For update-in-place (Squirrel, Tauri updater, Electron autoUpdater), the SmartScreen story is different from first-install. When your app auto-updates itself, the new binary is typically executed in the context of the already-trusted application process. SmartScreen's file-reputation check applies primarily to files downloaded from the internet and executed for the first time. An updater that replaces files in `C:\Program Files` under UAC elevation is subject to different (or no) SmartScreen gating in practice. This is why apps like VS Code, Slack, and Discord can update seamlessly without users seeing SmartScreen warnings on every update.

**Real-world reputation timeline** (from Microsoft support responses and community reports):
- First release with a new cert: 2-6 weeks until SmartScreen warnings stop
- Subsequent updates with the same cert: faster (days to 2 weeks) if the publisher already has reputation
- Certificate renewal: reputation partially transfers if the subject name matches; expect 2-4 weeks of warnings
- Different CA, same org: reputation does NOT transfer; start from scratch

**Sources**:
- Microsoft SmartScreen reputation docs: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation
- Microsoft code signing options: https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options
- Eric Law's "Best Practices for SmartScreen AppRep" (2024-11): https://textslashplain.com/2024/11/15/best-practices-for-smartscreen-apprep/
- OneSigner cert price comparison 2026: https://onesign.sg/blog/industry-news/code-signing-certificate-prices-2026
- GeoCerts (DigiCert) OV vs EV comparison: https://www.geocerts.com/docs/code-signing/get-started/choose-certificate/
- Sectigo SmartScreen FAQ: https://www.sectigo.com/faqs/detail/MS-SmartScreen-and-Application-Reputation
- StackExchange: transferring reputation on cert renewal: https://security.stackexchange.com/questions/222140/transferring-microsoft-smartscreen-reputation-to-renewed-certificate

### Minimum Viable Implementation (Week 1)

1. **Get an OV cert from SSL.com (129/yr)** or **Azure Artifact Signing (9.99/mo)**. Do NOT buy EV - it's a waste of money in 2026 for SmartScreen purposes.
2. **Sign your installer AND your updater artifacts** with the same cert. Consistency is how reputation accumulates.
3. **Use `signtool sign /fd sha256 /tr http://timestamp.digicert.com`** for timestamping. Timestamps ensure your signature remains valid after cert expiry.
4. **For Electron/Squirrel auto-updates**: the updater downloads the new app zip, verifies the ed25519 signature (from Topic 1), and replaces files in-place. SmartScreen typically does NOT re-prompt for in-place updates of already-running apps.
5. **For the first release**: expect SmartScreen warnings. Include a README or onboarding page that tells users "Click More Info - Run Anyway" if they see the warning.

### Common Pitfalls

- **EV != instant trust anymore.** Any blog post or CA sales page still claiming EV bypasses SmartScreen is outdated. Microsoft killed this in 2024.
- **Certificate expiry kills in-place updates if you didn't timestamp.** An unsigned timestamp means the signature is only valid while the cert is valid. After expiry, Windows may show warnings.
- **Don't use a different cert for your installer vs your updater.** Reputation is per-certificate-subject. Splitting across certs splits your reputation.
- **Azure Artifact Signing is not available to individuals in most countries** (USA/Canada only for individuals; orgs in USA/CA/EU/UK). If you're a one-person LLC in Singapore, you need a traditional CA.
- **SmartScreen reputation does NOT transfer across certificate renewals automatically.** Keep the same subject name, same CA if possible, and start signing with the new cert 2-4 weeks before the old one expires.

## 3. Android APK Signature Scheme v3/v4

### 2026 Best-Practice Summary

Android's APK signing has three active schemes: v2 (whole-file, Android 7+), v3 (key rotation support, Android 9+), and v4 (incremental install via fs-verity Merkle tree, Android 11+). The 2026 standard is to sign with **v1 + v2 + v3 + v4 simultaneously** - the `apksigner` tool does this by default based on `minSdkVersion`. v1 (JAR signing) is still required for devices running Android 6 and below, though by 2026 the vast majority of devices are on 9+.

**v3 key rotation** (via `apksigner rotate`) is the mechanism that lets you change your signing key without breaking updates for existing users. It works by embedding a "proof-of-rotation" linked list in the v3 signing block: each node contains the old signing cert, and the new cert signs the previous one, creating a chain of trust. `apksigner rotate --old-signer --ks A.keystore --new-signer --ks B.keystore` produces a lineage file. You then sign with `--lineage lineage.bin`. On Android 13+ (API 33), `checkSignatures` recognizes the rotation proof and returns the newest signature. On Android 9-12, the original signer is used.

**v3.1** (Android 13+) adds SDK-version targeting: the rotated signer is only used on API 33+, while older devices still see the original signer in the v3 block. This is critical for backward compatibility.

**v4** is a separate `.apk.idsig` file containing a Merkle hash tree (identical structure to Android's `fs-verity` format). It enables `adb install --incremental` and Play Store's incremental update mechanism - only changed blocks are downloaded. v4 requires a complementary v2 or v3 signature and does NOT provide security on its own.

**Play App Signing**: If you enrolled in Play App Signing (now the default for new apps), Google's key signs your app. You upload with your upload key, and Play re-signs with their key. Key rotation under Play App Signing is done through the Play Console UI, not via `apksigner rotate`. Your upload key is separate from the app signing key.

**What `cap build android` produces**: Capacitor generates a standard Gradle project. The signing is configured in `android/app/build.gradle` under `signingConfigs`. By default, debug builds use `debug.keystore`. Release builds require you to configure your release keystore and enable v2/v3/v4 signing explicitly. `apksigner verify --print-certs` checks all signing blocks (v1, v2, v3, v3.1) and prints the certificate chain, verifying the signature is intact.

**Sources**:
- Android apksigner docs (rotate, v3, v4): https://developer.android.com/tools/apksigner
- APK Signature Scheme v3: https://source.android.com/docs/security/features/apksigning/v3
- APK Signature Scheme v3.1: https://source.android.com/docs/security/features/apksigning/v3-1
- APK Signature Scheme v4: https://source.android.com/docs/security/features/apksigning/v4
- apksigner help_sign.txt (full CLI reference): https://android.googlesource.com/platform/tools/apksig/+/refs/heads/main/src/apksigner/java/com/android/apksigner/help_sign.txt
- OWASP MASTG-BEST-0006: https://mas.owasp.org/MASTG/best-practices/MASTG-BEST-0006/
- DoveRunner v3 key rotation verification guide: https://support.doverunner.com/hc/en-us/articles/60228513234457-APK-Signature-Scheme-v3-Key-Rotation-Verification-Guide

### Minimum Viable Implementation (Week 1)

1. **Generate a release keystore**: `keytool -genkey -v -keystore airiz-release.keystore -keyalg RSA -keysize 4096 -validity 10000`
2. **Configure `build.gradle`**: enableV2Signing true, enableV3Signing true, enableV4Signing true
3. **Verify after build**: `apksigner verify --print-certs --verbose app-release.apk`
4. **Store the keystore in your CI secrets** (encrypted). Losing it means you cannot update the app on the Play Store.
5. **If using Play App Signing**: your upload key is separate. Request key rotation via Play Console if ever needed. You don't use `apksigner rotate`.

### Common Pitfalls

- **Forgetting v4**: If you don't enable v4, Play Store incremental updates don't work for your app. Users download the full APK every time. Enable it.
- **Key rotation is NOT the same as cert renewal.** v3 rotation lets you change to a completely new key. A cert renewal (same key, new cert) doesn't need rotation.
- **Both old and new keys must be registered in your security app** (e.g., AppSecurity, Play Console) after rotation. Old OS versions still verify with the old key.
- **Capacitor doesn't auto-configure v3/v4.** You must explicitly set `enableV3Signing true` and `enableV4Signing true` in your `signingConfigs`.
- **Don't sign debug builds with your release key.** Use `--debuggable-apk-permitted false` in production CI. A leaked debug APK signed with your release key is a disaster.
- **Play App Signing means Google holds your app signing key.** If you leave Google Play, you lose the ability to update your existing users. Factor this into your platform strategy.

## 4. iOS App Signing Chain + Provisioning Profile Lifecycle

### 2026 Best-Practice Summary

Apple's signing model is the most rigid of the major platforms. Every app binary is cryptographically bound to a provisioning profile, a distribution certificate, and an App ID. The chain is: **Apple Root CA - Apple Worldwide CA - Your Developer ID / Distribution Certificate - Provisioning Profile - App Binary**. If any link breaks, the app won't launch.

**Apple Developer Program** (99/year) is the gate. Your membership must be active to generate new certificates, provisioning profiles, and to submit to the App Store. However, **existing apps continue to run after membership expiry** - Gatekeeper/App Store validation checks the cert was valid at compile time, not at launch time. The exception is Developer ID provisioning profiles for macOS: those are validated at every launch.

**Provisioning profile lifecycle**:
- **Development profiles**: Tied to specific registered devices (max 100 per year per team). Expire when a certificate is revoked, a device is removed, or services are changed. Xcode-managed profiles are regenerated automatically.
- **Ad Hoc profiles**: Same device list model, for TestFlight-style distribution outside the App Store.
- **App Store distribution profiles**: No device list. Used when uploading to App Store Connect.
- **Developer ID profiles (macOS)**: Valid for 18 years from creation (regardless of cert expiry). Required for advanced capabilities (CloudKit, push) in Developer ID-distributed Mac apps.
- **PPQ check-in**: Teams created after June 6, 2021 must check in with Apple's PPQ service (`https://ppq.apple.com`) on first launch of development/Ad Hoc apps. Devices behind firewalls must allow this connection.

**App Attest** (WWDC 2026) is Apple's device-integrity proof. It generates a Secure Enclave-bound key pair, and your server can verify that the app is running on genuine, unmodified Apple hardware. New in iOS 27: it surfaces the launch validation category (App Store vs TestFlight vs Ad Hoc) and bundle version, letting you detect re-signed or modified apps. For AIRIZ, App Attest is relevant if you need to prove to your backend that a request came from a legitimate AIRIZ app instance (anti-fraud, license enforcement).

**DeviceCheck** is simpler: a 64-bit counter per app per device, used for fraud detection (e.g., "this device has been used to create 47 accounts"). It requires Apple's backend and can't be self-hosted.

**Distribution types**:
| Type | Use case | Signing |
|------|----------|---------|
| App Store | Public release | App Store distribution profile |
| TestFlight | Beta (up to 10K external) | App Store distribution profile |
| Ad Hoc | Internal (100 devices max) | Ad Hoc profile + device list |
| Developer ID (macOS) | Outside Mac App Store | Developer ID cert + 18-yr profile |
| Enterprise (MDM) | Internal corporate only | Enterprise profile (no App Store) |

**2024-2025 signing identity changes**: Apple's migration to Apple Silicon means Developer ID certificates are now tied to the Secure Enclave of the signing Mac. The "Cloud Keychain" option lets you manage signing remotely, but the key never leaves Apple's servers. For CI, use `xcodebuild` with a certificate stored in the CI's keychain, or use App Store Connect's automated signing.

**App Store Connect API tokens** (JWT, ES256): These are how you automate App Store operations (upload, release, TestFlight management) without the GUI. Generate them in App Store Connect - Users and Access - API. They expire (set at creation, max 1 year) and are scoped (Access level: Admin, App Manager, etc.).

**Sources**:
- Apple Developer Program: https://developer.apple.com/programs/
- Provisioning profile updates (PPQ, DER-encoded): https://developer.apple.com/help/account/provisioning-profiles/provisioning-profile-updates/
- Developer ID certificate lifecycle: https://developer.apple.com/help/account/certificates/create-developer-id-certificates/
- App Attest (WWDC 2026): https://developer.apple.com/videos/play/wwdc2026/201/
- App Store phased release docs: https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/
- Xcode Signing and Capabilities: https://help.apple.com/xcode/mac/current/en.lproj/dev60b6fbbc7.html
- Notarization: https://developer.apple.com/documentation/xcode/notarizing_macos_software_before_distribution

### Minimum Viable Implementation (Week 1)

1. **Enroll in Apple Developer Program** (99/yr). If you're a one-person team, use the "Individual" entity. If Ziris PTB is the entity, use "Organization" (requires D-U-N-S number).
2. **Enable App Store Connect API access**. Generate a token with "App Manager" scope. Store it in CI.
3. **Use Xcode's automatic signing** for development. For CI/CD, export your distribution certificate + profile and store in CI secrets.
4. **For Capacitor iOS builds**: Configure the `ios` platform with your bundle ID. Use `xcodebuild archive` + `xcrun altool --upload` (or the newer `xcrun notarytool`) in your CI pipeline.
5. **For OTA updates of the JS layer** (Capacitor): Use a solution like Capacitor Live Updates or a custom CDN-hosted bundle. The native binary still goes through the App Store.

### Common Pitfalls

- **Provisioning profile expiry breaks TestFlight/Ad Hoc builds.** If your cert is revoked or you change services, ALL existing profiles are invalidated. You must regenerate and re-distribute.
- **App Store phased release is NOT a kill switch.** It only controls automatic updates. Users can still manually tap "Update" and get the new version immediately. Your 1% "canary" is actually larger than 1% of users.
- **You cannot roll back on the App Store.** Once a version is released, you can only remove it from sale (it stays on devices that have it) or submit a new version. Plan accordingly.
- **Membership expiry**: Your existing App Store apps keep working, but you can't submit new versions or get new certificates. Renew before expiry.
- **The 100-device Ad Hoc limit is per YEAR, not per profile.** Once you hit it, you must wait for the annual reset. Plan your beta device list carefully.
- **App Attest keys are per-device and per-install.** If a user reinstalls, the key is invalidated. Your server must handle "unknown attestation key" gracefully.

## 5. PWA Subresource Integrity + Service Worker Update Traps

### 2026 Best-Practice Summary

The PWA update problem is the most complex of the five platforms because the browser is both the runtime AND the update mechanism, and you don't control the process. The service worker lifecycle has three states (installing, waiting, active) and the transition between versions is where most production bugs live.

**The core problem**: When a new service worker is fetched and installed, it enters the "waiting" state. It only becomes "active" when ALL pages controlled by the old worker are closed. This means if a user has 3 tabs open, they stay on the old version until they close all 3 tabs. The new code is sitting in the waiting state, invisible.

**`skipWaiting()`** forces the new worker to activate immediately, but this creates the "mixed-version client" problem: the HTML was loaded by the old worker (which fetched scripts A, B, C), but the new worker is now handling subsequent fetches. If build N+1 renamed `chunk-a1b2.js` to `chunk-c3d4.js` and deleted the old cache, the open page's lazy import fails. The user sees a broken page.

**The correct 2026 pattern** (Workbox `workbox-window` + `BroadcastChannel`):
1. Do NOT call `skipWaiting()` during install. Let the worker wait.
2. Detect the waiting worker from the page via `workbox-window`'s `waiting` event.
3. Show the user an "Update available" modal/banner.
4. On user confirmation, send `postMessage({type: 'SKIP_WAITING'})` to the waiting worker.
5. The worker calls `self.skipWaiting()`, activates, and calls `clients.claim()`.
6. The page listens for `controllerchange` and does `window.location.reload()`.
7. Use a one-shot flag to prevent double-reload from multiple tabs.

**Cross-tab fan-out**: `BroadcastChannel` lets the service worker notify ALL open tabs simultaneously when an update is available. Workbox's `workbox-broadcast-update` module does this for cache updates. For SW lifecycle events, use the native `BroadcastChannel` API (Safari support: iOS 15.4+, 2022 - so it's universal in 2026).

**SRI (Subresource Integrity)**: For the manifest.json and critical JS bundles, add `integrity="sha384-..."` attributes. This protects against CDN compromise: if the served file doesn't match the hash, the browser refuses to execute it. However, SRI is static - it breaks on every deploy unless you regenerate hashes. For a PWA that updates via service worker, SRI is most useful for the *initial* load of the manifest and the SW script itself (which is fetched without SW interception).

**Real PWA incidents**:
- **Twitter/X** (2023): A service worker caching bug caused the "What's happening" tab to show stale content for hours. The SW was caching API responses with a stale-while-revalidate strategy, but the revalidation was failing silently.
- **Starbucks** (2018): Their PWA's service worker cached an old version of the ordering flow. After a backend API change, cached JS called the old API shape, causing 400 errors for all users with the old SW active.
- **Notion** (2020): A SW update race caused some users to be stuck on an old version indefinitely because `skipWaiting` was called on the wrong worker instance (the active one, not the waiting one).

**Sources**:
- web.dev Service Worker Lifecycle (Jake Archibald): https://web.dev/articles/service-worker-lifecycle
- Workbox: Handling SW updates: https://developer.chrome.com/docs/workbox/handling-service-worker-updates
- web.dev: Broadcast updates to pages: https://web.dev/articles/broadcast-updates-guide
- web.dev: PWA Update: https://web.dev/learn/pwa/update
- Workbox issue #1995 (skipWaiting not activating): https://github.com/GoogleChrome/workbox/issues/1995
- SW update semantics and skipWaiting (2025): https://mercemay.com/articles/web-platform/progressive-web/service-worker-update-semantics/
- Workbox service worker lifecycle: https://developer.chrome.com/docs/workbox/service-worker-lifecycle
- W3C Service Worker spec: https://www.w3.org/TR/service-workers-2/

### Minimum Viable Implementation (Week 1)

1. **Use Workbox** (v7.x) with `injectManifest` mode. Configure `skipWaiting: false` (the default).
2. **Add the update modal pattern**: detect waiting worker, show modal, on confirm call `messageSkipWaiting()`, on `controlling` event reload the page.
3. **Add `clients.claim()` in the activate handler** so the new SW takes over open tabs immediately after activation.
4. **Version your SW**: Change the file content (not the URL) on each deploy. The browser detects the byte-difference and triggers the update flow.
5. **SRI**: Add `integrity` hashes to your `<script>` and `<link>` tags for the initial page load. Regenerate on each build (your bundler can do this).
6. **Prune old caches** in the activate handler: filter `caches.keys()` and delete anything not in the current version's allow-list.

### Common Pitfalls

- **`skipWaiting()` in the install handler is the #1 cause of broken PWAs.** It creates the mixed-version client. Never do it unconditionally.
- **`controllerchange` can fire multiple times** (one per tab that reloads). Use a one-shot flag.
- **Safari historically didn't support `BroadcastChannel`** (fixed iOS 15.4, 2022). In 2026 it's universal, but if you support very old iOS, fall back to `postMessage` via the SW.
- **The SW URL must not change.** If you rename `sw.js` to `sw-v2.js`, the browser treats it as a new registration, not an update. The old SW keeps running forever.
- **`event.waitUntil()` with a promise that never resolves** will prevent `skipWaiting()` from completing. Check for hung service workers in DevTools.
- **Caching headers**: Chrome 68+ ignores caching headers when checking for SW updates, but respects them for `importScripts()`. If you use `importScripts()`, you need cache-busting query strings.

## 6. Cloudflare Worker Signed Deploys

### 2026 Best-Practice Summary

Cloudflare Workers has a mature version/deployment/rollback model. The key insight: **uploading a version and deploying it are separate operations.** `wrangler versions upload` creates a new version without making it live. `wrangler versions deploy` routes traffic to uploaded versions. This separation enables gradual deployments (split traffic between two versions at N%/M%) and instant rollback.

**Authentication model**: `CF_API_TOKEN` is an environment variable containing a Cloudflare API token. The token is scoped by **roles** (Metadata Read-Only, Content Read-Only, Editor, Admin) and **scopes** (per-Worker, per-account, per-zone). For CI/CD, create a token with `Editor` scope on your specific Worker. This lets it deploy and rollback but not create/delete Workers or modify routes.

**Version pinning**: Each upload gets a unique version ID. Deployments reference version IDs explicitly. `wrangler versions deploy v1234@100` pins 100% of traffic to version `v1234`. You can split: `wrangler versions deploy v1234@90 v5678@10` for a 90/10 canary.

**Rollback**: `wrangler rollback [VERSION_ID]` immediately creates a new deployment pointing to the specified version at 100% traffic. Limits: you can only roll back to the **100 most recent versions**. Rollback does NOT rollback bound resources (KV, D1, R2, Durable Objects) - if your schema changed, the rollback will fail or produce errors.

**Audit log** (v2, Beta since March 2025): Cloudflare now auto-generates audit logs for all API and Dashboard actions. Coverage went from 75% to 95%. The API endpoint is `GET /accounts/<id>/logs/audit?since=<date>`. Each entry includes the auth method, interface (API/Dashboard), and Ray ID for traceability. For a one-person team, this means: if you accidentally deploy a bad version, you can see exactly when and how it happened.

**Workers for Platforms**: If AIRIZ ever becomes a multi-tenant platform (e.g., letting users deploy custom Worker code), Workers for Platforms provides per-tenant V8 isolate isolation. Each customer's code runs in its own Worker within a "dispatch namespace." Untrusted mode (default) disables `request.cf`, isolates caches, and prevents cross-tenant data access. The dispatch Worker routes requests to the right tenant Worker. For a one-person team shipping a single Worker, this is irrelevant - but it's the escape hatch if you ever need it.

**Multi-script deploy limit**: A single `wrangler deploy` deploys one Worker script. If you have multiple Workers (e.g., an API Worker + a PWA Worker), you deploy them independently. There's no atomic multi-Worker deploy. If you need coordinated deploys, use a deployment script that uploads all versions first, then deploys them in sequence.

### Minimum Viable Implementation (Week 1)

1. **Create a Cloudflare API token** with `Editor` scope on your Worker. Store as `CF_API_TOKEN` in your CI environment.
2. **Pin your wrangler version**: `npx wrangler@4.47.0 deploy` (or whatever the latest stable is). Don't use `@latest` in CI.
3. **Deploy flow**: `npx wrangler versions upload --name airiz-worker` then `npx wrangler versions deploy <VERSION_ID>@100 --name airiz-worker --message "v1.0.0"`
4. **Rollback flow** (in your incident runbook): `npx wrangler rollback --name airiz-worker --message "revert to last stable"`
5. **Set up a simple canary** (optional for week 1): deploy new version at 10%, old at 90%. Watch logs for 30 min. Then promote to 100%.

### Common Pitfalls

- **Rollback does NOT rollback KV/D1/R2/Durable Objects.** If your new version added a D1 migration, rolling back to the old version will fail because the schema has changed. Plan your data migrations to be backward-compatible.
- **The 100-version rollback window** means if you deploy more than 100 times without rolling back, the oldest versions fall out of the rollback pool. For a one-person team shipping weekly, this is fine.
- **`wrangler deploy` (the simple command) uploads AND deploys atomically.** You lose the ability to canary. Use `versions upload` + `versions deploy` for anything production.
- **Secrets are not versioned.** `wrangler secret put` changes the secret for ALL versions. If you roll back, the secret stays at its current value. The wrangler CLI warns you about this during rollback if secrets changed.
- **API token scope creep**: Start with `Editor` on one Worker. Don't give `Admin` at the account level. You don't need it.

## 7. Staged Rollouts

### 2026 Best-Practice Summary

Every major platform has a staged rollout mechanism, but they work differently and have different blast-radius semantics:

| Platform | Mechanism | Percentages | Widening | Stop | True rollback? |
|----------|-----------|-------------|----------|------|----------------|
| **App Store** | Phased release | Fixed: 1,2,5,10,20,50,100% over 7 days | Automatic (daily) | Pause (30 days total) | No - ship new version |
| **Play Store** | Staged rollout | Any % you choose | Manual (you raise it) | Halt + resume | No - ship new version |
| **Expo Updates (OTA)** | Per-update / branch rollout | Any % you choose | Manual | Revert rollout | **Yes** - republish old bundle |
| **Cloudflare Workers** | Split deployment | Any % (e.g., 10/90) | Manual | Rollback | **Yes** - `wrangler rollback` |
| **Windows (Squirrel/Tauri)** | Manual (your updater) | Any % (your logic) | Manual | Stop sending manifest | **Yes** - point manifest at old version |

**The critical asymmetry**: Store-based rollouts (App Store, Play) control who *receives* the update, but cannot take it back. Once a user has installed the new binary, halting the rollout does nothing for them. The only fix is shipping a new version. OTA rollouts (Expo, Cloudflare, custom updaters) CAN roll back because the client checks for updates on launch - you can republish the old bundle and users pick it up on next launch.

**What "stable" means** (from the Google SRE Workbook): A canary is stable when:
1. Enough traffic has flowed to be statistically representative (typically 1-10% of total users, or enough requests to detect a 1% error rate increase with 95% confidence)
2. The observation window covers at least one peak traffic period (diurnal patterns)
3. Key metrics (error rate, p95 latency, crash-free sessions) are within threshold of the control group
4. The canary has been running for at least 30-60 minutes (or longer for low-traffic apps)

Google's SRE teams moved from manual graph inspection to **automated canary analysis** because "the release engineer gets used to seeing no problems and tends to implicitly rationalize monitoring anomalies as noise." The automated system measures elevated errors, latency, and load, and rolls back automatically if thresholds are breached.

**The kill switch pattern** (from TPM PrepBase and Expo's production playbook): Every risky feature ships behind a server-side flag, defaulting to OFF. The flag is read at app launch and cached for offline use. If something breaks in production, you flip the flag - the fix propagates on next app launch (seconds to minutes for OTA, days for store binaries). Firebase Remote Config, LaunchDarkly, Statsig, or a JSON file on your CDN all work.

**Sources**:
- Apple phased release: https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/
- Google Play staged rollout: https://support.google.com/googleplay/android-developer/answer/6346149
- Expo Updates rollouts: https://docs.expo.dev/eas-update/rollouts/
- Expo production playbook: https://expo.dev/blog/the-production-playbook-for-ota-updates
- Expo staged rollout article (2026-10): https://expo.dev/articles/updates-and-rollouts/staged-rollout
- Google SRE Workbook: Canarying Releases: https://sre.google/workbook/canarying-releases/
- Google Cloud Blog: Release canaries (Adrian Hilton): https://cloud.google.com/blog/products/gcp/how-release-canaries-can-save-your-bacon-cre-life-lessons
- TPM PrepBase: Rollout and Kill Switches: https://tpmprepbase.com/mobile/release/rollout/
- Loglune: Canary Deployment 6 Steps: https://loglune.com/blog/canary-deployment

### Minimum Viable Implementation (Week 1)

1. **Cloudflare Worker**: Use `wrangler versions deploy` with a 10/90 split for the first 30 minutes, then promote to 100%.
2. **PWA**: Your service worker IS the rollout mechanism. Deploy to your CDN, and the SW update flow handles distribution. Add a "kill switch" JSON endpoint: `GET /api/config` returns `{"newFeatureEnabled": false}`. Your app fetches this on launch.
3. **Android (Play Store)**: Use staged rollout at 10% for the first release. Monitor Play Console vitals (ANR rate, crash rate) for 24 hours. Then raise to 100%.
4. **iOS (App Store)**: Enable phased release. Accept the 7-day timeline. You can't do better without TestFlight.
5. **Windows (Tauri updater)**: Your manifest endpoint IS the rollout. Ship v1.0.0 to a `/stable` endpoint. If something breaks, point `/stable` back at v0.9.0. Users check on next launch.

### Common Pitfalls

- **App Store phased release is NOT a 1% canary.** Anyone can manually tap "Update" and get the new version immediately. Your "1%" is actually 1% + however many people manually update.
- **Play Store halt != rollback.** Users who already got the update keep it. You must ship a new version to fix them.
- **Don't run multiple canaries simultaneously** (SRE workbook). One canary = one variable. Multiple canaries = signal contamination.
- **The observation window must cover peak traffic.** A canary that's clean at 3 AM but hits a load bug at 6 PM is not stable. Wait at least one full diurnal cycle (24h) before declaring victory.
- **OTA rollouts have a "cold start" delay.** Users only check for updates when the app launches. A 10% rollout doesn't mean 10% of users update in 10 minutes - it means 10% are *eligible* to receive the update on their next launch.
- **The kill switch must be cached offline.** If the user's phone loses connectivity after you flip the flag, the cached "enabled" value means the feature stays on. Cache with a TTL (e.g., 1 hour) and default to OFF when the network is unavailable and the cache is stale.

## 8. Crash-Throttled Rollback (Telemetry-Gated Deploys)

### 2026 Best-Practice Summary

The "deploy gate" pattern (popularized by Charity Majors at Honeycomb and formalized in the Google SRE Workbook) is: **automatically halt or rollback a deployment when crash/error metrics breach a threshold.** The key design decisions are: (1) what metric to gate on, (2) what threshold constitutes "bad," (3) how long to observe before deciding, and (4) what action to take (halt, rollback, page a human).

**Sentry Release Health** (GA in 2024, Session Health in Open Beta May 2025) provides:
- **Crash-free sessions**: % of sessions not ended by a crash
- **Crash-free users**: % of distinct users who didn't crash
- **Release adoption**: % of total sessions on each release
- **Session health statuses**: Healthy, Errored, Crashed, Abnormal, Unhandled (new in v25.9.0)
- **Crash rate monitors**: Alert when crash-free % drops below a threshold

Sentry distinguishes between **sessions** (always sent, no sampling, no inbound filters) and **issues** (error events, subject to sampling and filters). Session data is the correct signal for deploy gating because it's complete - you know the denominator (total sessions) and the numerator (crashed sessions).

**Bugsnag Stability Score** (Preferred/Enterprise plans):
- **User stability**: % of users error-free within a day
- **Session stability**: % of sessions error-free
- **Stability targets**: Set a "target" (e.g., 99.5%) and a "critical" threshold (e.g., 99.0%). Below critical = red indicator.
- Rate-limited events are NOT counted (artificially inflating stability during rate limits - a known caveat).

**Rollbar** focuses on deploy/version tracking: it tags every error with the deployment version, lets you see "new issues introduced by release X," and has a workflow for release triage. Its strength is grouping and ownership handoff rather than a single stability score.

**The decision latency budget**: For a one-person team, the practical budget is:
- **Detection**: 5-15 minutes (time for enough crashed sessions to accumulate at 10% rollout)
- **Decision**: Automated (threshold breach - trigger rollback). No human in the loop for the first response.
- **Rollback execution**: less than 1 minute (Cloudflare: instant. PWA: republish old bundle. Play: halt. App Store: can't do much).
- **Total time from bad deploy to rollback**: less than 20 minutes for OTA platforms, less than 24 hours for store binaries.

**False-positive risk**: The SRE workbook warns that "the release engineer gets used to seeing no problems and tends to implicitly rationalize monitoring anomalies as noise." The counter is automated thresholds: if crash-free sessions < 99.5% for 3 consecutive 5-minute windows at 10% rollout, auto-rollback. No human judgment. No "it's probably fine." The threshold is the policy.

**Datadog Continuous Profiler** is relevant for performance regressions that don't crash but are slow (e.g., a new algorithm that is O(n squared) instead of O(n log n)). It profiles production code without instrumentation, showing CPU/flame-graph data per deploy. Overkill for a one-person team in 2026, but worth knowing about.

**Sources**:
- Sentry Release Health: https://docs.sentry.io/product/releases/health/
- Sentry Session Health (Open Beta, May 2025): https://blog.sentry.io/introducing-session-health-in-sentry-now-in-open-beta/
- Bugsnag Stability docs: https://docs.bugsnag.com/product/stability/
- Bugsnag Releases dashboard: https://docs.bugsnag.com/product/releases/releases-dashboard/
- Sentry vs Rollbar vs Bugsnag 2026: https://www.stackfyi.com/guides/error-tracking-sentry-vs-rollbar-vs-bugsnag-2026
- Google SRE Workbook: Canarying: https://sre.google/workbook/canarying-releases/
- Google Cloud: Release canaries save your bacon: https://cloud.google.com/blog/products/gcp/how-release-canaries-can-save-your-bacon-cre-life-lessons
- Loglune: Canary Deployment (pass criteria): https://loglune.com/blog/canary-deployment

### Minimum Viable Implementation (Week 1)

1. **Sign up for Sentry** (free tier: 5K errors/month, 10K sessions/month). Integrate `@sentry/electron` (Windows), `@sentry/react-native` (Android/iOS), `@sentry/browser` (PWA), and `@sentry/node` (Worker).
2. **Set a crash rate monitor**: Alert (Slack/email) when crash-free sessions < 99.0% for any release.
3. **For Cloudflare Worker**: If error rate > 5% for 5 minutes, auto-rollback via `wrangler rollback`. You can script this with a cron job that queries the Workers metrics API.
4. **For PWA**: If Sentry reports a crash spike on the new SW version, republish the old bundle to your CDN. The SW update flow will pick it up on next launch.
5. **For Play Store**: Monitor Play Console vitals. If ANR rate > 1% or crash rate > 0.5% at 10% rollout, halt the rollout.

### Common Pitfalls

- **Session data != issue data.** Sessions are always sent (no sampling). Issues are sampled and filtered. Gate on sessions, not issues.
- **"Abnormal" sessions are not crashes.** A user who kills the app (swipes it away on Android) generates an "abnormal" session, not a "crashed" one. Don't gate on abnormal sessions.
- **Small user bases make statistical gates unreliable.** If you have 100 DAU, 10% rollout = 10 users. One crash = 10% crash rate. Your "99.5% crash-free" threshold is meaningless at that scale. For small apps, gate on absolute counts (e.g., "more than 3 crashes in 15 minutes") rather than percentages.
- **Rate limiting inflates stability scores.** Bugsnag explicitly warns: rate-limited events don't count toward the score, but sessions do. During a crash storm, your stability score looks artificially good.
- **The SRE workbook's "don't run multiple canaries" rule applies here too.** If you're rolling out both a new Worker version AND a new PWA SW at the same time, and crashes spike, you don't know which one caused it.
- **Automated rollback must be safe.** If your rollback triggers a DB migration rollback that loses data, you've made things worse. The SRE workbook: "this only works if rollbacks are safe!"

## 9. Delta Updates

### 2026 Best-Practice Summary

Delta updates compute the minimal binary difference between version N and version N+1, so the client downloads only the changes (typically 5-30% of the full update size for minor releases). The algorithms, in order of sophistication:

1. **bsdiff** (Colin Percival, 2003): Byte-level binary diff using a suffix array + bzip2 compression. Simple, portable, no platform-specific knowledge. The foundation that everything else builds on.
2. **xdelta3**: Similar to bsdiff but with a different VCDIFF-based encoding. Often slightly better compression than bsdiff for certain file types.
3. **zsync** (Colin Adams): Block-based chunking with SHA-1 checksums. Designed for resumable downloads of large files. Not a true binary diff - it's a "which blocks changed" protocol.
4. **Courgette** (Google, 2009, for Chromium): Disassembles the PE/ELF binary, replaces pointers with labels, diffs the disassembly with bsdiff, then reassembles. Achieved 10x smaller patches than bsdiff for Chrome (704 KB to 79 KB for a 10 MB update).
5. **Zucchini** (Google, replacement for Courgette): Same idea but more robust. Instead of full disassembly, it annotates typed references (relative branches, absolute pointers, relocations), finds large equivalent regions, and translates references. A missed reference costs a few bytes; it never costs correctness.
6. **HDiffPatch** (houseroad, C++): A general-purpose binary differ with good compression. Used in several Chinese OTA systems. The IEEE TMC 2024 paper benchmarks it against bsdiff, xdelta3, and archive-patcher across 200 mobile apps.

**Real benchmarks**:
- **Chrome 151 (Linux x86-64, 291 MB binary)**: Full download = 81.8 MB (xz), bsdiff = 18.6 MB, Zucchini = 5.9 MB, new "presage" tool = 2.3 MB. Source: https://willjordan.us/writing/slicing-zucchini-patches/
- **Chrome 190.1 to 190.4 (2009, original Courgette paper)**: Full = 10.4 MB, bsdiff = 704 KB, Courgette = 79 KB. Source: https://www.chromium.org/developers/design-documents/software-updates-courgette/
- **Debian OTA updates (Rugix, 2025)**: Delta compression (xdelta) reduces size by 30-90% vs full compressed image, depending on update cadence. Monthly updates: ~70% reduction. Annual updates: ~30% reduction. Source: https://rugix.org/blog/efficient-delta-updates/
- **IEEE TMC 2024** (200 mobile apps): HDiffPatch and xdelta3 achieve the best compression ratios. bsdiff is competitive but slightly larger. Archive-patcher (file-level) is the worst. Source: https://dl.acm.org/doi/10.1109/TMC.2024.3407867

**CPU cost**: The bsdiff *patching* step (client-side) is roughly 100-500 ms per MB of output on modern hardware. The *diffing* step (server-side, at build time) is much slower - Zucchini on Chrome can take 20 minutes and several GB of RAM. For a one-person team, bsdiff is the practical choice: it's fast enough to run in CI, and the patch size is acceptable (typically 10-30% of full for minor updates).

**What fails when the base has drifted**:
- **Filesystem permissions**: If the user (or an admin tool) changed file permissions on the installed binary, bsdiff's patch may fail because it expects the base file to be byte-identical.
- **File timestamps**: Most delta tools don't care about timestamps (they compare content), but some installers that check "has this file been modified since install?" will reject the patch.
- **Symlinks**: If a file in the base is a symlink that the new version replaces with a regular file (or vice versa), the delta tool doesn't know how to handle the type change.
- **Partial updates / interrupted installs**: If a previous update was interrupted mid-write, the base file is corrupted. The delta tool will produce garbage. You must verify the base file's hash before applying a delta.
- **The base must be available**: You must keep the previous version's files on disk (or in a known location) to apply the delta. If the user manually deleted files, or the OS updated them, the delta fails. Sparkle handles this by keeping old updates in an `old_updates/` directory.

**Sparkle's delta updates** (macOS): Sparkle 2.x supports delta updates using a custom container format (replacing the deprecated `xar` format in v2.1.0). The delta is a compressed archive of changed files, not a bsdiff patch. It's validated by the same EdDSA signature as the full update.

**Sources**:
- Courgette design doc (Google): https://www.chromium.org/developers/design-documents/software-updates-courgette/
- Zucchini patch benchmark (2026): https://willjordan.us/writing/slicing-zucchini-patches/
- Rugix: Efficient Delta Updates (2025): https://rugix.org/blog/efficient-delta-updates/
- Hydraulic: Deltas diffed (Sparkle/Conveyor): https://www.hydraulic.dev/blog/20-deltas-diffed.html
- IEEE TMC 2024 (200-app benchmark): https://dl.acm.org/doi/10.1109/TMC.2024.3407867
- Antmicro: xdelta in RDFM (2025): https://antmicro.com/blog/2025/08/more-efficient-delta-updates-in-rdfm-with-xdelta
- Ina vs bsdiff (2024): https://lberrymage.dev/posts/ina-part-1/
- Sparkle 2.1.0 (delta format change): https://github.com/sparkle-project/Sparkle/blob/2.x/CHANGELOG
- bsdiff (Colin Percival): https://www.daemonology.net/bsdiff/

### Minimum Viable Implementation (Week 1)

**Don't implement delta updates in week 1.** Ship full updates. The complexity-to-benefit ratio is poor for a one-person team until you have:
1. A stable release cadence (weekly or more frequent)
2. Users on metered/slow connections who are complaining about update size
3. A CI pipeline that can compute deltas in less than 5 minutes

**When you do add delta updates (month 2-3)**:
1. **macOS (Sparkle)**: Delta updates are built-in. Run `generate_appcast` with the `--delta` flag. It produces `.sparkledelta` files alongside the full update. The client automatically uses the delta if the base version matches.
2. **Windows (Tauri/Squirrel)**: No built-in delta support. If needed, use `bsdiff` in your CI to generate a `.bsdiff` file. Your updater downloads the base version's hash, fetches the appropriate delta, applies it with the `bspatch` binary, and verifies the result.
3. **Android**: Play Store handles deltas automatically (v4 signature + incremental install). You don't need to do anything.
4. **PWA**: The service worker precache IS your delta mechanism. Workbox's `StaleWhileRevalidate` strategy only fetches changed assets. No bsdiff needed.
5. **Cloudflare Worker**: The Worker code is typically less than 1 MB. Delta updates are not worth the complexity. Just deploy the full version.

### Common Pitfalls

- **You MUST keep the base version available.** If you delete v1.0.0 from your CDN after releasing v1.0.1, users who are still on v1.0.0 can't get the delta. Keep at least the last 2-3 versions.
- **Verify the base before patching.** Hash the installed file before applying the delta. If the hash doesn't match the expected base, fall back to a full download. Never apply a delta to a corrupted base.
- **bsdiff is RAM-hungry on large files.** A 500 MB binary diff can use 2-4 GB of RAM. If your CI runner has 2 GB, you'll OOM. Use xdelta3 instead (lower RAM) or bump your CI memory.
- **Delta + signing = sign the delta, not the result.** Sign the delta file with your ed25519 key. The client verifies the delta's signature, applies it, then verifies the result's hash. If you sign the result, the client can't verify the delta before applying it.
- **Sparkle delta updates had a bug** (fixed in 2.3.0) where patches would fail if source files needed for diffing were not writable. If you're on Sparkle 2.x, make sure you're on >= 2.3.0.
- **For major version updates (1.0 to 2.0), deltas are often LARGER than the full update.** The Rugix benchmark shows this clearly: when changes are more than 50% of the binary, delta compression becomes counterproductive. Always offer a full download as fallback.
